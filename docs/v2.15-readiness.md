# GoldSrcOps v2.15 Release Readiness

Review date: 2026-09-17. Status: candidate preparation. No v2.15 tag,
immutable image, production rollout, or stable release has been published yet.

## Scope

The v2.15 product scope consists of two Bounded Activity Windows slices
integrated in protected `main` through pull requests
[#169](https://github.com/tov-vl/gold-src-ops/pull/169) and
[#170](https://github.com/tov-vl/gold-src-ops/pull/170):

- `GET /api/dashboard/activity` accepts optional, validated
  `window=1h|6h|24h|7d`; omission preserves the prior API behavior.
- Incidents, commands, and completed rounds are constrained by effective event
  time before each source query applies its bounded limit, followed by the
  existing deterministic global newest-first limit.
- The static-rendered Reader page defaults to `24h` and preserves range,
  server, and event-type scope through tabs, refresh, explicit server clearing,
  and empty-result navigation.
- Every server section exposes a `24h` Activity entry point already scoped to
  that server.
- Incident investigation links to `kind=incidents` for the affected server in
  the `24h` window.
- Invalid window values return a validation problem instead of silently
  widening the query.

The slices add no schema migration, response-body field,
authorization-policy change, background worker, production identity, mutation
permission, event producer, delivery activation, or game-host artifact.

This record freezes the release-candidate scope. Arbitrary date ranges,
pagination, unbounded history, saved filters, alert delivery,
gameplay-detail expansion, schema change, infrastructure change, or another UI
slice is not part of `v2.15.0-rc.1` acceptance.

## Claim Boundary

Candidate acceptance can show that an authenticated Reader can constrain the
bounded Recent Activity investigation to one fixed time window, controlled
server, and event type, and can enter that context from existing server and
incident views without exposing additional fields or mutating production
state. It cannot prove complete history, retention completeness, long-term
reliability, high availability, multi-region resilience, user adoption, or an
achieved SLO.

Public documentation may contain revision identifiers, image digests,
workflow links, sanitized counts, durations, and pass/fail results. Host and
provider identifiers, addresses, credentials, secret paths or aliases,
operator identity, raw database rows, tokens, source identities, event
identifiers, and RCON content stay outside Git.

## Compatibility And Reduced Gate

- Existing API clients may omit `window` and receive the same bounded
  latest-events behavior as before.
- The response body is unchanged. Existing clients do not need a contract
  update to ignore the new request option.
- Effective-time filtering before each source limit prevents newer
  out-of-window records from displacing an older matching result.
- The page remains static server-side rendering behind the existing `Reader`
  policy. Operator access follows the existing role hierarchy.
- Contextual links encode only the existing server, source, and range query
  parameters and add no endpoint or browser-side state.
- API and Web must be published and deployed together because the Web client
  sends the new optional window parameter.
- No EF Core migration or persistence change exists. A fresh backup, restore
  rehearsal, migration timing exercise, and previous-runtime schema rehearsal
  are therefore not v2.15 gates.
- No game-host artifact changed. Plugin activation, gameplay capture, RCON
  action, or a game-service soak would not add release-relevant evidence.
- Pull requests #169 and #170 and both post-merge workflows already exercised
  the complete application, container, and browser suites. This readiness pull
  request uses the fail-closed documentation-only fast path; the candidate tag
  still runs the complete release workflow against the exact source revision.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.14.0..main` commit and file inventory and record the
   reviewed candidate revision.
3. Require `Change Scope`, `Quality Gate`, `Container Smoke`, and `Browser
   Smoke` on the documentation-only readiness revision. The required check
   names remain present while the docs fast path avoids rebuilding unchanged
   application artifacts.

### 2. Candidate Publication

1. Create signed annotated tag `v2.15.0-rc.1` at the reviewed `main` revision.
2. Require the complete tag workflow to build and publish both API and Web
   images from that exact revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

The tag workflow is the one intentional full validation pass after repository
closure. It requires no interactive production authorization while it builds
and verifies the images.

### 3. Digest-Pinned Rollout

1. Retain the current v2.14 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, application
   container identities and restart counts, A2S state, incidents, durable
   queues, incomplete commands, and scheduled-backup freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.
5. Do not provision an identity, activate the game-event agent, install a
   plugin, start a producer or delivery path, or manufacture gameplay data.

### 4. Short Production Smoke

Collect at least three healthy read-only samples spanning at least three
minutes and stop on the first unexplained failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image
   digests.
2. Require no unexpected API or Web restart and preserve the baseline for all
   untouched containers and the game service.
3. Require the controlled server to remain recently polled and A2S-reachable
   with zero bots. Require no newly opened incident, pending-outbox growth,
   dead letter, or incomplete command. Do not drain reviewed deferred work to
   make the smoke pass.
4. Through an existing authenticated Reader-capable session, open Recent
   Activity without a range and require the `24h` default, then switch through
   `1h`, `6h`, `24h`, and `7d` while preserving the controlled server and
   selected source.
5. Open Activity from an existing server view and require the matching server
   and `24h` range; follow the incident-context entry and require that server,
   `kind=incidents`, and `24h` remain selected.
6. Verify Refresh and event-type tabs preserve the current range and server;
   verify `Clear server` removes only the server scope. A naturally empty
   window or source is acceptable; do not manufacture production data.
7. Confirm the page and browser storage contain no bearer token, credential,
   secret reference, raw database row, address, or unauthorized mutation
   control.
8. Recheck public health and scheduled-backup freshness in the final sample.

This smoke does not repeat a game-host continuity interval, soak, backup or
restore rehearsal, migration rehearsal, alert-outbox investigation, Auth0
reconfiguration, or gameplay-delivery exercise. Existing passive monitoring
continues independently.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On startup, health, authorization, window filtering, context preservation,
  navigation, or rendering failure, recreate API and Web together from the
  retained v2.14 digests.
- Do not mutate PostgreSQL, monitoring state, game-event state, RCON state,
  incident history, command history, or durable queues to make the smoke pass.
- Store sanitized production evidence outside Git as an owner-only regular
  file.

## Stable Publication Gate

Stable `v2.15.0` remains blocked until all four gates pass:

1. The candidate identity table is complete from verified publication output.
2. The digest-pinned rollout and short production smoke pass.
3. Production has either retained the candidate or cleanly rolled back with a
   documented reason.
4. A signed stable tag promotes the exact accepted API and Web digests without
   rebuilding them, and both stable references pass published-image smoke.

Candidate acceptance and stable-publication evidence belong in one short
follow-up pull request after both remote stages complete.
