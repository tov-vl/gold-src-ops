## Delivery gap found in current source

The addon registers `goldsrcops_player_lookup_enabled` with default `0`.
The [package builder](../tools/release/build-weapon-selection-sandbox.ps1) emits
only `goldsrcops_weapons_enabled "1"` for the game-host configuration.
The [installer](../ops/gameserver/weapon-selection-addon.sh) validates that exact
configuration and requires its hash to remain unchanged during an upgrade.
The [claimed upgrade workflow](../ops/gameserver/addon-upgrade.py) independently
permits only binary/dictionary changes; loader and configuration must match.
The existing [upgrade contract](v2.64-addon-upgrade-workflow.md) deliberately
preserves these constraints.

Consequently the current package cannot persistently enable lookup. A transient
RCON setting would not establish restart persistence, and a manual config edit
would leave the installation receipt and player-backup baseline inconsistent.
Changing the compiled default would also remove the agreed default-off gate.

[Compose](../ops/production/compose.yml) and its
[environment example](../ops/production/deployment.env.example) additionally need
separate, default-false API/Web search flags. These mappings do not currently
exist; setting an unmapped host variable alone would not enable the applications.

## Proposed bounded R3 prerequisite

Subject to a new scope decision under the [release process](release-process.md):

1. Add an explicit package-builder option for lookup activation. Preserve the
   legacy package configuration when omitted. An opted-in package adds only the
   reviewed lookup CVAR with value `1`; sandbox and ordinary packages stay off.
2. Teach the weapon-selection installer and claimed workflow to accept that
   exact configuration transition and its reverse. Keep the loader unchanged,
   reject arbitrary commands/values, and leave the map addon contract unchanged.
3. Include configuration bytes, metadata and hashes in the upgrade/rollback
   transaction together with binary, dictionary and receipt. Keep the accepted
   backup baseline aligned with the installed package. Preserve the current
   player vault, including changes made after deployment, during rollback.
4. Preserve empty-server checks, locks, bounded acceptance and pending-operation
   reconciliation. An interrupted or uncertain transition must not be retried
   automatically or exposed to scheduled capture as an accepted baseline.
5. Map `GOLDSRCOPS_PUBLIC_PLAYER_SEARCH_API_ENABLED` and
   `GOLDSRCOPS_PUBLIC_PLAYER_SEARCH_WEB_ENABLED` to each host's
   `PublicPlayerSearch__Enabled`, both defaulting to `false`. Separate flags allow
   API acceptance before exposing the form and hiding Web before API rollback.

This prerequisite is an extension to recovery tooling, not a request to weaken
its existing checks. The local implementation and rehearsal decision comes
before candidate freeze; exact production operations remain a later recorded
boundary. Do not publish or deploy a candidate that omits this prerequisite.

## Required focused rehearsal

- Build legacy/default-off and explicitly enabled packages. Reject unexpected
  configuration, loader drift, payload/hash mismatch and unsafe file metadata.
- Exercise the actual installer and claimed workflow on a disposable engine:
  accepted predecessor -> lookup-enabled candidate -> accepted predecessor.
  Verify lookup after cold restart and map change; verify the old package's
  behavior after rollback. Freeze the exact predecessor/candidate package hashes.
- Verify vault bytes and metadata across stopped-server transitions, then prove
  that player progress added after upgrade survives rollback. Receipt and backup
  baseline must match the final live files in each accepted state.
- Cover interruption at configuration replacement, receipt/baseline transition
  and acceptance failure. A pending operation must block backup and replay until
  reconciled. Reuse the existing tests where they own these behaviors.
- Validate effective Compose with flags absent, independently enabled and both
  enabled. Keep unrelated services, secrets, mounts and monitoring policy intact.
- Run the affected packaging/recovery smoke and complete required PR/main CI.
  The historical 0.23 -> 0.24 rehearsal does not prove the new config transition.

## Rollout and rollback plan to freeze after rehearsal

1. Refresh read-only control-plane and game baselines in the owner-only record:
   actual image digests, addon package/receipt, backup baseline, tooling revision,
   pending state, service health, mounts and monitoring hashes. Confirm rollback
   artifacts remain available. Never retain player names or private host data in
   tracked evidence. Recheck server occupancy immediately before any stop.
2. Publish the exact candidate from reviewed main and independently verify image
   digests/OCI revision and addon package hashes. Measure this real candidate's
   CI timing for the existing [timing record](ci-release-timing-2026-10.md).
3. Install the reviewed compatible recovery tooling, then upgrade the addon only
   on an empty server. Verify running version, persisted flag, protocol and
   accepted baseline independently. Stop forward progress on an unexplained
   failure or uncertain outcome; reconcile before another mutation.
4. Deploy the API digest with search enabled while Web search remains hidden.
   Accept bounded protocol/HTTP behavior before deploying/enabling Web. Recreate
   only affected services; verify unchanged services, mounts and monitoring.
5. Accept RU/EN search with and without JavaScript, keyboard/mobile behavior,
   unchanged top-ten refresh and no query leakage to URLs/logs/metric labels.
   Use synthetic data only in the disposable rehearsal. Production search may
   observe existing names without copying them into public evidence; empty
   production data does not prove duplicates or below-top-ten lookup.
6. On a documented failure, hide Web search first, then disable/restore API and
   restore the affected application digests/configuration. Roll back the addon
   through the rehearsed empty-server workflow when required, preserving current
   player data. Tooling rollback must remain compatible with any pending journal;
   do not replace it underneath an unresolved operation. No database/vault restore.
7. Promote only the accepted candidate digests without rebuilding and close the
   release evidence after independent readback. No availability/SLO claim is made.

## Monitoring and independent gates

The fixed `player_search` metric operation is already implemented. Existing
Grafana per-operation panels can show its outcomes. The current
[four-operation warning policy](web-public-api-alerts.md) excludes search.
Keep that policy unchanged for this release and explicitly accept metrics-only
search observation; no traffic or no warning does not establish search health.
A dedicated search warning policy is a separate change, not implied by this plan.

Game-client visual acceptance, two-player play and the first successful scheduled
weekly backup remain independent. They do not replace the new configuration and
rollback rehearsal, and this preparation makes no claim that they passed.
