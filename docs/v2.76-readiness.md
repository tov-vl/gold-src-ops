## Persistent activation and recovery contract

Before this extension, the package and installer supported only
`goldsrcops_weapons_enabled "1"`, while lookup defaulted to zero. A transient
RCON setting could not establish restart persistence. Manual edits would have
broken the receipt/backup baseline. The compiled lookup default remains zero.

The [package builder](../tools/release/build-weapon-selection-sandbox.ps1) now
accepts `-EnablePlayerLookup` only with `-Target game-host-addon`. Without the
option the existing package config is unchanged; sandbox activation is rejected
before creating output. Enabled config has exactly two LF-terminated lines:

```text
goldsrcops_weapons_enabled "1"
goldsrcops_player_lookup_enabled "1"
```

The [installer](../ops/gameserver/weapon-selection-addon.sh) and
[claimed workflow](../ops/gameserver/addon-upgrade.py) validate exact bytes for
both old and new config. They allow only the legacy or the above form for weapon
selection; map-menu keeps its legacy form. A changed binary and unchanged loader
are still required. Arbitrary commands/values, extra lines and NUL are rejected.
Config-only transitions are deliberately not introduced.

The installer retains configuration bytes/metadata alongside binary, receipt and
dictionary. A failed copy restores the predecessor. The existing claimed
workflow verifies all installed hashes, aligns the backup baseline after runtime
acceptance, and retains pending on unknown effects. Current player data survives
rollback. Empty-server checks, locks and no-replay rules remain unchanged. See
[upgrade procedure](v2.64-addon-upgrade-workflow.md).

[Compose](../ops/production/compose.yml) maps separate
`GOLDSRCOPS_PUBLIC_PLAYER_SEARCH_API_ENABLED` and
`GOLDSRCOPS_PUBLIC_PLAYER_SEARCH_WEB_ENABLED` variables to each host's
`PublicPlayerSearch__Enabled`, defaulting to `false`. The
[environment example](../ops/production/deployment.env.example) leaves both off.
API can be accepted before exposing Web; Web can be hidden before API rollback.

The owner's decision covers this local implementation and rehearsal. Production
operations require a subsequently frozen revision, artifacts and rollback
boundary under the [release process](release-process.md).

## Rollout and rollback plan to freeze after required CI

1. Refresh read-only control-plane and game baselines in the owner-only record:
   actual image digests, addon package/receipt, backup baseline, tooling revision,
   pending state, service health, mounts and monitoring hashes. Confirm rollback
   artifacts remain available. Never retain player names or private host data in
   tracked evidence. Recheck server occupancy immediately before any stop.
2. Publish the exact candidate from reviewed main and independently verify image
   digests/OCI revision and addon package hashes. Measure this real candidate's
   CI timing for the existing [timing record](ci-release-timing-2026-10.md).
3. Install the reviewed compatible recovery tooling, then upgrade the addon only
   on an empty server. Verify running version, persisted flag, protocol and
   accepted baseline independently. Stop forward progress on an unexplained
   failure or uncertain outcome; reconcile before another mutation.
4. Deploy the API digest with search enabled while Web search remains hidden.
   Accept bounded protocol/HTTP behavior before deploying/enabling Web. Recreate
   only affected services; verify unchanged services, mounts and monitoring.
5. Accept RU/EN search with and without JavaScript, keyboard/mobile behavior,
   unchanged top-ten refresh and no query leakage to URLs/logs/metric labels.
   Use synthetic data only in the disposable rehearsal. Production search may
   observe existing names without copying them into public evidence; empty
   production data does not prove duplicates or below-top-ten lookup.
6. On a documented failure, hide Web search first, then disable/restore API and
   restore the affected application digests/configuration. Roll back the addon
   through the rehearsed empty-server workflow when required, preserving current
   player data. Tooling rollback must remain compatible with any pending journal;
   do not replace it underneath an unresolved operation. No database/vault restore.
7. Promote only the accepted candidate digests without rebuilding and close the
   release evidence after independent readback. No availability/SLO claim is made.

## Monitoring and independent gates

The fixed `player_search` metric operation is already implemented. Existing
Grafana per-operation panels can show its outcomes. The current
[four-operation warning policy](web-public-api-alerts.md) excludes search.
Keep that policy unchanged for this release and explicitly accept metrics-only
search observation; no traffic or no warning does not establish search health.
A dedicated search warning policy is a separate change, not implied by this plan.

Game-client visual acceptance, two-player play and the first successful scheduled
weekly backup remain independent. They do not replace the new configuration and
rollback rehearsal, and this preparation makes no claim that they passed.
