Implementation date: 2026-09-04. Status: local exporter, canonical JSONL,
deterministic evaluator, least-privilege live Metrics API proof, and live B2
archive/recovery rehearsal completed. The external scheduler environment and
manual cycle are complete. Four automatic scheduled invocations have succeeded
as of 2026-09-05; recovery of a scheduled segment remains pending.
Transport-failure enrichment is fixture-proved but not connected
to a live `logs:read` credential; alert routing and a fresh 24-hour shadow remain
pending.

## Purpose And Boundary

`GoldSrcOps.AvailabilityExporter` is a standalone operator tool. It is not
included in the production API image and must run outside the control-plane
failure domain. The tool:

1. queries bounded Grafana Cloud Prometheus `query_range` windows;
2. joins Synthetic Monitoring metrics to the reviewed custom labels;
3. correlates values with the source timestamp returned by `timestamp(...)`;
4. optionally enriches no-status failures from a bounded Loki `query_range`;
5. normalizes provider data into the canonical v2.4 JSONL contract;
6. evaluates stored evidence against generated UTC minute slots; and
7. archives and recovers canonical segments through split storage credentials.

The production API, PostgreSQL, and game-server hosts do not receive provider
credentials or raw availability evidence. The tool does not retain HTTP
response bodies, Loki lines, target addresses, provider resource identifiers,
or account metadata in its canonical output.

## Export Contract

The exporter reads these metrics:

- `probe_success`;
- `probe_http_status_code`; and
- `probe_duration_seconds`.

Each query is restricted by `job`, `probe`, `environment`, `role`, and
`monitor_revision`. Custom labels are selected through `sm_check_info` using
the shared `job`, `instance`, `probe`, and `config_version` labels.

Prometheus range evaluation can repeat the last source sample. The exporter
therefore issues a matching `timestamp(...)` query for every value query and
keys observations by check identity plus source timestamp. Repeated evaluation
points produce one stable `execution_id`; conflicting values fail the export.
Supporting status and duration values are attached only when their source
timestamp matches the `probe_success` source timestamp.

When a failed sample has no HTTP status and optional log enrichment is
configured, the exporter makes one bounded query for failed HTTP-probe logs in
the same window. A detail is accepted only when its timestamp is within ten
seconds of the metric source timestamp and all matching recognized details map
to one category. Missing, unknown, or conflicting details remain
`monitor_error`; the exporter does not infer a category from phase durations.

The output is a create-only UTF-8 JSONL segment. A temporary file is flushed in
the destination directory and moved into place without overwrite. Re-running
an overlapping window creates another segment; the evaluator deduplicates
identical records by `execution_id` and rejects conflicting duplicates.

## Credentials

Create a dedicated access-policy token limited to `metrics:read`. Supply the
three values only through the process environment:

```text
GOLDSRCOPS_GRAFANA_METRICS_URL
GOLDSRCOPS_GRAFANA_METRICS_USER
GOLDSRCOPS_GRAFANA_METRICS_TOKEN
```

The URL must be an HTTPS Prometheus base URL without embedded credentials,
query parameters, or a fragment. Credentials are sent only in the Metrics API
Basic authorization header. They are not accepted as command-line options,
written to evidence, or included in normal error messages.

Optional transport-failure enrichment uses a separate credential limited to
`logs:read` and requires all three settings together:

```text
GOLDSRCOPS_GRAFANA_LOGS_URL
GOLDSRCOPS_GRAFANA_LOGS_USER
GOLDSRCOPS_GRAFANA_LOGS_TOKEN
```

The URL is the HTTPS Loki base URL. If none of these variables is set, the
metrics-only behavior is unchanged. A partial configuration fails before any
query. Log requests use a fixed label selector, a 30-second timeout, an 8 MiB
response limit, and a 5,000-line limit with one sentinel line to detect
truncation. Raw lines exist only while parsing the response; exceptions and
canonical records contain neither the line nor provider target and error text.

## Usage

Use UTC minute boundaries and write local evidence under an ignored owner-only
directory such as `artifacts/availability`:

```powershell
dotnet run --project .\src\GoldSrcOps.AvailabilityExporter -- export `
  --window-start 2026-09-04T12:00:00Z `
  --window-end 2026-09-04T13:00:00Z `
  --job <reviewed-job-label> `
  --probe <reviewed-probe-label> `
  --role primary `
  --monitor-revision v2-4-shadow-001 `
  --location <sanitized-location> `
  --output .\artifacts\availability\segment-20260904T130000Z.jsonl
```

The default export overlaps the requested start by ten minutes and queries at
15-second steps. Both values are bounded CLI options. The normalized segment
may therefore contain records before `--window-start`; this is intentional and
makes a later catch-up export safe.

Evaluate one segment or a directory of `*.jsonl` segments:

```powershell
dotnet run --project .\src\GoldSrcOps.AvailabilityExporter -- evaluate `
  --input .\artifacts\availability `
  --window-start 2026-09-04T12:00:00Z `
  --window-end 2026-09-05T12:00:00Z `
  --evaluated-at 2026-09-05T12:05:00Z `
  --monitor-revision v2-4-shadow-001 `
  --location <sanitized-location> `
  --output .\artifacts\availability\report-20260905T120500Z.json
```

The evaluator generates the denominator independently of returned rows, waits
the five-minute grace period, considers the earliest attempt in each slot
canonical, and reports the raw outcome counts. `MeetsTarget` remains `null`
while any expected slot is still inside the grace period.

## Off-host Archive

The `archive` command writes one validated canonical JSONL segment to a
dedicated private Backblaze B2 bucket through its S3-compatible HTTPS API:

```powershell
dotnet run --project .\src\GoldSrcOps.AvailabilityExporter -- archive `
  --input .\artifacts\availability\segment.jsonl
```

The object key is content-addressed from the segment SHA-256 under the fixed
`availability/v1/segments/sha256` namespace. Before upload, a read-only client
performs `HEAD`; an existing object causes a conclusive local rejection without
calling `PUT`. When the key is absent, a separate writer performs exactly one
upload. The adapter exposes no list or delete operation, and SDK retries are
disabled.

Backblaze B2 does not document atomic conditional creation for its S3-compatible
`PutObject`. The `HEAD` then `PUT` protocol therefore prevents sequential
duplicates but cannot close a race between concurrent writers. Exactly one
serialized writer may own this namespace. B2 file versioning preserves prior
versions if an operational error violates that rule, but an additional version
is still an anomaly that requires investigation.

A timeout, transport failure, `409`, `5xx`, or otherwise inconclusive response
is reported as an unknown outcome and must be investigated through a read-only
rehearsal, never by blindly retrying the upload.

After an unknown outcome, calculate the expected digest locally with
`Get-FileHash -Algorithm SHA256` and run `rehearse`. A successful verified
download proves that the original request committed; `not found` is a
conclusive result only after the provider's normal read-after-write interval.

Supply storage configuration only through the process environment:

```text
GOLDSRCOPS_B2_S3_ENDPOINT
GOLDSRCOPS_B2_REGION
GOLDSRCOPS_B2_BUCKET
GOLDSRCOPS_B2_WRITE_KEY_ID
GOLDSRCOPS_B2_WRITE_APPLICATION_KEY
GOLDSRCOPS_B2_READ_KEY_ID
GOLDSRCOPS_B2_READ_APPLICATION_KEY
```

The endpoint must be the root HTTPS S3 endpoint for the configured B2 region.
Use a separate private bucket, one prefix-scoped write-only key for `archive`,
and a different prefix-scoped read-only key for `rehearse`. Do not reuse the
PostgreSQL restic bucket, namespace, or credential. Configure bucket-managed
encryption and a reviewed 90-day lifecycle, with 45 days as the contractual
minimum.

The Backblaze console's `Write Only` preset grants more capabilities than a pure
`PutObject` permission. Bucket and prefix scoping, a 90-day key expiry, and the
absence of delete/list commands in this application limit the current shadow
slice, but the credential-level capability gap remains accepted risk. Review a
narrower custom capability set before reusing this writer pattern elsewhere.

## Recovery Rehearsal

Use the SHA-256 printed by a successful archive and the original deterministic
evaluation report:

```powershell
dotnet run --project .\src\GoldSrcOps.AvailabilityExporter -- rehearse `
  --sha256 <64-hex-digest> `
  --download-output .\artifacts\availability\rehearsal\segment.jsonl `
  --expected-report .\artifacts\availability\report.json `
  --output .\artifacts\availability\rehearsal\report.json `
  --window-start 2026-09-04T12:00:00Z `
  --window-end 2026-09-04T13:00:00Z `
  --evaluated-at 2026-09-04T13:05:00Z `
  --monitor-revision v2-4-shadow-001 `
  --location <sanitized-location>
```

The command derives the remote key from the digest, streams at most 64 MiB into
a create-only local file, verifies SHA-256, parses the canonical records, and
re-runs the evaluator with the supplied immutable inputs. It succeeds only when
the new report equals the saved report value-for-value. Credentials, bucket
names, endpoints, and object keys are not written to either report.

## Live B2 Rehearsal

On 2026-09-04, the dedicated private archive accepted one canonical 9,298-byte
segment containing 25 normalized records. A second archive attempt for the same
SHA-256 was rejected by the read-before-write guard without a second upload. A
separate read-only credential then downloaded the segment, reproduced its digest
and record count, and generated a report equal to the saved deterministic report:
15 expected slots were good, with no bad, missing, pending, or conflicting
results.

The bucket uses provider-managed encryption and a reviewed approximately 90-day
lifecycle. Reader and writer credentials are bucket- and prefix-scoped, separate
from PostgreSQL backup storage, expire after 90 days, and are kept outside Git.
This proves the current storage and recovery path only. It is not a completed
24-hour shadow, an activated `API-01` window, or evidence that the draft SLO has
been achieved.

## Transport-Failure Classification

The optional Loki adapter recognizes provider-owned blackbox-exporter failure
messages for DNS resolution and TLS certificate verification. For the generic
`HTTP request failed` message, it maps a bounded allowlist of established error
markers to DNS, TCP connect, TLS, or timeout. An unrecognized error, a marker
that matches more than one category, or multiple categories within the
correlation window remains `monitor_error`. A response that exceeds a byte or
line limit fails the export instead of returning partial evidence.

On 2026-09-04, read-only inspection confirmed that the live Synthetic
Monitoring Loki streams expose the same check, environment, role, revision, and
probe labels used by the metric queries, and that their lines use logfmt. No
failed primary-probe stream was present in the available seven-day history, so
the live provider path for each failure category is not yet proved. Contract
fixtures cover recognized, unknown, ambiguous, oversized, malformed, and
correlation cases without retaining raw target or error text.

six-hour window. GitHub scheduling is intentionally not part of the SLI: its
documented delay, drop, and inactivity-disable behavior is absorbed by bounded
overlap while Grafana remains the source of minute-level probe samples. One
concurrency group serializes scheduled and manual writers, cancellation is
disabled, and raw segments are never retained as GitHub artifacts. The
activation variable was enabled after the manual proof. After the initial delay,
four `schedule` runs succeeded between 2026-09-04T19:54:31Z and
2026-09-05T04:58:00Z. The latest
[scheduled run](https://github.com/tov-vl/gold-src-ops/actions/runs/33945949528)
completed the pinned-revision check and the export/archive step. This proves
automatic invocation, but the irregular delivery does not prove hourly
continuity or independent recovery of its archive. The workflow now maps the
three optional Loki secrets only into the export step; live credential setup,
controlled failure proof, and advancing the existing exporter pin remain rollout
actions. A separate manual DNS proof workflow reads the dispatched `main` SHA,
requires at least three distinct diagnostic `dns_error` slots, and removes the
temporary segment without archiving. It does not use the scheduler's B2 secrets

`ops/availability/README.md` for the credential boundary and runbook.
