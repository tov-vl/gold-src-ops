# v2.107 - Private game-host health overview

## Scope

One additive, read-only dashboard in the existing private Grafana, UID
`goldsrcops-game-host-overview`. It reuses the existing Prometheus datasource,
metrics and alert policies. No new service, permission, secret, SSH command,
provider integration or public endpoint is required. No game or agent restart,
backup capture, journal mutation, alert acknowledgement or client session is
part of this release. The previous dashboards remain independent.

## Reading the dashboard

Five status cards cover agent/queue, backup, storage, RAM and sampled CPU.
Unknown data is gray, a pending condition is yellow and firing is red.
"No warnings" means only that the observed scope is valid and its existing
Prometheus policies currently have no pending/firing conditions. It is not a
global game-health or availability promise. Rule evaluation can lag newly
published readings by one ordinary evaluation interval.

The cards require successful observations no older than 180 seconds, reject
future timestamps, and require a valid recording-rule sample no older than
60 seconds. Agent/storage/resources also require fresh source timestamps.
Storage requires all four fixed roles. RAM and CPU validity are independent:
a missing CPU sample must not hide usable RAM, nor must a RAM warning turn CPU
red. CPU has no utilization alert threshold; a valid sample is blue, not green.

The detail panels retain their existing per-value freshness gates. A failed
role can leave other roles readable, while the storage summary stays unknown.
CPU busy and steal are short samples around one second, not minute averages,
per-process utilization, latency or game FPS. Zero configured swap is valid.
Unsupported inode reporting is explained in the existing storage dashboard.

Backup age/source and weekly attempt/missed-slot fields are separate. A newer
manual copy does not rewrite the weekly result or acknowledge an intervention.
The warning table contains only alert name, component and pending/firing state;
an empty table is not health proof. The overview contains links to the five
existing detail dashboards and this runbook. External IRM heartbeat receipt
and notification delivery must be checked in IRM; a local firing heartbeat is
not accepted as external delivery proof.

## Installation and rollback

This is an R3 operator-dashboard change. Freeze a clean reviewed source,
the three-file immutable `game-health-overview` package and its manifest/hash.
Preserve the existing container identities, dashboard fingerprints, rules,
worker flags and backup state in the private operator record.

The fixed wrapper reuses the existing claimed dashboard protocol. It refuses
an existing UID and creates only this dashboard in the current operations
folder with `overwrite=false`. Acceptance reads back the complete model and
records its version/hash. A lost response leaves pending evidence and blocks
automatic retry. The documented rollback deletes only the exact accepted new
UID; operator edits, provisioned state or hash drift block deletion. It never
deletes an old dashboard or recreates a container.

1. Verify the package independently against the reviewed source and confirm
   the new UID is absent in the intended private Grafana.
2. Stage only the three verified files in the dedicated operator directory.
3. Execute one claimed install with the exact dashboard hash.
4. Independently check the model, all datasource queries, current freshness,
   preserved backup-history distinction and unchanged existing runtime.
5. If a gate fails, use only the exact hash-bound rollback when its recorded
   boundary still holds. Reconcile an uncertain write before another action.
6. Promote the accepted package bytes without rebuilding; close the record
   with CI, publication and production evidence distinguished.
