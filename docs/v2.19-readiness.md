# GoldSrcOps v2.19 Release Readiness

Review date: 2026-09-20. Status: remediation candidate preparation. Signed
candidate `v2.19.0-rc.2` is deployed in `CatchUp` mode with provider delivery
disabled. A bounded historical catch-up accepted the opening event, then
failed closed when the matching recovery exposed an overly strict receiver
correlation check. The source sender is disabled, the recovery remains durable
as a dead letter, and no provider action was created.

## Scope

The v2.19 release scope is Permanent Receiver Readiness:

- a dedicated durable availability-event receiver and PostgreSQL boundary;
- provider-independent ingestion and a separately gated provider dispatcher;
- exact idempotency, incident-correlation, retry, lease, and ordering behavior;
- receiver-only migrations, image, Compose, Caddy, secret, resource, backup,
  and restore contracts;
- immutable receiver-image publication and independent digest verification;
- a first persistent CatchUp placement on `gso-control-01` with both the
  control-plane sender and provider delivery disabled.

The detailed direct-provider trial, adapter decision, and local implementation
evidence are retained in
[v2.19 Permanent Receiver Readiness](v2.19-permanent-receiver-readiness.md).

## Claim Boundary

Candidate acceptance can show that the exact receiver artifact starts against
its dedicated database, accepts only authorized and valid events, preserves
idempotency and recovery correlation across restart, remains provider-muted,
and can be backed up and restored independently. It can also show that the
co-located route and resource boundary do not disturb the existing control
plane or game host.

Acceptance cannot prove a separate failure domain, high availability, human
notification, escalation delivery, sustained live sender or dispatcher
behavior, provider rate-limit recovery, long-term reliability, or an achieved
SLO. It can prove only the exact muted historical pair after the preserved
dead-letter recovery is replayed through the reviewed operator boundary.

## Compatibility And Migration Review

- The control-plane database has no v2.19 migration or model change.
- The receiver owns two additive migrations in its separate database. They
  have passed initial application, idempotent reapplication, encrypted backup,
  `100%` repository check, isolated restore, and post-restore reapplication in
  the receiver container smoke.
- API and Web remain compatible with the existing v2.18 production database
  and are not part of the first target recreation.
- Caddy adds only the exact receiver POST path and private network alias; the
  existing public API and Web routes remain unchanged.
- CatchUp mode does not require or authorize provider delivery. The production
  provider worker remains disabled throughout remediation and replay.
- The source incident failure count may increase between the opening and
  recovery events. Receiver correlation therefore treats a nondecreasing
  recovery value as the final incident value while still rejecting a lower
  value and preserving exact server, name, incident, and opening-time checks.
- This compatibility fix changes no database schema, public request shape,
  migration, retry policy, or provider behavior.
- The dedicated database and route are additive. Rollback does not down-migrate
  either database and does not delete receiver state.

## Ordered Candidate Plan

### 1. Freeze And Publish The Remediation

1. Merge the compatibility fix and its PostgreSQL regression coverage through
   protected `main` after required checks.
2. Record the exact merge SHA, confirm `v2.19.0-rc.3` and `v2.19.0` remain
   unused, and verify the commit inventory against `v2.19.0-rc.2`.
3. Create, locally verify, and push signed annotated tag `v2.19.0-rc.3` at that
   exact revision.
4. Require `Quality Gate`, `Container Smoke`, and `Browser Smoke`, followed by
   build-mode publication and independent digest verification of API, Web, and
   AlertReceiver images.
5. Stop before deployment if any artifact identity, OCI metadata, digest, or
   published-image smoke differs from the frozen revision.

### 2. Replace Only The Receiver Image

1. Retain the exact `rc.2` receiver digest, owner-only environment, dedicated
   database, backup, and rollback commands outside Git.
2. Verify the source dead letter, receiver open incident, provider-muted state,
   sender-disabled state, and unaffected runtime baselines before mutation.
3. Deploy only the independently verified `rc.3` AlertReceiver digest. Do not
   recreate API, Web, databases, Caddy, or the provider dispatcher.
4. Verify exact image identity, health, readiness, resource state, and that the
   receiver is still `CatchUp` and provider delivery is still disabled.

### 3. Reconcile The Preserved Recovery

1. Re-verify the exact dead-letter recovery identity and replay it once through
   the guarded operator endpoint with a fresh idempotency key and audit reason.
2. Start exactly one sender dispatcher against the `CatchUp` receiver. Keep
   provider delivery disabled.
3. Require the source recovery to become processed, the receiver incident to
   become resolved with the final failure count, and both receiver events to
   remain provider-suppressed.
4. Disable the sender again and verify no pending, processing, or dead-letter
   work remains for the bounded pair. Do not retry an uncertain replay or
   delivery result.

### 4. Prove Continuity And Close Acceptance

1. Confirm receiver health, dedicated database state, and zero provider work.
2. Confirm API/Web health, control-plane database and telemetry continuity,
   A2S reachability, zero bots, game-service identity, and no unexpected
   restart of unchanged components.
3. Record only sanitized counts, states, artifact identities, and workflow
   links in repository evidence.

### 5. Stop For The Next Decision

Successful muted catch-up does not authorize live sender operation or provider
delivery. Stable promotion and any provider canary remain separate decisions
after the accepted `rc.3` claim boundary is complete.

## Failure And Rollback Rules

- Stop on the first unexplained publication, migration, route, health,
  authorization, backup, restore, resource, or continuity failure.
- Before event ingestion, rollback removes the route and receiver runtime and
  leaves the dedicated database and backup intact for diagnosis.
- After any accepted ingestion, preserve receiver state and reconcile it; do
  not retry an event or delete a row merely to make a gate pass.
- Do not down-migrate either database, drain the production queue, enable a
  worker, replace a published tag, rebuild an accepted image, or alter
  unaffected API/Web/game-host runtime as an automatic recovery action.
- If Caddy rollback cannot restore the exact pre-change route boundary, stop
  and obtain a new decision rather than continuing the deployment.
