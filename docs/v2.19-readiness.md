# GoldSrcOps v2.19 Release Readiness

Review date: 2026-09-19. Status: candidate preparation. Product, receiver,
deployment, recovery, and publication contracts are integrated. Candidate
publication and every target-environment mutation remain pending.

## Scope

The v2.19 release scope is Permanent Receiver Readiness:

- a dedicated durable availability-event receiver and PostgreSQL boundary;
- provider-independent ingestion and a separately gated provider dispatcher;
- exact idempotency, incident-correlation, retry, lease, and ordering behavior;
- receiver-only migrations, image, Compose, Caddy, secret, resource, backup,
  and restore contracts;
- immutable receiver-image publication and independent digest verification;
- a first persistent CatchUp placement on `gso-control-01` with both the
  control-plane sender and provider delivery disabled.

The detailed direct-provider trial, adapter decision, and local implementation
evidence are retained in
[v2.19 Permanent Receiver Readiness](v2.19-permanent-receiver-readiness.md).

## Claim Boundary

Candidate acceptance can show that the exact receiver artifact starts against
its dedicated database, accepts only authorized and valid events, preserves
idempotency and recovery correlation across restart, remains provider-muted,
and can be backed up and restored independently. It can also show that the
co-located route and resource boundary do not disturb the existing control
plane or game host.

Acceptance cannot prove a separate failure domain, high availability, human
notification, escalation delivery, historical catch-up, live sender or
dispatcher behavior, provider rate-limit recovery, long-term reliability, or
an achieved SLO. The production pending pair must not be consumed or mutated to
make this gate pass.

## Ordered Candidate Plan

### 1. Freeze And Publish

1. Merge this readiness package through protected `main` after required checks.
2. Record the exact merge SHA, confirm `v2.19.0-rc.1` and `v2.19.0` remain
   unused, and verify the commit inventory against `v2.18.0`.
3. Create, locally verify, and push signed annotated tag `v2.19.0-rc.1` at that
   exact revision.
4. Require `Quality Gate`, `Container Smoke`, and `Browser Smoke`, followed by
   build-mode publication and independent digest verification of API, Web, and
   AlertReceiver images.
5. Stop before deployment if any artifact identity, OCI metadata, digest, or
   published-image smoke differs from the frozen revision.

### 2. Prepare The Dormant Target

1. Retain owner-only pre-change Caddy/Compose, exact v2.18 API/Web digests,
   private topology, credentials, and rollback commands outside Git.
2. Prepare the distinct receiver DNS and owner-controlled environment without
   placing secret values or private host details in repository evidence.
3. Capture control-plane, game-host, pending-queue, backup, and resource
   baselines before any target mutation.
4. Run the reviewed control-plane and receiver preflights against the exact
   candidate receiver digest.

### 3. Deploy CatchUp With Delivery Off

1. Create the dedicated receiver PostgreSQL boundary and apply both migrations
   through the exact candidate image.
2. Add the reviewed private Caddy route and start only the receiver in
   `CatchUp` mode with provider delivery disabled.
3. Do not enable `AlertDelivery__Enabled`, start a provider dispatcher, or
   consume the existing pending pair.
4. Verify exact image digest and OCI revision, non-root/read-only hardening,
   health, private metrics, authorization rejection/acceptance, resource
   limits, restart count, and service continuity.

### 4. Prove Recovery And Continuity

1. Create a fresh encrypted receiver-database backup and run a `100%`
   repository check.
2. Restore into an isolated disposable database, verify two migrations, reapply
   them idempotently, and preserve any naturally received event count without
   exposing rows in tracked evidence.
3. Confirm API/Web health, control-plane database and telemetry continuity,
   A2S reachability, zero bots, game-service identity, and no unexpected
   restart of unchanged components.
4. Confirm the production outbox pair remains pending with zero processing work
   and no new dead letter caused by this deployment.

### 5. Stop For The Next Decision

Successful dormant deployment does not authorize historical catch-up or live
delivery. Re-review the two pending events and obtain a separate bounded
decision before enabling either sender or provider worker. Stable promotion is
also deferred until the accepted v2.19 claim boundary is complete.

## Failure And Rollback Rules

- Stop on the first unexplained publication, migration, route, health,
  authorization, backup, restore, resource, or continuity failure.
- Before event ingestion, rollback removes the route and receiver runtime and
  leaves the dedicated database and backup intact for diagnosis.
- After any accepted ingestion, preserve receiver state and reconcile it; do
  not retry an event or delete a row merely to make a gate pass.
- Do not down-migrate either database, drain the production queue, enable a
  worker, replace a published tag, rebuild an accepted image, or alter
  unaffected API/Web/game-host runtime as an automatic recovery action.
- If Caddy rollback cannot restore the exact pre-change route boundary, stop
  and obtain a new decision rather than continuing the deployment.
