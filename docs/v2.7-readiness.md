# GoldSrcOps v2.7 Release Readiness

Review date: 2026-09-13. Status: release-candidate preparation; the repository
scope is integrated, while candidate publication and the bounded production
smoke remain pending.

## Scope

The v2.7 product scope is one Incident Investigation slice integrated in
protected `main` through pull request
[#128](https://github.com/tov-vl/gold-src-ops/pull/128):

- `/operator/incidents/{id}` renders one durable availability incident under
  the existing `Reader` policy.
- The Web host composes the existing incident, server, current-status, and
  bounded snapshot Reader endpoints without adding an API contract.
- Opening and recovery context uses at most 50 snapshots from each 15-minute
  boundary window, de-duplicates overlapping records, and orders them by
  observation time.
- Fleet Triage, the incident list, and per-server history link to the exact
  incident record.
- Missing records, absent retained observations, and unavailable upstream data
  fail without exposing a mutation surface or inventing a causal explanation.

The candidate baseline also carries forward the v2.6 production-acceptance and
stable-publication records merged after the signed v2.6 application revision.
Those commits are part of the candidate review boundary but do not add another
v2.7 product workflow.

This record freezes the release-candidate scope. New API endpoints, incident
acknowledgement or annotation, ownership, export, postmortem generation,
lifecycle commands, schema changes, and infrastructure changes are not part of
`v2.7.0-rc.1`.

## Claim Boundary

The target remains one single-node control plane, one Web instance, and one
controlled external game server. Candidate acceptance can show that an
authenticated user can investigate an already-retained incident in that
reference deployment without disturbing monitoring. It cannot prove root
cause, complete historical retention, high availability, multi-region
resilience, long-term reliability, real-player adoption, or an achieved SLO.

Public documentation may contain revision identifiers, image digests,
workflow links, sanitized counts, and bounded outcomes. Host and provider
identifiers, addresses, credentials, secret aliases, operator identity, raw
database rows, tokens, incident reasons, probe failure reasons, and owner-only
evidence stay outside Git.

## Compatibility Review

- No EF Core migration or persistence model change exists in the candidate
  diff. A fresh backup, restore rehearsal, migration timing exercise, and
  previous-runtime schema rehearsal are therefore not routine v2.7 gates.
- Existing API routes and mutation contracts are unchanged. The Web client
  composes existing Reader endpoints with bounded query parameters.
- The investigation route is static server-side rendering behind the existing
  `Reader` policy. Operator access follows the existing role hierarchy, while
  Reader sessions receive no mutation form.
- Current server status is explicitly separated from the historical incident;
  missing retained snapshots remain missing evidence rather than an inferred
  root cause.
- Ordinary rollback recreates API and Web from the retained v2.6 digests. The
  database and all non-application containers remain unchanged.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.6.0..main` commit and file inventory.
3. Require `Quality Gate`, `Container Smoke`, and `Browser Smoke` on the final
   candidate revision.

### 2. Candidate Publication

1. Create signed annotated tag `v2.7.0-rc.1` at the reviewed `main` revision.
2. Require build-mode publication of both API and Web images from that exact
   revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

### 3. Digest-Pinned Rollout

1. Retain the current v2.6 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, container and
   game-service identities, restart counts, A2S state, incidents, queues, and
   scheduled-backup freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.

### 4. Short Production Smoke

Run one read-only 10-15 minute session and stop on the first unexplained
failure:

1. Require public API liveness, API readiness, and Web health to return HTTP
   `200`, with candidate version, revision, and exact image digests.
2. Verify anonymous routes remain sanitized and protected routes still require
   authentication.
3. Use an existing authenticated Operator session, which includes Reader
   access, to navigate from the fleet or incident history to one already-retained
   incident. Do not create an incident for release evidence.
4. Verify the page renders the exact durable record, distinct current-server
   context, and the available opening and recovery observations. Missing
   retained observations must be presented as missing evidence.
5. Confirm the page exposes no mutation form and browser content or storage
   contains no bearer token, credential value, secret reference, or command
   payload. If unchanged OIDC makes a fresh Reader-only login unnecessary,
   reuse Reader authorization and concealment evidence from Browser Smoke on
   the exact Web digest and record that substitution explicitly.
6. Require the controlled server to remain recently polled and reachable with
   zero bots. Require no unexpected container or game-service restart, newly
   opened incident, pending outbox item, dead letter, or incomplete command.
7. Recheck public health and scheduled-backup freshness at the end.

This short smoke is sufficient for the additive read-only Web change. It is not
a new soak, recovery rehearsal, lifecycle acceptance, or SLO claim. Existing
passive monitoring and the independent `API-01` window continue without user
participation.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On candidate startup, health, OIDC, authorization, data-boundary, or rendering
  failure, recreate API and Web together from the retained v2.6 digests.
- Do not mutate the database, monitoring state, RCON state, incident history,
  or durable queues to make the smoke pass.
- A bad or missing availability minute remains bad. Do not pause, reset,
  backfill, or reinterpret `API-01`.
- Store sanitized smoke evidence outside Git as an owner-only regular file.

## Stable Publication Gate

Stable `v2.7.0` remains blocked until:

1. The candidate identity table is complete from verified publication output.
2. The digest-pinned rollout and short production smoke pass.
3. Production has either retained the candidate or cleanly rolled back with a
   documented reason.
4. A signed stable tag promotes the exact accepted API and Web digests without
   rebuilding them, and both stable references pass published-image smoke.
