# GoldSrcOps v2.22 Release Readiness

Review date: 2026-09-21. Status: candidate preparation. The End-to-End
Delivery Readiness product revision is integrated into protected `main`.
Candidate publication, target rollout, production acceptance, stable
promotion, and release closure remain pending.

## Scope

The v2.22 release scope is End-to-End Delivery Readiness:

- the configured receiver `CatchUp` or `Live` mode in the existing sanitized
  private provider-delivery status;
- server-side composition of the existing source alert-delivery snapshot and
  receiver provider-delivery snapshot;
- one Operator-only delivery chain for the control-plane sender, receiver mode,
  and provider worker;
- explicit `Safely paused`, `Partially active`, `Action required`, and `Live`
  classifications;
- fail-closed rendering of an unavailable receiver mode as `Unknown` and
  `Partially active` during a mixed-version interval;
- responsive desktop and mobile presentation while preserving the existing
  provider queue and immutable review workflow.

The view is read-only. It cannot retry, replay, delete, reclassify, unblock,
review, enable, or reconfigure delivery work.

## Claim Boundary

Candidate acceptance can show that the exact Web and AlertReceiver artifacts
compose naturally existing source and provider delivery state for an
authenticated Operator, classify the three-stage chain according to the
reviewed rules, expose only sanitized aggregate fields, and leave the receiver
and both delivery workers in their pre-rollout modes. It can also show public
health, exact image identity, unchanged durable queue and review state, and
continuity of unaffected runtime.

Acceptance cannot prove notification delivery, escalation, provider
reachability, worker liveness, throughput, retry correctness under failure,
sustained operation, high availability, long-term reliability, or an achieved
SLO. It must not enable a worker, change receiver mode, create or mutate queue
rows, or alter reviews or provider state to manufacture a chain state.

## Compatibility Review

- Neither the control-plane nor receiver database has a v2.22 migration,
  model change, backfill, or data correction.
- The receiver adds `ReceiverMode` to its existing internal status response.
  A v2.21 Web ignores the additive field.
- A v2.22 Web treats a missing or unknown receiver mode as `Unknown` and
  `Partially active`; it cannot falsely report a mixed-version chain as safely
  paused or live.
- Replace AlertReceiver before Web to avoid that temporary unknown state. No
  queue or provider mutation is possible in either order.
- The Web BFF requests both protected status snapshots server-side. Browser
  code receives neither receiver authorization nor a new public endpoint.
- The existing provider-operations authorization, public Caddy routes, roles,
  identity-provider configuration, and delivery settings are unchanged.
- Rollback restores the accepted v2.21 Web and AlertReceiver digests without a
  database, queue, authorization, API, Caddy, telemetry, identity, receiver
  mode, or game-host action.

## Ordered Candidate Plan

### 1. Merge Readiness And Freeze

1. Merge this documentation-only readiness record through protected `main`
   after its required checks pass.
2. Record the exact readiness merge SHA and retain the green product
   post-merge workflow `#35639230653` as the application gate.
3. Confirm `v2.22.0-rc.1` and `v2.22.0` remain unused and compare the final
   inventory with signed stable `v2.21.0`.
4. Retain the accepted v2.21 Web and AlertReceiver digests, owner-only
   environments, authorization file, and rollback commands outside Git.

### 2. Publish And Verify The Candidate

1. Create, locally verify, and push signed annotated tag `v2.22.0-rc.1` at the
   exact reviewed `main` revision.
2. Require the complete tag workflow followed by publication and independent
   digest verification for every workflow image.
3. Verify OCI source, revision, version, license, and immutable Web and
   AlertReceiver digests before preparing a target mutation.
4. Stop before rollout if artifact identity differs from the frozen revision.

### 3. Capture Baseline And Roll Out

1. Capture sanitized API, Web, receiver, source queue, provider queue, review,
   incident, backup, A2S, game-service, image, and restart baselines. Keep
   topology and raw rows owner-only.
2. Do not run a backup/restore rehearsal, migration action, game-host action,
   queue drain, receiver-mode change, or delivery operation for this R1 release.
3. Replace AlertReceiver and then Web with their independently verified
   candidate digests. Recreate no other component.
4. Keep the existing operations authorization unchanged, the receiver in
   `CatchUp`, and both delivery workers disabled.

### 4. Accept Or Roll Back

1. Collect at least three healthy read-only samples spanning at least three
   minutes for public API/Web health, receiver health, exact candidate identity,
   restart counts, and dependent runtime continuity.
2. Through an existing Operator session, verify the delivery chain matches
   bounded owner-only source and provider evidence and exposes no credential,
   payload, raw provider response, or mutation control.
3. Confirm Reader access remains forbidden and the provider-operations route
   remains absent from public Caddy.
4. Confirm source and provider pending, processing, dead-letter, and review
   state did not change as a side effect of observation; both workers remain
   disabled and the receiver remains in `CatchUp`.
5. On failure, restore only Web and AlertReceiver to the recorded v2.21
   digests. No database, authorization, queue, review, API, Caddy, telemetry,
   identity, receiver-mode, or game-host rollback is part of this release.

### 5. Promote And Close

1. After production retains the candidate and every R1 gate passes, create and
   push signed annotated tag `v2.22.0` at the exact candidate revision.
2. Require stable publication to promote the accepted digests without
   rebuilding and independently verify every stable image reference.
3. Publish the GitHub Release and merge one documentation-only evidence PR
   containing the sanitized candidate, rollout, acceptance, promotion,
   anomaly, and claim-boundary results.

## Failure Rules

- Stop on the first unexplained CI, artifact, health, authorization, route,
  queue, review, identity, receiver-mode, or continuity failure.
- Never retry an uncertain mutation, replace a published tag, rebuild an
  accepted image, expose the operations route publicly, or enable a delivery
  worker to make acceptance pass.
- Do not create or alter durable data or configuration to manufacture a chain
  state.
- Stop for a new decision if the runtime scope, risk class, secret identity,
  receiver mode, worker state, or rollback boundary changes.
