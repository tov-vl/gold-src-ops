# GoldSrcOps v2.9 Release Readiness

Review date: 2026-09-14. Status: released. Signed candidate publication,
digest-pinned production rollout, bounded read-only acceptance, digest-preserving
stable promotion, and published-image verification are complete.

## Scope

The v2.9 product scope is one Recent Operations Activity slice integrated in
protected `main` through pull request
[#137](https://github.com/tov-vl/gold-src-ops/pull/137):

- `GET /api/dashboard/activity?limit=` returns one bounded fleet timeline under
  the existing `Reader` policy.
- The accepted limit is 1 to 100, with a default of 50. Each source query
  materializes at most the effective limit before the final merge returns at
  most that limit.
- Incident and command records are merged in deterministic reverse chronology,
  with source type and source identifier providing stable tie breaking.
- The response contains event identity, server identity and name, category,
  state, and occurrence time only.
- `/operator/activity` renders static All, Incidents, and Commands views with
  links into existing incident investigation and command-history routes.
- Static rendering, responsive layouts, and the existing server-side token
  boundary remain in effect.

The candidate baseline also carries forward the v2.8 production-acceptance and
stable-publication records merged after the signed v2.8 application revision.
It includes the risk-based CI release-gate change from pull request
[#136](https://github.com/tov-vl/gold-src-ops/pull/136). That change affects
repository and publication tooling, not the production runtime contract.

This record freezes the release-candidate scope. Arbitrary activity time ranges,
pagination, export, realtime delivery, saved filters, incident mutation,
command submission, schema changes, worker changes, OIDC changes, and
infrastructure changes are not part of `v2.9.0-rc.1`.

## Claim Boundary

The target remains one single-node control plane, one Web instance, and one
controlled external game server. Candidate acceptance can show that an
authenticated Reader can inspect a bounded, sanitized timeline from retained
incident and command records in that reference deployment without disturbing
monitoring. It cannot prove complete audit retention, realtime delivery, high
availability, multi-region resilience, long-term reliability, user adoption,
or an achieved SLO.

Public documentation may contain revision identifiers, image digests, workflow
links, sanitized counts, and bounded outcomes. Host and provider identifiers,
addresses, credentials, secret aliases, operator identity, raw database rows,
tokens, incident reasons, command payloads, results, and failure details stay
outside Git.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.8.0..main` commit and file inventory.
3. Require `Change Scope`, `Quality Gate`, `Container Smoke`, and `Browser
   Smoke` on the documentation-only readiness revision. The required check names
   remain present while the verified docs fast path avoids rebuilding unchanged
   application artifacts.

### 2. Candidate Publication

1. Create signed annotated tag `v2.9.0-rc.1` at the reviewed `main` revision.
2. Require build-mode publication of both API and Web images from that exact
   revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

### 3. Digest-Pinned Rollout

1. Retain the current v2.8 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, container and
   game-service identities, restart counts, A2S state, incidents, queues, and
   scheduled-backup freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.

### 4. Short Production Smoke

Collect at least three healthy read-only samples spanning at least three minutes
and stop on the first unexplained failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image digests.
2. Verify anonymous routes remain sanitized and the activity API still requires
   authentication.
3. Through an existing authenticated Operator session, which includes Reader
   access, request bounded recent activity and require reverse-chronological
   ordering, accepted limit semantics, known source types, and only the
   minimized contract fields. Do not print identifiers or raw records in
   evidence.
4. Navigate to `/operator/activity` and verify All, Incidents, and Commands
   render, filter deterministically, link only to the existing authorized detail
   routes, and add no mutation control.
5. Confirm browser content and storage contain no bearer token, credential
   value, secret reference, incident reason, command payload, result, requester,
   or failure detail. If unchanged OIDC makes a fresh Reader-only login
   unnecessary, reuse Reader authorization and concealment evidence from
   Browser Smoke on the exact Web digest and record that substitution
   explicitly.
6. Require the controlled server to remain recently polled and reachable with
   zero bots. Require no unexpected container or game-service restart, newly
   opened incident, pending outbox item, dead letter, or incomplete command.
7. Recheck public health and scheduled-backup freshness in the final sample.

This short smoke is sufficient for the additive read-only API and Web change.
It requires no repeated interactive authorization once a valid session or
non-interactive evidence path is available. It is not a new soak, recovery
rehearsal, lifecycle acceptance, or SLO claim. Existing passive monitoring and
the independent `API-01` window continue without user participation.

## Acceptance Evidence

The candidate was deployed by exact API and Web digest. Only the two application
containers were recreated; PostgreSQL, Caddy, telemetry services, and the game
service retained their identities and restart counts. No migration or other
schema-changing operation ran.

Three healthy system samples were collected from
`2026-09-14T08:46:43.0853527Z` through
`2026-09-14T08:53:28.6956202Z`, a span of 405.61 seconds. Every sample returned
HTTP `200` for API liveness, API readiness, and Web health; reported a recent,
reachable A2S poll with zero bots; retained fresh scheduled-backup evidence; and
found zero open incidents, pending outbox messages, dead letters, and incomplete
commands. A final independent request from the game host returned HTTP `200` for
API liveness, API readiness, and the Web root.

The existing Operator session rendered six minimized activity events in reverse
chronology: two incidents and four commands. All, Incidents, and Commands views
returned the expected counts, links stayed within the existing authorized
detail routes, and the page exposed no form or mutation control. Browser content
and storage contained no bearer-like value or forbidden detail, and no console
warning or error was observed. Because OIDC and authorization were unchanged,
Reader-only concealment was reused from Browser Smoke on the exact immutable Web
image; this is not a claim of a fresh Reader login.

The game service remained active and boot-disabled. Its restart count,
invocation, and main process were unchanged, and exactly one configured UDP
listener remained owned by the service. Sanitized evidence is stored outside
Git in owner-only files. This bounded smoke is short operational evidence for
the additive release, not proof of long-term reliability, high availability, or
an achieved SLO.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On candidate startup, health, authorization, activity-contract, query,
  data-boundary, or rendering failure, recreate API and Web together from the
  retained v2.8 digests.
- Do not mutate PostgreSQL, monitoring state, RCON state, incident history,
  command history, snapshot history, or durable queues to make the smoke pass.
- A bad or missing availability minute remains bad. Do not pause, reset,
  backfill, or reinterpret `API-01`.
- Store sanitized smoke evidence outside Git as an owner-only regular file.
