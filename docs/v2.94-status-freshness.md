# v2.94 - Public status freshness

## Scope

R1, API read behavior only. A recent A2S observation from one server must not
hide another server's expired Online state in the public fleet summary.
The existing per-server freshness window is twice its polling interval plus
10 seconds, inclusive. Disabled servers remain excluded.

| Enabled observations | Summary |
| --- | --- |
| None, missing, or all expired | unknown |
| Some fresh, any stale/non-Online server or open incident | degraded |
| Every server fresh and Online, no open incidents | operational |

Only fresh Online observations count as online. Expired and missing observations
require attention but do not create Offline observations or incidents.
LastObservedAtUtc remains the most recent enabled observation, not proof that
every server was checked then. All rows use one application-clock reading.

The repository's internal summary projection now carries the configured poll
interval. Public JSON, enum values, authentication, output cache (15 seconds),
database schema, polling, incident transitions and gameplay remain unchanged.
The existing Web 180-second transport-age fallback remains conservative and
does not upgrade degraded/unknown API results. Operator historical summaries
and raw status detail remain outside this public-summary release.

## Verification plan

- Deterministic unit tests: mixed fresh/stale servers, exact boundaries for
  different intervals, missing observations, disabled servers, all expired
  stored states, expiry without new polls and recovery after a new observation.
- API integration: anonymous sanitized JSON and a fresh server masking an old
  Online server, exercising the persistence projection.
- Web RU/EN: fresh aggregate timestamp preserves degraded/unknown API states.
- Focused .NET tests, repository quality gates and scoped InspectCode.
- Required PR CI, signed candidate publication, independent image checks.
- Digest-pinned API-only rollout and at least three read-only samples spanning
  three minutes; verify health, public status, unchanged dependencies and queues.
- Stable promotion without rebuild and final evidence PR.

### Target acceptance

Only the API was recreated using its verified digest. Target OCI revision,
version, source and license matched publication. Before rollout, the previous
API was healthy, the scheduled backup was fresh and no command was Pending or
Running. Only the API image setting changed; volumes and other services were
preserved. Three successful read-only samples spanned 196 seconds on
2026-10-28. Each confirmed:

- API liveness/readiness, anonymous status and public Web RU/EN returned 200;
  the protected server endpoint retained 401 and the receiver rejected an
  unsupported GET with 404.
- Public status was operational: one monitored server, one fresh Online
  observation, zero servers requiring attention and zero open incidents.
- A2S remained reachable and fresh; Pending/Running commands remained zero.
- API and collector Prometheus targets were up; delivery gates remained disabled
  and the receiver remained in CatchUp mode.
- All nine containers were running, health checks passed and mounts were
  preserved. The other eight container identities and restart counts did not
  change. The recovered static network assignments remained intact.

Rollback was not needed. Missing/stale/mixed-state negative cases were tested
deterministically in the repository; production observations were not modified
to manufacture those states. Interactive Reader/Operator login, gameplay,
long-term availability and a 24-hour activity window were not exercised by this
R1 read-only acceptance. No such claim is made.
