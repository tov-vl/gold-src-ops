# GoldSrcOps v2.3 Controlled Game-Server Baseline

## Status

This document starts v2.3 Slice 2 by defining the provider-independent
selection, provisioning, network, recovery, and evidence contract for one
controlled Counter-Strike 1.6 server. A self-operated MyArena game VDS is the
conditional target selected in
`docs/v2.3-gameserver-provider-decision.md`. No paid service has been purchased,
and no external server or endpoint is claimed to exist yet. A disposable local
target-runtime rehearsal completed on 2026-08-29; it is compatibility evidence,
not external Slice 2 evidence.

The first baseline deliberately excludes YaPB and other synthetic players. A
stable no-bot environment must be observed before controlled load is added.

## Goal

Operate one project-owned ReHLDS and ReGameDLL_CS server outside the
GoldSrcOps control-plane host, then verify the existing A2S polling and guarded
RCON workflows across a real UDP network boundary.

This slice proves the protocol and operational boundary. It does not add a
hosting-provider adapter or make GoldSrcOps responsible for billing,
provisioning, file management, or process lifecycle APIs.

## Entry Conditions

- The operator owns or administers the selected game server.
- The provider permits the pinned engine and GameDLL versions, guarded RCON,
  backups, and later synthetic bot load.
- The environment exposes a stable IPv4 A2S endpoint.
- RCON can be reached through a private tunnel or restricted to an explicitly
  approved control-plane source address.
- Server and provider credentials remain outside Git, image layers, command
  history, logs, screenshots, and public evidence.

If the host cannot restrict RCON to an approved source, A2S-only exploration
may continue, but Slice 2 cannot be declared complete.

## Provider Selection Gate

The managed-hosting or self-operated target is acceptable only when all of the
following are available:

- explicit control over the ReHLDS and ReGameDLL_CS binaries;
- a stable IPv4 address or DNS name and a known UDP game/query port;
- a fixed or controllable source boundary for RCON;
- process stop, start, restart, and status operations;
- configuration and log access without exposing the RCON password in routine
  output;
- exportable configuration backups or a provider-native backup with a tested
  restore path;
- a documented policy for platform updates so pinned files are not overwritten
  without notice;
- enough ownership to run a later YaPB experiment without misrepresenting bots
  as real users.

Reject a target that requires a proprietary application integration, prevents
artifact verification, exposes unrestricted RCON, or cannot restore its
configuration independently of the live instance.

The provider name, region, price, account identifiers, and management endpoint
are deployment records, not application configuration. Only sanitized,
portfolio-relevant details belong in public repository evidence.

The first comparison selects a MyArena KVM game VDS conditionally, with Timeweb
Cloud as the fallback. The selection remains blocked on the purchase-time
checks in `docs/v2.3-gameserver-provider-decision.md`; it is not deployment
evidence.

## Network Contract

| Source | Destination | Purpose | Required control |
| --- | --- | --- | --- |
| Public clients and approved probes | Game-server UDP endpoint | Gameplay and `A2S_INFO` | Public only when intentionally operated as a public server; otherwise allowlisted for the baseline |
| Approved baseline probe or control-plane source | Game-server UDP endpoint | RCON challenge, command, and response | Private tunnel preferred; otherwise exact source-IP restriction and accepted plaintext-UDP risk |
| Operator workstation | Provider management plane or host SSH | Provisioning, restart, backup, and recovery | Provider MFA or SSH keys; never exposed through GoldSrcOps |
| Game-server host | External update sources | Initial installation or an approved update window | Deny unnecessary outbound access after provisioning when the platform permits it |

GoldSrc normally carries gameplay, A2S, and RCON through the same UDP server
endpoint. A port firewall therefore may not distinguish a public A2S request
from an RCON packet. When a private tunnel is unavailable, combine the provider
firewall where useful with the ReHLDS RCON source allowlist and one approved
control-plane egress address. Before the Slice 3 VPS exists, a temporary
operator-controlled source may be approved for the baseline and revoked after
verification. Final production evidence must repeat the check from the VPS.
Do not compensate for a failed smoke test by opening RCON to the Internet.

ReHLDS provides `rcon_adduser <ipaddress/CIDR>`, `rcon_deluser`, and
`rcon_users` for this application-layer restriction, as documented in the
[`3.15.0.896` README](https://github.com/rehlds/ReHLDS/blob/3.15.0.896/README.md).
An empty RCON user list allows any source that knows the password; it is not a
deny-all state. Configure the approved IPv4 source as an exact `/32`, verify a
non-empty list with `rcon_users`, and repeat that verification after every
restart. If the provider startup path does not persist the allowlist safely,
Slice 2 remains incomplete.

The residual RCON boundary is explicit: its password and command traffic are
not transport-encrypted by the legacy protocol. Source restriction reduces
exposure but does not provide confidentiality or cryptographic peer identity.

## Configuration And Secrets

Tracked evidence may contain:

- component versions, release URLs, hashes, and signature-verification result;
- sanitized configuration names and a configuration diff with secret values
  removed;
- intended A2S visibility, port numbers, source-restriction method, and backup
  ownership;
- GoldSrcOps server id, command id, terminal status, snapshot times, and
  incident ids;
- restart and restore timings without provider account identifiers.

The following must remain in the selected secret boundary:

- RCON password;
- provider credentials, recovery codes, and account identifiers;
- SSH and tunnel private keys;
- non-public management endpoints;
- GoldSrcOps bearer tokens and secret-provider values.

Generate a high-entropy RCON password compatible with the existing client,
which rejects double quotes. Store the value on the server and under the
dedicated `RconSecrets:<alias>` application setting only. PostgreSQL retains
the canonical `rcon-secret://<alias>` reference, never the password.

## Provisioning Sequence

1. Select a target against the provider gate and record any accepted residual
   risk before purchase or provisioning.
2. Apply the reviewed, plan-first
   [`ops/gameserver` host bootstrap](../ops/gameserver/README.md), reboot when
   required, and reverify key-only operator access plus the allowlisted
   firewall boundary.
3. Create a minimal Counter-Strike 1.6 dedicated server with ReHLDS and
   ReGameDLL_CS only. Do not install YaPB, AMX Mod X, ReAPI, gameplay plugins,
   or custom content during the baseline.
4. Capture a recoverable pre-change snapshot or export before replacing any
   provider-supplied runtime files.
5. Install the verified candidate artifacts and record the exact runtime
   versions reported by the server.
6. Configure the server identity, one known map, logging bounds, RCON secret,
   and source restriction. Keep the secret out of shell history and evidence.
7. Apply the network controls and verify from an unapproved source, when a safe
   test source is available, that RCON access is not accepted.
8. Start the server and freeze the sanitized baseline configuration.
9. Verify A2S from an independently routed probe outside the game-server host.
   Repeat the same check from the final control-plane VPS after Slice 3.
10. Register the endpoint in a local GoldSrcOps instance, observe scheduled
   polling, and run exactly one guarded `say` command.
11. Exercise the documented stop/start and configuration-restore procedure,
    then repeat the A2S check.
12. Observe a continuous 24-hour no-bot baseline before considering YaPB.

The stop/start rehearsal is an intentional operation. It must have a rollback
path and should not be combined with an engine upgrade or another configuration
change.

## External A2S Verification

Run the protocol diagnostic from a non-loopback source outside the game-server
host, replacing the placeholder with the reviewed endpoint:

```powershell
dotnet run --project .\src\GoldSrcOps.A2SSpike -- `
  <game-server-host>:<query-port> `
  --timeout 5000 `
  --encoding windows-1251
```

Record the resolved endpoint, sanitized server name, map, engine response,
player count, bot count, protocol, version, and latency. The first no-bot
baseline requires the A2S bot count to remain zero. Player counts observed
during operator testing are test traffic, not adoption evidence.

If the final VPS does not exist yet, this is provisional external-path
evidence. Slice 3 or the final environment gate must repeat it from the actual
control-plane source address.

Next, follow `docs/smoke-test.md` to register the same endpoint in a local
GoldSrcOps instance. Evidence must show repeated scheduled snapshots rather
than only one successful diagnostic request.

## Guarded RCON Verification

For Slice 2, keep the GoldSrcOps API on loopback and let only its UDP target be
remote. This preserves the JWT protection in `tools/smoke/rcon-live.ps1`, which
refuses to transmit bearer tokens to a non-loopback API.

Run the authenticated preflight first:

```powershell
.\tools\smoke\rcon-live.ps1 `
  -ServerId "<registered-server-id>" `
  -AcknowledgeOwnedServer `
  -WhatIf
```

After checking the displayed name, endpoint, and generated command, run the
same helper without `-WhatIf`. Type the server id again when prompted. Record
only the returned command id, server id, terminal status, elapsed time, and the
persisted audit identity.

Do not retry after a timeout until the persisted command record is inspected.
GoldSrc RCON has no idempotency key, so an ambiguous timeout can follow a
successful remote execution.

## Baseline Acceptance

Slice 2 is complete only when evidence demonstrates all of the following:

- exact ReHLDS, ReGameDLL_CS, and base server builds plus verified release
  artifacts;
- a documented provider or host ownership boundary and recoverable sanitized
  configuration;
- external A2S success followed by repeated GoldSrcOps polling over the same
  non-loopback network path;
- one guarded `say` command with a persisted Operator identity and `Succeeded`
  terminal status;
- RCON restricted to the approved path, with any lack of transport
  confidentiality explicitly accepted, and a non-empty ReHLDS RCON user list
  verified again after restart;
- a successful controlled stop/start and configuration restore;
- a 24-hour no-bot observation with no unexplained outage at the end and A2S
  bot count remaining zero;
- no provider credential, RCON password, bearer token, private key, or private
  management endpoint in Git, logs, screenshots, or public telemetry.

YaPB remains blocked until this acceptance set is complete. Its later evidence
must report bot and total player counts separately.

The 24-hour interval is a bounded configuration-stability gate, not a claimed
availability SLO or the longer deployment soak required by the v2.3 release
gate.

## Stop Conditions

- Stop before RCON if source restriction or a private path cannot be proved.
- Stop before installation if a release hash or detached signature fails.
- Stop and rotate credentials if a secret appears in output or evidence.
- Stop provider evaluation if pinned runtime files are replaced automatically
  without a controllable update policy.
- Stop command testing after an ambiguous timeout; inspect durable state before
  deciding on any manual retry.
- Stop the baseline clock after an unexplained restart, version drift, bot
  appearance, or configuration change. Resolve and restart the observation.
