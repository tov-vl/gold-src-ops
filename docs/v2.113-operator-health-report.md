# v2.113 - Downloadable Operator health report

## Scope and compatibility

Add an Operator-only text attachment at `/operator/game-host-health/report`,
linked from the existing health page. Download reads a new snapshot through the
existing server-side BFF client; it can differ from the already displayed page.
The response is UTF-8 plain text with a fixed download filename, no-store and
nosniff. It requires no JavaScript and stores no report file on the server.

The report contains generation/evaluation times, observation ages, five fixed
component cards, known measurements and active warning names/states with the
existing static first checks, preservation notes and guide links. Missing or
invalid values are Unknown; zero remains valid. Freshness uses the existing
API boundaries: 180 seconds for observations and 60 seconds for rule evaluation.
Unknown, Stale and a fresh empty warning snapshot remain distinct. Future times,
duplicate entries and unknown warning names cannot establish a healthy state.

Projection is bounded to the five cards, 28 measurement slots and 17 warning
names. Only fixed labels, finite nonnegative numbers and timestamps are written;
provider descriptions, error text, unrecognized fields, host addresses and
credentials are not reflected. Failed reads produce an explicit Unknown report;
caller cancellation propagates without an automatic retry.

This is R1, Web only. Existing OperatorPolicy, API/contracts, accepted v2.111 API,
warning catalog, collection, database, game/agent, notification delivery and
provider/access configuration are unchanged. No new permissions or credentials.
Rollback replaces Web with its accepted v2.112 immutable digest; no durable
state or report archive needs migration or recovery.

## Required gates and status

Implementation and local verification are complete; publication and production
acceptance remain pending. Required evidence includes:

- Operator/Reader/anonymous authorization before any health read; no-store
  attachment headers and fixed filename, including trailing-slash routing.
- Fresh, missing, duplicate, stale/future, malformed and unavailable data;
  numeric zero/nonfinite values, bounded output and no raw-text reflection.
- Cancellation propagation, one upstream read per download and no server store.
- Authenticated no-JavaScript Chromium download, token-free body and responsive
  health page with the existing refresh/unknown/stale behavior preserved.
- Complete local quality gate, scoped pinned InspectCode and required PR/tag CI.
- Signed candidate, independent image identity checks, Web-only exact-digest
  rollout and runtime/Operator download acceptance, followed by same-digest
  stable promotion and final evidence publication.

No live fault injection, Steam session, multiplayer or activity window is
required. Fixture coverage of fault states must remain separate from ordinary
production read-only acceptance.

Local restore with audit, solution formatting/build and dependency audit passed.
Project test totals are 857 Unit/API, 523 Web and 54 receiver; the ordinary Web
run skips the existing 63 opt-in browser cases. A final focused run passed all
35 report/page and no-JavaScript Chromium cases, including the actual attachment
and token-free body. Desktop output was visually reviewed and the existing
390-pixel no-overflow/refresh/unknown/stale checks passed.

The initial combined test run recorded one timeout in an untouched UDP/RCON
datagram-limit test. All 12 RCON cases passed in isolation and the complete
857-case Unit/API project subsequently passed without a code or timeout-policy
change. The original failure is retained; its exact timing cause is unproven.

Pinned InspectCode 2026.2.3.1 checked changed C#/Razor files at Hint and above.
Product code has no errors or warnings after fixes. Existing host/if-chain and
initializer-style notes are reviewed exceptions. The cancellation completion
assertion deliberately uses its own deadline after the request token is already
cancelled. No analysis severity or project policy was changed.

An independent check matched all five component keys, 16 metric keys and the
existing 180/60-second freshness boundaries to the API implementation. The report
uses 28 fixed measurement slots and excludes provider descriptions. Read-only
production preflight and an in-memory Compose plan passed for a Web-only image
change; no production write has been performed at this stage.
