# v2.96 - Passive game-event agent monitoring

## Frozen scope

R3, operations-only release. The existing v2.95 agent executable, game process,
SQLite schema, queue contents, credentials and application images are preserved.
The new host timer observes aggregate diagnostics through the existing private
telemetry pipeline once per minute. It does not create events, initialize a queue,
recover leases, import files, retry deliveries, restart workers or send alerts.

The existing restricted backup SSH dispatcher gains exactly one command:
`agent-status`, without arguments. It invokes a fixed root-owned helper, verifies
the installed persistent guard and executes the installed `status --json` as the
game service user. Existing `capture`, `status` and `bundle` behavior remains.
No account, key, sudoers rule, firewall or public endpoint is added. This command
nevertheless expands the key's read capability and requires the owner's explicit
permission before production installation.

The helper projects a bounded schema-1 envelope. It excludes source identifiers,
sequence numbers, event payloads, player names, private addresses and credentials.
Only aggregate counts, observation time, service state and import/delivery cycle
facts cross SSH. Invalid, oversized, inconsistent or unreadable state fails closed.
The status process receives a secret file reference but does not read its contents.

## Metrics and freshness

The fixed resource is `goldsrcops-game-event-agent-monitor`; the metric prefix is
`goldsrcops_game_event_agent_`. Only loop metrics have a label, bounded to `import`
and `delivery`. There is no source, event or player label.

| Signal | Meaning |
| --- | --- |
| `observation_success`, `observed_timestamp_seconds` | Collector pass and its wall-clock timestamp, including failed observations |
| `source_observed_timestamp_seconds`, `service_active` | Valid host observation time and current agent unit state |
| `queue_capacity`, `queue_pending`, `queue_in_flight`, `queue_dead_letter` | Existing queue aggregates; dead letters are separate from waiting work |
| `spool_available`, `spool_ready`, `spool_processing`, `spool_rejected` | Spool accessibility and bounded directory counts |
| `oldest_waiting_age_seconds` | Oldest pending/in-flight enqueue, including backoff; zero when no work waits |
| `loop_state`, `loop_stale_after_seconds` | Recomputed cycle state and its configured diagnostic allowance |
| `loop_last_completed_timestamp_seconds`, `loop_last_success_timestamp_seconds` | Completed and error-free passes, including idle passes; zero means never observed |

Loop values are disabled 0, unavailable 1, starting 2, running 3, stale 4, failed 5,
retrying 6, blocked 7 and stopped 8. Idle success proves that a loop advances; it
does not prove delivery of an HTTP event. An inactive service reports stopped.
The monitor recomputes expiry using cycle timestamps and preserves the inclusive
v2.95 stale budget. A host snapshot older than 30 seconds or more than five seconds
in the future is refused by the collector.

Dashboard `goldsrcops-game-event-agent` uses instant queries for current facts.
Every fact requires a successful observation and collector/source timestamps
between zero and 180 seconds old. Retained exporter series cannot keep current
counts healthy after transport failure, a frozen observer or future-dated source
time. The observation badge becomes unavailable; dependent current facts become
no-data. History retains past valid values with gaps. Waiting age advances between
samples only while pending/in-flight work exists. Missing success timestamps are
not displayed as an event delivery claim.
An unreadable spool preserves valid queue facts but emits no directory counts;
spool panels also require `spool_available=1` to mask retained exporter values.

## Installation and rollback boundary

Build a clean accepted revision with
`tools/release/build-agent-monitor.ps1 -Version 2.96.0 -OutputDirectory <operator-directory>`.
The immutable ZIP contains nine explicitly listed files plus a manifest with
revision, length, mode and SHA-256 for each payload. Existing outputs are refused.
Candidate `agent-monitor-v2.96.0-rc.1` and stable `agent-monitor-v2.96.0` are signed
annotated tags. This is a separate operations package; it does not rebuild the
agent, addon or API/Web/receiver images or change the global latest release.

Before rollout, freeze the old dispatcher hash and metadata, existing SSH/sudoers
identity, installed agent identity, queue/source continuity, unit process IDs and
existing container image/instance identities in the private operator record.
Require the new roots, unit/config paths and dashboard UID to be absent. Stage
and verify every manifest file before exposing the new command. Game-host files
are root-owned under `/opt/goldsrcops-agent-observation`; control-plane files are
under `/opt/goldsrcops-agent-monitor`. Only the dispatcher is replaced in place,
using an atomic same-directory rename after preserving its exact prior bytes.

The new root-owned config derives the numeric private Collector address from the
already installed monitor configuration. It does not accept a public endpoint,
proxy, DNS override, alternate SSH destination or arbitrary command. The new
oneshot service has a 40-second deadline, no restart policy, read-only filesystem,
no capabilities and no access to Docker or application secrets. Its SSH call has
one connection attempt and a bounded process-group cleanup. No existing service
or container needs to be restarted.

The new dashboard is API-managed because the existing provisioned dashboard
provider disables deletion. Its helper resolves the pinned existing private
Grafana container, consumes the existing protected password only in memory,
requires the new UID to be absent and submits one `overwrite=false` request into
the existing operations folder. A durable pending claim precedes the request;
uncertain outcomes require read-only reconciliation, never automatic retry.
An accepted receipt fixes the returned dashboard fingerprint and version.

Rollback stops/disables only the new timer/service, then uses
`agent-monitor-dashboard.py rollback --dashboard-sha256 <accepted-source-hash>`
to remove only the new API-managed UID if its accepted body/version still match.
Restore the preserved dispatcher only if the installed new hash still matches.
Remove only this release's new files/config/units after exact hash/metadata checks;
preserve the operator claim and rollback evidence. Refuse drift instead of
overwriting it. No queue, spool, database, key, network, old dashboard or provider
configuration is restored or deleted by this rollback.

## Verification and remaining gates

Focused tests exercise passive capture, privacy, malformed/future/old observations,
idle/backlog/stuck/failed/retrying/blocked/stopped states and command restrictions.
Disposable root fixtures cover dashboard installation, exact rollback, lost-response
claims, pre-existing/provisioned resources and operator edits. The pinned local
Collector/Prometheus/Grafana rehearsal tests all production expressions, distinct
queue/spool values, failed observations retaining raw exporter gauges, frozen/future
timestamps, recovery and an API dashboard lifecycle. Existing dashboards and rules
are checked in the same isolated stack.

Local Linux verification passed 12 observation/privacy/metric tests, six
disposable dashboard claim/rollback tests and the extended backup dispatcher
rehearsal. The complete pinned telemetry rehearsal passed agent idle, backlog,
stale/stopped/unavailable, clock and recovery scenarios. Existing backup,
leaderboard and Web rule scenarios (21/25/30 respectively) and their dashboard
rehearsals also passed. Both new systemd units passed syntax/dependency validation.
The PowerShell package builder passed parser validation and built a clean-branch
rehearsal ZIP. Eight disposable real-file host cases exercised success, partial
installation, bad hashes and operator drift for both roles with unchanged queue
bytes and exact rollback. Accepted-source packaging remains a separate gate.

No C# source changed, so local .NET and InspectCode were not repeated. Full
required product CI remains mandatory. An initial Windows stack attempt lacked
the Python time-zone database; a process-local standard zoneinfo path allowed the
unchanged stack to pass. No application globalization or host package setting was
changed to obtain that result.

Read-only target preparation confirmed the existing Grafana password file uses a
final line terminator. The helper now follows the container's password-file
convention while rejecting embedded/multiple lines; a regression covers LF, CRLF
and unformatted files. No credential file or Grafana setting was changed.

Required product and post-merge CI, immutable candidate publication, explicit
permission for the new restricted command, production installation and independent
target acceptance remain separate gates until their exact results are recorded.
Target checks require two advancing idle observations, actual Prometheus facts,
the exact Grafana dashboard, unchanged game/agent/container identities and queue
continuity. No real player, Steam session, owner notification or 24-hour activity
observation is needed or claimed by this release.
