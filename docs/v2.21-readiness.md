# GoldSrcOps v2.21 Release Readiness

Review date: 2026-09-21. Status: candidate preparation. The Provider Delivery
Overview product revision is integrated into protected `main`. Candidate
publication, target rollout, production acceptance, stable promotion, and
release closure remain pending.

## Scope

The v2.21 release scope is Provider Delivery Overview:

- one separately authorized internal receiver status endpoint;
- provider-worker configuration, pending, processing, dead-letter, and
  unreviewed-dead-letter counts;
- oldest-pending and observation timestamps;
- a server-side Web client that keeps receiver authorization outside browser
  code;
- an Operator-only `/operator/provider-delivery` overview with clear, active,
  paused-with-work, and action-required states;
- a link to the existing immutable provider dead-letter review workflow.

The overview is read-only. It cannot retry, replay, delete, reclassify,
unblock, review, or enable provider work.

## Claim Boundary

Candidate acceptance can show that the exact Web and AlertReceiver artifacts
return the naturally existing provider-outbox snapshot to an authenticated
Operator, render only the reviewed aggregate fields, preserve the separate
operations authorization inside the server-side boundary, and leave provider
and source alert delivery disabled. It can also show public health, exact image
identity, unchanged queue/review state, and continuity of unaffected runtime.

Acceptance cannot prove notification delivery, escalation, provider-worker
liveness, throughput, retry correctness under failure, sustained operation,
high availability, long-term reliability, or an achieved SLO. It must not
create or mutate queue rows, reviews, incidents, or provider state to
manufacture an overview state.

## Compatibility Review

- Neither the control-plane nor receiver database has a v2.21 migration,
  model change, backfill, or data correction.
- Existing provider-outbox and append-only review rows are read without
  mutation. The existing statistics and review queries remain bounded by the
  current schema and indexes.
- The receiver endpoint reuses the separate v2.20 provider-operations
  authorization. No new secret, role, identity-provider change, or public
  Caddy route is introduced.
- The v2.21 Web can temporarily show an unavailable state against a v2.20
  receiver. Replace AlertReceiver before Web to avoid that mixed-version
  interval; no queue mutation is possible in either order.
- The v2.20 Web ignores the new receiver endpoint, so receiver-first rollout is
  backward compatible.
- Rollback restores the accepted v2.20 Web and AlertReceiver digests without a
  database action and without changing operations authorization or either
  delivery-worker setting.

## Ordered Candidate Plan

### 1. Merge Readiness And Freeze

1. Merge this documentation-only readiness record through protected `main`
   after its required checks pass.
2. Record the exact readiness merge SHA and require product post-merge workflow
   `#35616058235` to be green.
3. Confirm `v2.21.0-rc.1` and `v2.21.0` remain unused and compare the final
   inventory with signed stable `v2.20.0`.
4. Retain the accepted v2.20 Web and AlertReceiver digests, owner-only
   environments, authorization file, and rollback commands outside Git.

### 2. Publish And Verify The Candidate

1. Create, locally verify, and push signed annotated tag `v2.21.0-rc.1` at the
   exact reviewed `main` revision.
2. Require `Quality Gate`, `Container Smoke`, and `Browser Smoke`, followed by
   publication and independent digest verification for every workflow image.
3. Verify OCI source, revision, version, license, and immutable Web and
   AlertReceiver digests before preparing a target mutation.
4. Stop before rollout if artifact identity differs from the frozen revision.

### 3. Capture Baseline And Roll Out

1. Capture sanitized API, Web, receiver, queue, review, incident, backup, A2S,
   game-service, image, and restart baselines. Keep topology and raw rows
   owner-only.
2. Do not run a backup/restore rehearsal, migration action, game-host action,
   queue drain, or provider operation for this R1 release.
3. Replace AlertReceiver and then Web with their independently verified
   candidate digests. Recreate no other component.
4. Keep the existing operations authorization unchanged and keep
   `AlertDelivery__Enabled=false`, `ProviderDelivery__Enabled=false`, and the
   receiver mode unchanged.

### 4. Accept Or Roll Back

1. Collect at least three healthy read-only samples spanning at least three
   minutes for public API/Web health, receiver health, exact candidate identity,
   restart counts, and dependent runtime continuity.
2. Through an existing Operator session, verify the overview matches bounded
   owner-only queue evidence and exposes no credential, payload, raw provider
   response, or mutation control. Confirm Reader access remains forbidden and
   the provider-operations route remains absent from public Caddy.
3. Confirm pending, processing, dead-letter, and review state did not change as
   a side effect of observation; both delivery workers remain disabled.
4. On failure, restore only Web and AlertReceiver to the recorded v2.20
   digests. No database, authorization, queue, review, API, Caddy, telemetry,
   identity, or game-host rollback is part of this release.

### 5. Promote And Close

1. After production retains the candidate and every R1 gate passes, create and
   push signed annotated tag `v2.21.0` at the exact candidate revision.
2. Require stable publication to promote the accepted digests without
   rebuilding and independently verify every stable image reference.
3. Publish the GitHub Release and merge one documentation-only evidence PR
   containing the sanitized candidate, rollout, acceptance, promotion, anomaly,
   and claim-boundary results.

## Failure Rules

- Stop on the first unexplained CI, artifact, health, authorization, route,
  queue, review, identity, or continuity failure.
- Never retry an uncertain mutation, replace a published tag, rebuild an
  accepted image, expose the operations route publicly, or enable a delivery
  worker to make acceptance pass.
- Do not create or alter durable data to manufacture overview evidence.
- Stop for a new decision if the runtime scope, risk class, secret identity,
  worker state, or rollback boundary changes.
