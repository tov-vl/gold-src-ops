# GoldSrcOps v2.16 Release Readiness

Review date: 2026-09-17. Status: stable release published; candidate acceptance
and digest-preserving publication are complete.

## Scope

The v2.16 product scope is the Bounded Activity Pagination slice integrated in
protected `main` through pull request
[#173](https://github.com/tov-vl/gold-src-ops/pull/173):

- `GET /api/dashboard/activity` accepts an optional opaque `cursor` and returns
  nullable `previousCursor` and `nextCursor` values with the existing bounded
  items.
- Every cursor fixes the UTC upper query boundary and is bound to the requested
  limit, controlled server, event type, and activity window.
- Malformed, non-canonical, unsupported, out-of-range, and cross-scope cursors
  return a validation problem instead of broadening the query.
- Each source query materializes at most `offset + limit + 1` rows. The public
  limit remains capped at 100 and the cursor offset is capped at 500.
- The cross-source result keeps deterministic reverse-chronological ordering.
- The static-rendered Reader page exposes `Newer` and `Older` navigation,
  preserves server, event type, and range while paging, and resets to the
  newest page when any of those filters changes.
- Focused cursor, service, API, repository, Reader client, static-rendering,
  responsive Chromium, and browser token-boundary coverage protects the
  bounded contract.

The slice adds nullable response fields but no schema migration,
authorization-policy change, background worker, production identity, mutation
permission, event producer, delivery activation, or game-host artifact.

This record freezes the release-candidate scope. Arbitrary date ranges,
unbounded history, cursor persistence, saved filters, activity export, alert
delivery, gameplay-detail expansion, schema change, infrastructure change, or
another UI slice is not part of `v2.16.0-rc.1` acceptance.

## Claim Boundary

Candidate acceptance can show that an authenticated Reader can move through a
bounded activity result while preserving the fixed upper time boundary and the
selected server, source, and range, then return toward the newest page without
exposing additional item fields or mutating production state. It cannot prove
complete history, retention completeness, snapshot isolation against
late-arriving historical rows, long-term cursor durability, high availability,
multi-region resilience, user adoption, or an achieved SLO.

Public documentation may contain revision identifiers, image digests,
workflow links, sanitized counts, durations, and pass/fail results. Host and
provider identifiers, addresses, credentials, secret paths or aliases,
operator identity, raw database rows, tokens, cursor samples from production,
source identities, event identifiers, and RCON content stay outside Git.

## Compatibility And Reduced Gate

- Existing API clients may omit `cursor` and receive the same bounded newest
  page as before.
- The response adds only nullable cursor fields. Tolerant clients may ignore
  them; the existing activity item shape is unchanged.
- Cursor version, shape, range, canonical encoding, and exact request scope are
  validated before the page position is accepted.
- The cursor is routing state, not a bearer token, authorization grant,
  integrity proof, or durable bookmark. The Reader policy is applied to every
  request.
- The fixed upper query boundary stabilizes the active time window against new
  current events, but a late-arriving historical row can still affect offset
  pagination.
- Changing server, event type, range, or limit invalidates the prior cursor and
  starts a new newest-page investigation.
- API and Web must be published and deployed together because the Web client
  consumes and returns the new cursor fields.
- No EF Core migration or persistence change exists. A fresh backup, restore
  rehearsal, migration timing exercise, and previous-runtime schema rehearsal
  are therefore not v2.16 gates.
- No game-host artifact changed. Plugin activation, gameplay capture, RCON
  action, or a game-service soak would not add release-relevant evidence.
- Pull request #173 exercised the complete application, container, and browser
  suites. This readiness pull request uses the fail-closed documentation-only
  fast path; the candidate tag still runs the complete release workflow against
  the exact source revision.

## Candidate Acceptance Result

The candidate was deployed by exact API and Web digest without a migration and
without recreating PostgreSQL, Caddy, telemetry, or the game service. Four
read-only samples over 182 seconds retained public API and Web health, exact
candidate identity, A2S reachability, zero bots, zero open or newly opened
incidents, zero dead letters, zero incomplete commands, fresh scheduled-backup
evidence, and zero container restarts. The game service remained active,
boot-disabled, restart-free, and the sole owner of one configured UDP listener.
The two reviewed deferred alert-outbox records remained unchanged while
delivery stayed disabled.

An existing authenticated Reader session rendered six natural events in the
`7d` window. Because the data did not exceed the fixed 50-item Reader page, the
UI correctly exposed no `Older` or `Newer` control. No operational event was
manufactured to force pagination. A bounded API page cycle accepted a canonical
cursor, rejected malformed and mismatched-scope cursors, and confirmed that
event type, range, and server changes reset to the newest page.

Published-image Browser Smoke passed the token-boundary contract. The browser
automation sandbox could not directly inspect production browser storage, so
this acceptance does not independently claim its contents. The rendered page
exposed no mutation control or server address. All owner-only evidence files
remained regular `root:root` files with mode `0600`. No rollback or unexplained
release transition occurred. This short acceptance is bounded release evidence,
not proof of long-term reliability or an achieved SLO.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.15.0..main` commit and file inventory and record the
   reviewed candidate revision.
3. Require `Change Scope`, `Quality Gate`, `Container Smoke`, and `Browser
   Smoke` on the documentation-only readiness revision. The required check
   names remain present while the docs fast path avoids rebuilding unchanged
   application artifacts.

### 2. Candidate Publication

1. Create signed annotated tag `v2.16.0-rc.1` at the reviewed `main` revision.
2. Require the complete tag workflow to build and publish both API and Web
   images from that exact revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

The tag workflow is the one intentional full validation pass after repository
closure. It requires no interactive production authorization while it builds
and verifies the images.

### 3. Digest-Pinned Rollout

1. Retain the current v2.15 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, application
   container identities and restart counts, A2S state, incidents, durable
   queues, incomplete commands, and scheduled-backup freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.
5. Do not provision an identity, activate the game-event agent, install a
   plugin, start a producer or delivery path, or manufacture gameplay data.

### 4. Short Production Smoke

Collect at least three healthy read-only samples spanning at least three
minutes and stop on the first unexplained failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image
   digests.
2. Require no unexpected API or Web restart and preserve the baseline for all
   untouched containers and the game service.
3. Require the controlled server to remain recently polled and A2S-reachable
   with zero bots. Require no newly opened incident, pending-outbox growth,
   dead letter, or incomplete command. Do not drain reviewed deferred work to
   make the smoke pass.
4. Through an existing authenticated Reader-capable session, open Recent
   Activity with the production-default scope and confirm the newest page and
   absence of any mutation control or newly exposed activity detail.
5. Exercise a bounded API page cycle with a small limit against naturally
   existing data: retain the returned next cursor, request the older page with
   the same server, source, range, and limit, then use the previous cursor to
   move toward the newest page. Do not record cursor values or event identities.
6. Require the page cycle to retain the fixed upper time boundary, deterministic
   ordering, bounded item count, and selected scope. Verify that malformed and
   mismatched-scope cursors fail validation instead of broadening the result.
7. If the naturally retained data exposes UI pagination, follow `Older` and
   `Newer` and verify scope-preserving URLs. If it does not, record that bounded
   data precluded the control and rely on the exact-image Browser Smoke rather
   than manufacturing events.
8. Change event type, range, and server scope and confirm each change returns
   to the newest page. Confirm browser storage contains no bearer token,
   credential, secret reference, raw database row, address, or unauthorized
   mutation control.
9. Recheck public health and scheduled-backup freshness in the final sample.

This smoke does not repeat a game-host continuity interval, soak, backup or
restore rehearsal, migration rehearsal, alert-outbox investigation, Auth0
reconfiguration, or gameplay-delivery exercise. Existing passive monitoring
continues independently.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On startup, health, authorization, cursor validation, pagination ordering,
  scope preservation, navigation, or rendering failure, recreate API and Web
  together from the retained v2.15 digests.
- Do not mutate PostgreSQL, monitoring state, game-event state, RCON state,
  incident history, command history, or durable queues to make the smoke pass.
- Store sanitized production evidence outside Git as an owner-only regular
  file.
