# GoldSrcOps v2.10 Release Readiness

Review date: 2026-09-14. Status: release-candidate preparation. The five
game-event repository slices are integrated, while candidate publication,
recovery rehearsal, production migration, and bounded acceptance remain
pending.

## Scope

The v2.10 repository scope is integrated in protected `main` through pull
requests #140 through #144:

- a versioned, server-bound machine ingress for one anonymous
  `round.ended` event;
- one additive PostgreSQL inbox with idempotency, sequence-conflict detection,
  bounded retention, and low-cardinality metrics;
- a sandbox companion Worker with a bounded SQLite outbox, leased exact-byte
  delivery, bounded retry, and terminal dead letters;
- a strict file-spool IPC with crash reconciliation and bounded directory
  states;
- a default-off AMX Mod X/ReAPI sample producer covered by a pinned compiler
  smoke and strict importer fixture; and
- a bounded Reader projection and static-rendered Events page containing only
  occurrence time, map, and aggregate player and bot counts.

The repository also carries forward the v2.9 production-acceptance record from
pull request #139. That documentation change does not expand v2.10 runtime
behavior.

This record freezes the release-candidate scope. Machine-client provisioning,
game-host Worker or plugin installation, secret injection, spool activation,
delivery activation, a production event, dead-letter replay, additional event
types, a broker, and player-level data are not part of `v2.10.0-rc.1`
acceptance. They remain a separate, explicitly reviewed production pilot.

## Claim Boundary

Candidate acceptance can show that the reference control plane safely carries
the dormant v2.10 schema and API/Web code, that the migration is recoverable and
compatible with the previous runtime, and that an authenticated Reader sees a
bounded empty or retained game-event projection without a widened browser
boundary. It cannot show that production gameplay delivery works because no
production writer identity, agent, or plugin is activated by this release.

Repository tests can show deterministic behavior for the agent, spool, producer
fixture, ingress, retention, and Reader projection. They cannot prove game-host
filesystem ownership, abrupt power-loss durability, provider compatibility,
real event cadence, long-term reliability, high availability, or an achieved
SLO.

Public documentation may contain revision identifiers, image digests, workflow
links, sanitized counts, durations, and pass/fail results. Host and provider
identifiers, addresses, credentials, secret paths, token values, source or event
identities, raw database rows, queue payloads, and RCON content stay outside
Git.

## Migration SQL Review

Migration `20260914101652_AddGameEventInboxFoundation` creates
`goldsrcops.game_event_inbox` with:

- UUID primary key `Id` and a cascading foreign key to `servers.Id`;
- positive contract-version and source-sequence constraints;
- an all-null or bounded aggregate population constraint where bots cannot
  exceed players;
- a receive-time retention index;
- a server, occurrence-time, and ID Reader index; and
- a unique server, source-instance, and sequence tuple.

The migration creates a new table and indexes. It contains no update, delete,
row-by-row backfill, existing-column change, or existing-table index build. It
still requires a serialized production maintenance action because DDL and the
foreign key can briefly lock catalog and referenced-table state.

The expected EF migration count increases from 11 to 12. The restore rehearsal
must require `game_event_inbox` in its table inventory, apply the exact candidate
migration bundle, reapply it without changing migration history, and start the
retained v2.9 API against the migrated copy through a read-only connection with
background mutation paths disabled.

The schema is additive for v2.9. Ordinary rollback restores the retained v2.9
API and Web digests while leaving the new table in place. Running the down
migration would destroy retained event data and is not the normal rollback path.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness and restore-rehearsal contract through protected
   `main`.
2. Repeat the exact `v2.9.0..main` commit and file inventory and confirm that no
   undeclared runtime or infrastructure path entered the candidate.
3. Require `Change Scope`, `Quality Gate`, `Container Smoke`, and `Browser
   Smoke`. Because this change strengthens executable recovery tooling, it must
   use the full CI path rather than the documentation fast path.

### 2. Candidate Publication

1. Create signed annotated tag `v2.10.0-rc.1` at the reviewed `main` revision.
2. Require build-mode publication of API and Web images from that exact
   revision.
3. Record and independently verify both immutable digests, OCI source revision,
   and published-image smoke jobs.
4. Do not publish `latest`, create the stable tag, or treat the source Worker
   and plugin as approved host-installation artifacts.

### 3. Backup And Isolated Migration Rehearsal

1. Retain the current v2.9 API and Web digests in owner-only rollback
   configuration.
2. Create one fresh encrypted off-host PostgreSQL backup and run a `100%`
   repository data check. Preserve the preceding known-good snapshot.
3. Restore the fresh snapshot into disposable PostgreSQL without network
   egress or a published host port.
4. Apply the migration bundle from the exact candidate API digest, require 12
   migration-history entries and `game_event_inbox`, and verify the expected
   keys, constraints, and indexes.
5. Reapply the bundle and require the migration count and schema inventory to
   remain unchanged.
6. Start the retained v2.9 API against the migrated copy using a read-only
   connection with polling, dispatch, retention, alert delivery, and telemetry
   disabled; require liveness and readiness.
7. Store only sanitized owner-only evidence outside Git and remove disposable
   containers and decrypted volumes.

### 4. Digest-Pinned Dormant Rollout

1. Capture a sanitized continuity baseline for public health, container and
   game-service identities, restart counts, A2S state, incidents, durable
   queues, and scheduled-backup freshness.
2. Run production preflight against the verified candidate API and Web digests.
3. Apply the candidate migration bundle once as a serialized one-shot action.
4. Recreate only API and Web from the exact candidate digests. Do not recreate
   Caddy, PostgreSQL, telemetry, or the game service.
5. Do not provision an OAuth machine client, install the Worker or plugin,
   inject game-event credentials, enable spool import or delivery, or create an
   inbox row.

### 5. Short Production Smoke

Collect read-only samples for 10 to 15 minutes and stop on the first unexplained
failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image digests.
2. Verify the migration history contains the expected latest migration and the
   new inbox table is present without exposing database rows.
3. Require anonymous access to remain denied for both game-event routes. Verify
   Reader access to the bounded GET route and denial of the machine-only POST
   route without provisioning a production writer.
4. Through an existing authenticated Operator session, render the Events page
   and its empty state or retained bounded rows. Require only occurrence time,
   map, players, and bots to cross the browser boundary and require no mutation
   control or bearer-like value in browser content or storage.
5. Require all control-plane containers and the game service to retain their
   baseline identities and restart counts. Require recent reachable A2S with
   zero bots, no new incident, no pending durable work, and fresh scheduled
   backup evidence.
6. Recheck public health and the disabled production game-event delivery state
   in the final sample.

This interval is release smoke, not a soak or reliability claim. It does not
repeat the full OIDC matrix, backup recovery, RCON command, lifecycle mutation,
incident exercise, or interactive login when an existing session and exact
candidate browser evidence are sufficient. Passive monitoring and `API-01`
continue independently.

### 6. Separate Production Delivery Pilot

After candidate acceptance, prepare a separately reviewed and reversible pilot
for one controlled server. It must pin the Worker and plugin build, provision a
single-server OAuth machine identity, install owner-only paths and secrets,
start with import and delivery disabled, and activate one boundary at a time.
One bounded `round.ended` event may then prove spool import, outbox receipt,
API idempotency, Reader projection, and zero residual queue work. Pilot failure
blocks production game-event activation, not rollback of the accepted dormant
v2.10 control-plane release.

## Failure And Rollback Rules

- Do not deploy if candidate publication, digest verification, the fresh backup,
  `100%` repository check, restore, migration, reapplication, previous-runtime
  startup, preflight, or continuity baseline fails.
- If production migration fails, stop before recreating API or Web and
  investigate from the retained database and owner-only evidence.
- On API/Web startup, health, authorization, Reader-boundary, or rendering
  failure, recreate API and Web together from retained v2.9 digests. Leave the
  additive table in place and do not run the down migration.
- Do not insert a synthetic production game event, provision a temporary writer,
  alter monitoring cadence, or mutate incidents, commands, RCON state, or
  durable queues to make release smoke pass.
- A bad or missing availability minute remains bad. Do not pause, reset,
  backfill, or reinterpret `API-01`.

## Stable Publication Gate

Stable `v2.10.0` remains blocked until:

1. The candidate identity table is complete from verified signed-tag output.
2. The fresh backup and isolated migration rehearsal pass against the exact
   candidate and retained v2.9 images.
3. The dormant digest-pinned rollout and short production smoke pass, and
   production either retains the candidate or cleanly rolls back.
4. A signed stable tag promotes the exact accepted API and Web digests without
   rebuilding them, and both stable references pass published-image smoke.

The production delivery pilot is not a hidden stable-release gate. Its result
must be reported separately and cannot be used to overstate dormant release
acceptance.
