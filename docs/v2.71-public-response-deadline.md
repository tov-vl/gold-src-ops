# v2.71 - Complete public API response deadline

The public pages previously waited beyond their configured five-second API
limit when headers arrived promptly but the JSON body stalled. Measurements
and the chosen improvement are recorded in the
[performance baseline](public-page-performance-2026-10.md).

`PublicStatusClient` now keeps one linked cancellation budget alive from request
start through JSON deserialization for status, history, leaderboard and server
join reads. It uses the existing HttpClient timeout configuration (five seconds
in production). The budget is not restarted after headers. Its expiration
retains TaskCanceledException so existing page fallbacks continue to work;
caller cancellation remains distinct. Response disposal, optional 404/null,
empty-response validation and history-window validation are preserved.

No retry, API/schema/authentication change, new HTML cache or game change is
included. The home page keeps its parallel reads. This is an R1 Web-only release;
rollback restores the preceding Web digest without database actions.

## Local evidence

Eighteen focused service tests passed, including eleven new deadline cases:
all four reads, missing/partial bodies, one shared header/body budget, waiting
for headers, caller cancellation during either stage, and optional 404 without
reading a stalled body. Existing success and input validation cases passed.

A real local Web/Kestrel process called a synthetic HTTP API. Each of five
scenarios ran once on all three pages, after warmup. All fifteen responses
retained HTTP 200, page HTML and navigation. With immediate API headers and a
body delayed seven seconds, complete Web response times changed as follows:

| Page | Before, ms | After, ms |
| --- | ---: | ---: |
| `/` | 7009 | 5022 |
| `/play` | 7020 | 5008 |
| `/leaderboard` | 7013 | 5004 |

The reduction is approximately two seconds (28-29%) for this synthetic failure
scenario. Normal local requests completed in 6-23 ms; the sample does not prove
a normal-load speed improvement. Delayed headers still timed out near five
seconds; immediate 503 and one-second header delays retained their fallback
behavior. No production fault was injected.

An initial new assertion incorrectly rejected a null InnerException in the
caller-cancellation case; the assertion was corrected. This was a fixture issue,
not an application failure. Full gates and publication are recorded in
[readiness](v2.71-readiness.md).
