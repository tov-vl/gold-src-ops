# v2.27 Fast Re-entry Product Slice

Status: scoped on 2026-09-24; no implementation, host transition, or release
has been performed.

## Product Hypothesis

Let a player return to play shortly after death instead of waiting for the
next classic round. Start with a fixed, team-based `fast-reentry-v1` experiment,
not a claim that a complete Team Deathmatch mode or player progression exists.
The accepted `public-classic-v1` remains the live and rollback profile until a
separately reviewed game-host transition passes its gates.

The first behavioral target is respawn within three seconds of a controlled
death, with at most two seconds of visible protection that ends on attack.
Exact cvar values must be frozen after local runtime testing, not inferred
from configuration documentation alone. Keep the existing five-map inventory;
test one map first and verify profile reapplication after a map change before
considering the rotation accepted.

## Native First

The pinned ReGameDLL_CS `5.30.0.814` documents `mp_forcerespawn`,
`mp_respawn_immunitytime`, and `mp_respawn_immunity_force_unset`. It also
documents `mp_round_infinite` and `mp_roundrespawn_time`, whose interaction
with team elimination and objective maps needs an executable local check.
The first increment should use only reviewed native settings. Do not enable
random spawns: this version requires map `.nav` files, and spawn safety has
not been established for the accepted rotation.

The [AlliedModders ReDeathmatch thread](https://forums.alliedmods.net/showthread.php?t=346875)
is useful for later weapon-menu and spawn-placement research, but its
[upstream repository](https://github.com/ReDeathmatch/ReDeathmatch_AMXX) was
archived in 2025. Do not download, bundle, or activate it for this slice.
Revisit a maintained plugin or a small owned extension only if the native
experiment exposes a concrete player-facing gap.

Source for the pinned native settings:
[ReGameDLL_CS 5.30.0.814 game.cfg](https://github.com/rehlds/ReGameDLL_CS/blob/5.30.0.814/dist/game.cfg).
Player-filter semantics:
[AMX Mod X `get_players` reference](https://www.amxmodx.org/api/amxmodx/get_players).

## Existing Runtime Boundaries

- `ops/gameserver/managed-profile.sh` fixes `public-classic-v1` and reapplies
  it through `mapchangecfgfile`. A new profile must not overwrite its active
  configuration or silently change its marker and rollback inputs.
- `ops/gameserver/guarded-autostart.sh` verifies the active profile's exact
  hash and policy marker. `ops/gameserver/game-event-persistent.sh` accepts
  the classic profile for activation and binds active game and agent files to
  reviewed hashes. There is no approved in-place profile-switch operation
  while persistent telemetry is active. The implementation must design and
  rehearse an explicit transition that preserves the agent's durable queue,
  spool, identity, and independent service behavior. Refuse the transition
  if the exact rollback boundary cannot be proved.
- The v2.26 producer emits anonymous `round.ended` records when a round ends
  with at least one non-HLTV client. Its `get_players(..., "h")` guard does not
  exclude bots; the accepted host currently has zero bots. Suppressing or
  extending round endings can reduce these records without indicating
  delivery failure. Do not use round-event count as the fast-reentry
  acceptance signal, introduce player identity, or silently redefine the
  existing event contract. Fix and test bot-only suppression before any
  separate decision to enable bots.
- No API, Web, PostgreSQL, Auth0, alert delivery, firewall, or public endpoint
  change belongs to this slice.

## Implementation And Acceptance Gates

1. In a disposable local game runtime, confirm the pinned cvar behavior with
   one human client: controlled death, bounded respawn, protection visuals
   ending on attack, and stable team membership. This cannot prove damage
   immunity against another player. Check objective-map round behavior before
   freezing `mp_round_infinite` or related settings.
2. Add a fixed, plan-first profile and focused smoke for rendering, valid
   values, map-change reapplication, exact file ownership and hashes, refusal
   on drift, and restoration of the accepted classic profile. Define the
   transition around the active persistent guard and retained queue/spool,
   without weakening either service's boot checks.
3. Treat a live game-host switch as R3 and a separate decision. Rehearse
   rollback first; require external A2S, read-only RCON values, active guard
   checks, and unchanged agent aggregate state. With one consenting player,
   verify join, controlled death/respawn, map change, and return to classic.
   Stop on an unexplained gate failure without automatic retry.
4. A solo session does not prove spawn fairness, protection against damage
   from another player, team balance, or sustained play. Keep the mode
   experimental until a later multi-player session can test those claims.
   Ranks, weapon menus, custom spawn points, bots, and third-party plugins
   are separate slices.

The immediate next development task is the local runtime experiment and a
reviewed transition design. This document itself does not authorize a host
change or assert that the proposed gameplay works in production.
