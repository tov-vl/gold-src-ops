# v2.117 - Archive catch-up and independent schedule observation

## Scope and claim

Scheduled Archive requests a 1,440-minute window instead of 360 minutes. The
existing pinned exporter, five-minute ingestion delay, ten-minute raw-query
overlap, single-writer concurrency and one-attempt archive behavior remain.
Manual defaults and reviewed fingerprint-bound 60-minute rotation requests are
unchanged. Changing cron or promising hourly GitHub delivery is outside scope.

This reduces prospective gaps after delays shorter than the catch-up bound.
It does not prove complete source coverage, recover historical gaps, validate
every stored object, or establish an availability SLO. A delayed event beyond
24 hours can still exceed the requested window. An uncertain PUT is reconciled,
never automatically retried.

## Independent observation

A separate control-plane timer runs every ten minutes, outside GitHub schedule.
It makes at most two unauthenticated HTTPS GET requests to fixed public GitHub
API paths for this repository and workflow. Each response is bounded to 512 KiB,
each socket to eight seconds and the complete observation to 30 seconds. TLS
verification is enabled; redirects, environment proxies, credentials, logs and
automatic retries are absent. A 40-second systemd deadline is the outer bound.

The observer validates at most 20 recent schedule runs on main and, when one
exists, the newest successful first-attempt run's sole Archive job, source-pin
check and export/archive step. Manual workflows, reruns, skipped jobs, unrelated
branches/workflows, malformed responses and future timestamps cannot establish
freshness. Age starts at run creation, so later metadata edits cannot refresh it.
A successful workflow is execution evidence, not independent B2 Recovery.

Only five unlabeled numeric aggregates enter the existing private OTLP path:
observation success/time, presence/time of an accepted schedule success and
whether the latest run completed unsuccessfully. API responses, run identifiers, source
SHAs, addresses and credentials are not exported. Failure emits only failure and
observer time; old retained success values are masked by observation validity.
No GitHub token, new account, SSH capability or public port is needed.

Rules use bounded 30-minute last-observation history, while checking the
observer's own timestamp against real time. This bridges the ten-minute timer
without changing the existing Collector's [five-minute metric expiration](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/v0.159.0/exporter/prometheusexporter/README.md).
A retained old timestamp still expires after 30 minutes, and the latest failed
observation masks older success. Expiration gaps do not reset a held delay alert.


## Warning policy and first checks

| Warning | Condition held for five minutes | First check |
| --- | --- | --- |
| ArchiveScheduleMonitorUnavailable | No nonfuture observer heartbeat in 30 minutes | Check the independent timer, its service and private Collector. Archive state is unknown. |
| ArchiveScheduleObservationInvalid | Live heartbeat but failed public API/shape/job validation | Check public GitHub API availability/rate limiting and the fixed workflow/job contract. Retained values are not fresh evidence. |
| ArchiveScheduleDelayed | No accepted first-attempt success among 20 recent runs, or age strictly above three hours | Inspect schedule history, active writer and failed jobs. This does not authorize dispatch/retry. |
| ArchiveScheduleCatchupAtRisk | Accepted success age strictly above 18 hours | Review the approaching 24-hour catch-up boundary and source retention before any bounded recovery decision. |

At exact three/18-hour boundaries the age alerts are not firing. GitHub API
failures do not become zero-age success. Unknown history raises Delayed without
pretending a measured 18-hour age. All four warnings use the existing private
IRM/email channel and fixed name/state/time/runbook projection. Notification
history, existing recipients and watchdog remain unchanged. A real delay may
be firing immediately after installation; synthetic canaries use a separate
group and must not be mistaken for real outages.

Do not clear an alert by editing its source date, dismissing history, rotating
unrelated B2 keys or dispatching an unreviewed Archive. Source probe collection
continues independently of this archive/export workflow.

## Delivery and rollback

R3 scope: one workflow routing change, immutable archive-schedule-monitor
package, new observer service/timer, one rule file and additive allowlisted
notification routing. No API/Web/receiver image rebuild, game/agent restart,
database/queue mutation, B2 key change or exporter-pin advance is needed.

The package builder is tools/release/build-archive-monitor.ps1. Its manifest
binds source revision, length, mode and SHA-256 of all eight entries. Signed
candidate/stable archive-schedule-monitor-v2.117.0 tags identify the same package
bytes. Production acceptance requires a fresh public API observation, advancing
timer metrics, healthy rules, unrelated runtime/config continuity, one isolated
firing/resolved delivery check, and one 24-hour Archive with independent Recovery.

Rollback restores recorded routing/configuration and reloads monitoring, then
disables only the new timer. Written immutable objects, claims and notification
history remain preserved. Unknown effects or unrelated drift stop the operation.
