# v2.122 - Polling health in the Operator portal

## Scope and compatibility

R1, API and Web only. The additive Operator-only
`GET /api/operator/polling-health` feeds the static BFF page
`/operator/polling-health`. The page exposes worker observation and the three
existing warning states with separate timestamps, manual Refresh, first checks
and the existing polling runbook. No polling worker, rule, threshold, Grafana,
IRM, provider, credential, permission, database schema, game/agent or Archive
cadence changes. Public and Reader projections remain unchanged.

The existing trusted private Prometheus origin is reused. Exactly two requests
read seven raw worker gauges and the fixed three-rule group. Each has a
five-second header/body deadline and 32 KiB response bound; metrics are limited
to 28 samples, at most four complete sources. No retry, redirect, arbitrary
query, historical aggregation or provider payload is added. Source identity is
used internally to detect duplicates and is never returned to the browser.

The BFF keeps bearer tokens server-side. Its seven-second/16 KiB bounded read
independently validates the response before static rendering. Endpoint, page
and denied responses are no-store. Old API versions return an unavailable page
state through the BFF; mixed deployment never invents healthy data.

## Interpretation

One valid enabled source observed within 120 seconds is required. Multiple
current enabled sources are Unknown. A fresh disabled replica cannot hide an
active Error or a stale active source. Disabled-only and retained observations
remain Disabled/Stale, not proof of an active poller. Query samples and warning
evaluations must be nonfuture and at most 60 seconds old. Malformed or missing
subsections fail closed independently.

Running, Error, Disabled, Stale and Unknown remain distinct. Completion age is
calculated independently from worker state and compared with the existing
300..86400-second operational budget (370 seconds at production defaults).
Startup has no invented completion. Empty completed passes and failed A2S
responses are worker progress; worker/repository exceptions are separate.
Gauge callbacks are not atomic: a cycle timestamp may follow the observer
callback within one export, so both are bounded against the query time rather
than incorrectly ordering all fields against the observer timestamp.

The independent rule section shows Inactive, Pending or Firing only for the
complete fresh existing group. Missing, malformed and old evaluations stay
Unknown/Stale. A healthy worker does not clear or reinterpret a warning.
The page cannot restart, replay, acknowledge, silence or change policy.

## Verification and rollout readiness

Audit-enabled restore, format, build, tests and vulnerability audit passed:
1,680 tests succeeded; 66 opt-in browser tests are reserved for hosted CI.
The new headless desktop/mobile fixture also passed locally with JavaScript
disabled, server-side bearer transport and an unavailable-source Refresh.
Focused source/service/API/BFF tests cover malformed/future/stale observations,
duplicate sources, independent rule failures, role denial and bounded transport.
Forty-five focused API/source/service cases passed again after inspection fixes.
Scoped InspectCode completed with zero errors and four reviewed warnings:
three deliberate null-element guards at untrusted data boundaries and one
pre-existing unused host import. Notes preserve bounded validation, existing
host/fixture conventions and the established file style; no suppression ran.

Required CI, immutable candidate verification, independent runtime and actual
authenticated Operator browser acceptance remain release gates. Fixtures do not
establish production state or notification delivery. No live failure injection
or new notification canary is required because policy and routing are unchanged.

Rollback restores the exact prior image slots and recreates only API/Web with
their previously installed digests. All volumes, database, protected monitoring
files and the other thirteen captured containers are retained. An ordinary API
restart may briefly leave two current sources; the page must show Unknown until
the old observation crosses 120 seconds. Acceptance may wait only for that
freshness boundary, bounded to 150 seconds, without changing policy or retrying
the deployment. Stable promotion must reuse the accepted candidate digests.
