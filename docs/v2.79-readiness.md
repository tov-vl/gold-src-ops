## Bounded production acceptance

Use four isolated browser contexts: RU/EN with JavaScript, then RU/EN without it.
Use the existing same-origin request guard and route-drain-before-context-close
pattern from [release acceptance](release-acceptance.md). A fixed browser sequence
must implement the steps below; the existing `--partial` checker alone does not
assert the new fallback button and cannot substitute for this acceptance.

Total budget: at most 10 search POSTs, 256 HTTP requests and 180 seconds; each
operation at most 15 seconds. Space contexts by eleven seconds. Use a distinct
generated ASCII nickname of 3-31 bytes per context, held only in memory. A
collision, busy initial request or unexpected state is a refusal, not permission
to generate another probe or rerun automatically.

1. Load the localized leaderboard and require HTTP 200, no-store and correct
   language. Submit exact search once by keyboard. Require fresh empty results,
   the preserved nickname and localized fallback button. No automatic second
   POST may occur.
2. In JavaScript contexts, immediately activate the fallback by keyboard. Require
   one POST of the existing antiforgery form, contains intent and unchanged
   nickname. Require the natural shared busy response with a 1-10 second delay,
   selected contains mode and no fallback button. Early Enter must send no POST;
   countdown completion must not submit automatically. Submit one manual retry
   after expiry and require a fresh empty contains result. Three POSTs per context.
3. Without JavaScript, wait eleven seconds after the empty exact response, then
   activate the fallback by keyboard. Require one successful contains submission,
   preserved nickname/mode and no repeated shortcut. Two POSTs per context.
4. In both no-JavaScript contexts, inspect the empty-result action at widths
   320/390/1440 and 200% text before the eleven-second wait and fallback activation.
   Wait for full page load before geometry checks, then restore normal text size.
   This avoids consuming the short busy window in the JavaScript scenarios.
   Local browser evidence covers layout in all four contexts. Do not extend the
   POST budget to obtain screenshots.
5. Require no unexpected console/page/request errors, direct browser API calls,
   query nickname in URL or browser storage. Drain routed requests and close each
   context before marking it passed. Retain only sanitized phases, counts and
   outcomes, not nicknames, page bodies, screenshots or raw responses.
6. Reconcile the new instance's counters with the actual recorded outcomes,
   allowing at most 90 seconds for export/scrape visibility after the browser
   sequence. Expected successful run: eight fresh and two busy outcomes across
   ten POSTs, no unavailable/invalid/unexpected outcome. Concurrent public traffic
   must be identified; do not assert exact equality from an ambiguous aggregate.
   Require healthy rules and no unexplained warning.
7. Recheck Web health/identity and the preserved boundary. An unexplained failure,
   missing scenario, request-budget violation or uncertain transition stops
   promotion. Preserve diagnostics; no automatic acceptance rerun is included.

Existing local tests prove short-name suppression, invalid input, positive
partial matches and shared admission/cache semantics. The production exercise
proves the deployed action and its transport/telemetry; it is not a fresh audit
of every nickname, gameplay, vault recovery or an SLO observation window.

## Rollback plan

Stop on the first unexplained installation or acceptance failure. Record the
failed digest and last completed journal state before taking another action.
For a known completed Web transition:

1. Require the current setting/instance to be the recorded candidate and the
   preserved boundary to match. Verify the original deployment copy and the
   rollback digest/OCI metadata. Never choose a tag or rebuild old source.
2. Restore only the Web image setting to the frozen rollback reference, preserving
   other bytes and owner/mode. Recreate only Web through the same Compose scope.
3. Verify version `2.78.0-rc.1`, source
   `1dfe43b4ddeb2d536026b17d4a37b6773a2b332c`, exact rollback digest, mounts,
   health, RU/EN leaderboard and preserved other eight containers and 17 files.
   Confirm the old exact/contains form is available and the new shortcut absent.
   Reconcile any read-only search probe separately from failed-candidate counters.
4. Mark rolled-back only after independent verification. Preserve the failed
   candidate, journal and diagnostics; do not issue a stable tag.

If SSH is lost, a setting/Compose command has an uncertain outcome, another
operator changed the boundary, or rollback cannot restore the recorded state,
stop and reconcile before another write. Do not replay an apply/rollback, erase
a journal or restore databases/vaults. A fresh attempt needs a reviewed identity
and operation ID. Both forward and reverse Web restarts invalidate current
in-memory sessions; no game restart is needed.
