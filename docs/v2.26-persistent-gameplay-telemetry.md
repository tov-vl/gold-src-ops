# v2.26 Persistent Gameplay Telemetry Readiness

## Outcome

Prepare the existing anonymous `round.ended` producer and companion agent for
bounded long-lived operation without activating either component on the game
host. The slice closes two local observability and capacity gaps exposed by the
successful one-event v2.11 pilot:

- the producer refuses to add another incoming record once its reviewed spool
  intake limit is reached; and
- the agent exposes one versioned, aggregate-only JSON status snapshot for a
  future host guard and operator probe.

This is a local product increment. It does not install a new bundle, provision
or rotate identity, consume a secret, change systemd enablement, modify the live
game tree, restart the game, open a firewall rule, deliver an event, or change
the API, Web, PostgreSQL, Auth0, or control-plane runtime.

## Producer Backpressure

The AMX Mod X producer registers `goldsrcops_spool_max_pending` with a default
of 1,000 and a fixed valid range of 1 through 10,000. Before allocating an
event ID or opening a file, it enumerates the dedicated incoming directory and
counts every non-directory entry. Counting `.tmp` and unknown files makes the
boundary fail closed when a previous write was interrupted or an unexpected
file appears.

The producer suppresses the event when the directory cannot be inspected, the
configured limit is invalid, or the current count is already at the limit. It
does not delete, overwrite, rename, or quarantine old records to create room.
The existing aggregate failure count records the suppressed publish attempt.

This protects the game host from unbounded producer intake while the agent is
stopped or unable to import. It does not cap the agent's durable SQLite dead
letters or rejected-file evidence; those remain explicit operator states and
the SQLite queue retains its existing finite capacity.

## Machine-Readable Agent Status

`GoldSrcOps.GameEventAgent status --json` emits schema version 1 with:

- whether spool import and HTTP delivery are configured on;
- configured SQLite queue capacity;
- aggregate pending, in-flight, dead-letter, spool-receipt, and next-sequence
  values; and
- aggregate ready, processing, accepted, rejected, and temporary spool counts.

The response contains no event payload, source or server identity, filesystem
path, endpoint, OAuth setting, credential reference, map, player count, or bot
count. The existing human-readable `status` remains available and now also
shows the runtime gates and queue capacity.

The snapshot is evidence, not a single readiness Boolean. A future host policy
must allow short-lived processing and in-flight work while surfacing rejected
or dead-letter evidence separately. It must not block the agent from starting
when startup reconciliation is needed.

## Verification Boundary

Local acceptance requires:

1. focused GameEventAgent tests, including command parsing, aggregate snapshot
   shape, secret/identity omission, SQLite state, and spool counts;
2. compilation of the producer with the pinned AMX Mod X and ReAPI toolchain;
3. the complete repository Quality Gate before review; and
4. a scoped diff proving no production configuration, migration, service
   policy, or secret entered the change.

The later R3 activation slice must separately define the persistent plugin
overlay, compatibility with `guarded-autostart-v1`, agent and game service boot
ordering, restart/reboot recovery, identity lifecycle, rollback, and one fresh
real-round acceptance. It cannot proceed merely because this local increment
is green.

## Persistent Host Workflow

The follow-up repository increment adds that dedicated host policy without
activating it. `ops/gameserver/game-event-persistent.sh` is plan-only by
default and accepts only the already approved `public-classic-v1` plus
`guarded-autostart-v1` boundary. It reuses the reviewed v2.11 spool-only
transition, then installs hash-bound independent game and agent guards before
enabling bounded producer, spool import, delivery, and both boot entries.

The workflow keeps the game independent from agent, OAuth, and network health.
Its rollback disables intake and both boot entries first, preserves complete
local SQLite and producer-spool evidence in the owner-only rollback record,
uses the existing active pilot rollback, and restores the exact prior guarded
game files. Repository smoke covers plan behavior, CLI refusal, rendering,
ordering, interrupted-session rollback, service independence, and stdin-only
credential forwarding. External target preflight, rollback rehearsal,
controlled reboot, and one fresh real round remain separate R3 gates.
