# v2.116 - Recorded credential expiry notifications

## Scope and meaning

Four existing purposes (Grafana metrics/log reads and B2 archive reads/writes)
reuse the accepted credential-expiry evaluation. Collection exports only a
current evaluation timestamp and twenty binary purpose/state series. It does
not depend on opening the Operator page. No provider request, secret value,
credential ID, expiry date, verification date or secret reference is exported.
The stateless evaluator and its configuration/clock sources are singletons;
the metrics lifetime is managed by the API host without a polling worker.

The existing Operator endpoint and Web behavior are unchanged. Metrics remain
behind the existing metrics authorization and private OTLP path. Their fixed
purpose/state labels do not expose the Operator-only date fields.

## Warning policy

Each purpose has four distinct fixed alert names under CredentialExpiry:
GrafanaMetrics, GrafanaLogs, ArchiveReader or ArchiveWriter, followed by Soon,
Critical, Expired or Unknown. CredentialExpiryMonitorUnavailable covers missing,
future or more than 180-second-old evaluation timestamps. Every condition must
hold for five minutes. State rules require a complete binary one-hot observation;
missing or invalid purpose data becomes Unknown while evaluation is live.
Unavailable evaluation suppresses retained purpose warnings.
State rules select the process observation with the latest evaluation timestamp
and match its service instance before checking completeness. Collector-retained
samples from an older API process cannot create a false Unknown or preserve an
old expiry state across a restart. Equal newest timestamps with conflicting
observations still fail closed.

- Soon: positive remaining time above seven days and at most 30 days.
- Critical: positive remaining time at most seven days.
- Expired: the recorded deadline has been reached. This does not establish
  that provider access has failed; minute records use the conservative start
  of the recorded minute and can warn up to one minute early.
- Unknown: recorded metadata is missing, malformed or unverified, or the
  observation is incomplete. It is not a successful validity check.

Transitioning to a different state resolves the old alert and starts the new
state's five-minute hold. More severe states replace less severe states instead
of firing both. A refreshed evaluation never updates the provider verification
time. Healthy Recorded state creates no warning.

## Delivery and first checks

The existing private Prometheus/Alertmanager/IRM email chain accepts exactly
seventeen new alert/component/severity tuples. Fixed names encode purpose and
state; all other source labels and raw annotations are dropped. The outbound
projection retains only name, state, time, fingerprint and public runbook links.
Existing seventeen warning tuples and the separate heartbeat are preserved.
The established 30-second group wait, five-minute group interval and six-hour
repeat interval remain unchanged. Repeated evaluations do not create an email
for every scrape. A persistent problem can notify again after the repeat period.

Open the Operator credential-expiry register, check its evaluation time and the
recorded verification date, then inspect the owning provider metadata. Soon and
Critical require scheduling a separately reviewed rotation with complete old
ID/secret pairs retained for rollback. Expired requires checking the provider
and the relevant export/recovery path before claiming an access failure.
Unknown requires correcting verified metadata, not inventing a deadline.
MonitorUnavailable requires checking API, Collector and Prometheus observations;
it is distinct from missing individual provider metadata.

Keep credentials in the owner's protected store. Never paste them into the
register, chat, metrics, logs or a support request. This release does not create
or revoke keys, change the archive scheduler, run an Archive, alter provider
settings or install new permissions. No game, agent, database or backup changes
are included.

## Verification and release status

Implementation in progress. Required acceptance: focused clock/cardinality and
host registration tests; pinned local Prometheus state/freshness fixtures and
Alertmanager firing/resolved/dedup/restart/privacy rehearsal; local quality gate
and scoped inspection; required PR/main and candidate publication CI; API-only
digest rollout and hash-bound monitoring reload; one isolated controlled canary;
stable promotion of the accepted digests; final evidence PR.

This R3 slice preserves the old API digest and original monitoring files for
rollback. API is recreated; Prometheus and Alertmanager are reloaded without
recreating their containers or replacing notification state. Existing date inputs,
IRM endpoints and unrelated containers remain unchanged. A controlled canary
has a separate group identity and does not resolve real warning groups.

A successful webhook and an automatically resolved IRM group are separate
evidence from receipt of an email. A separate recovery email is not promised.
Synthetic tests do not demonstrate live credential expiration or provider failure.
