# GoldSrcOps v2.13 Release Readiness

Review date: 2026-09-16. Status: release candidate accepted; stable
digest-preserving publication remains pending.

## Scope

The v2.13 product scope is one Gameplay Activity Timeline slice integrated in
protected `main` through pull request
[#161](https://github.com/tov-vl/gold-src-ops/pull/161):

- `GET /api/dashboard/activity?limit=` includes retained `round.ended` records
  in the same bounded, globally ordered projection as incidents and commands.
- The activity response reuses the existing shape and exposes only event
  identity, source type, server identity and name, category, recorded state,
  and occurrence time.
- The Reader page adds a `Rounds` count and filter, visually distinguishes
  gameplay rows, and links each row to the existing bounded Events history.
- Desktop and mobile layouts keep all four filters visible without horizontal
  page overflow.

Map, player and bot counts, source instance, sequence, receipt time, intent
hash, raw database rows, and producer payloads remain outside the activity
projection. The slice adds no schema migration, response-shape change,
background worker, identity, mutation permission, event producer, or delivery
activation.

This record freezes the release-candidate scope. A new gameplay event,
continuous pilot activation, event export, pagination, alert delivery, schema
change, infrastructure change, or unrelated UI slice is not part of
`v2.13.0-rc.1` acceptance.

## Claim Boundary

Candidate acceptance can show that an authenticated Reader can inspect
retained completed-round activity alongside recent incidents and commands
without exposing additional gameplay metadata or disturbing monitoring. It
cannot prove complete event retention, continuous gameplay delivery, high
availability, multi-region resilience, long-term reliability, user adoption,
or an achieved SLO.

Public documentation may contain revision identifiers, image digests,
workflow links, sanitized counts, durations, and pass/fail results. Host and
provider identifiers, addresses, credentials, secret paths or aliases,
operator identity, raw database rows, tokens, source identities, event
identifiers, and RCON content stay outside Git.

## Compatibility And Reduced Gate

- The activity endpoint keeps its existing route, request, and response shape.
  Existing clients that ignore the new `Gameplay` source value remain
  unaffected.
- The repository selects a bounded subset per source, merges the subsets,
  orders them globally, and applies the requested final limit.
- The page remains static server-side rendering behind the existing `Reader`
  policy. Operator access follows the existing role hierarchy.
- No EF Core migration or persistence change exists. A fresh backup, restore
  rehearsal, migration timing exercise, and previous-runtime schema rehearsal
  are therefore not v2.13 gates.
- No game-host artifact changed. Another plugin activation, gameplay capture,
  RCON action, or game-service soak would not add release-relevant evidence.
- Pull request #161 and its post-merge workflow already exercised the full
  application, container, and browser suites. The readiness pull request uses
  the validated documentation-only fast path; the candidate tag still runs
  the complete release workflow against the exact source revision.

## Candidate Acceptance Result

The candidate was deployed by exact API and Web digest without a migration and
without recreating PostgreSQL, Caddy, telemetry, or the game service. Four
read-only samples over 181 seconds retained public API and Web health, candidate
identity, A2S reachability, zero bots, zero open or newly opened incidents, zero
dead letters, zero incomplete commands, fresh scheduled-backup evidence, and
zero container restarts. The retained game-event count remained one and the two
reviewed deferred alert-outbox records remained unchanged while delivery stayed
disabled.

An authenticated production session rendered All, Incidents, Commands, and
Rounds counts of 8/3/4/1. The retained gameplay row linked to the existing
bounded Events history. Recent Activity exposed no map, player or bot count,
source identity, sequence, receipt time, or intent hash; browser storage held no
token-like entry, the page exposed no mutation control, and the browser reported
no warning or error.

The game service separately retained its active and boot-disabled state,
invocation identity, process, restart count, and single configured UDP listener
over 442 seconds. The game-event agent remained inactive and boot-disabled with
no producer or delivery process.

The first rollout invocation supplied the Git tag form `v2.13.0-rc.1` as the
expected OCI version even though both verified image labels correctly use SemVer
`2.13.0-rc.1`. The strict identity guard rejected that invocation and restored
the exact v2.12 API and Web pair automatically. A fresh read-only baseline then
confirmed healthy service and unchanged durable state before the corrected
acceptance run. No service outside API and Web was recreated.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.12.0..main` commit and file inventory and record the
   reviewed candidate revision.
3. Require `Change Scope`, `Quality Gate`, `Container Smoke`, and `Browser
   Smoke` on the documentation-only readiness revision. The required check
   names remain present while the docs fast path avoids rebuilding unchanged
   application artifacts.

### 2. Candidate Publication

1. Create signed annotated tag `v2.13.0-rc.1` at the reviewed `main` revision.
2. Require the complete tag workflow to build and publish both API and Web
   images from that exact revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

The tag workflow is the one intentional full validation pass after repository
closure. It requires no interactive production authorization while it builds
and verifies the images.

### 3. Digest-Pinned Rollout

1. Retain the current v2.12 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, application
   container identities and restart counts, A2S state, incidents, durable
   queues, and scheduled-backup freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.
5. Do not provision an identity, activate the game-event agent, install a
   plugin, start a producer or delivery path, or manufacture gameplay data.

### 4. Short Production Smoke

Collect at least three healthy read-only samples spanning at least three
minutes and stop on the first unexplained failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image
   digests.
2. Require no unexpected API or Web restart and preserve the baseline for all
   untouched containers and the game service.
3. Require the controlled server to remain recently polled and A2S-reachable
   with zero bots. Require no newly opened incident, pending-outbox growth,
   dead letter, or incomplete command. Do not drain the reviewed deferred
   alert pair to make the smoke pass.
4. Through an existing authenticated Operator session, which includes Reader
   access, render Recent Activity and verify All, Incidents, Commands, and
   Rounds counts and filters. A retained gameplay row must link to the existing
   Events history and must not expose map, population, source identity,
   sequence, receipt time, or intent hash.
5. Reuse an already retained gameplay record when it is still inside the
   bounded timeline. If normal ordering places it outside the current result,
   verify the zero-count production state and rely on the exact-image Browser
   Smoke and endpoint tests for populated behavior; do not create another
   production event merely to satisfy this gate.
6. Confirm browser content and storage contain no bearer token, credential,
   secret reference, raw database row, or unauthorized mutation control.
7. Recheck public health and scheduled-backup freshness in the final sample.

This smoke does not repeat the v2.12 game-host continuity interval, a soak,
backup or restore rehearsal, migration rehearsal, alert-outbox investigation,
Auth0 reconfiguration, or gameplay-delivery exercise. Existing passive
monitoring continues independently.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On startup, health, authorization, activity ordering, projection boundary,
  navigation, or rendering failure, recreate API and Web together from the
  retained v2.12 digests.
- Do not mutate PostgreSQL, monitoring state, game-event state, RCON state,
  incident history, command history, or durable queues to make the smoke pass.
- Store sanitized production evidence outside Git as an owner-only regular
  file.

## Stable Publication Gate

Stable `v2.13.0` remains blocked until all four gates pass:

1. The candidate identity table is complete from verified publication output.
   **Passed.**
2. The digest-pinned rollout and short production smoke pass. **Passed.**
3. Production has either retained the candidate or cleanly rolled back with a
   documented reason. **Passed; the corrected candidate is retained.**
4. A signed stable tag promotes the exact accepted API and Web digests without
   rebuilding them, and both stable references pass published-image smoke.
   **Pending.**

Candidate acceptance and stable-publication evidence belong in short follow-up
pull requests so the signed tags continue to target the exact reviewed source
revision.
