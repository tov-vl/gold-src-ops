# v2.104 - Game-host storage observation

## Scope and contract

This R3 operations slice observes available bytes and inode capacity for four
fixed roles: `queue`, `spool`, `players` and `backup`. Each role resolves a fixed
existing directory on the game host. Paths, device/mount names, file inventories,
queue/player data and credentials are excluded from the SSH response, metrics
and notifications. Roles may share a filesystem; their capacities must not be
summed. Filesystems unrelated to those directories are outside coverage.

`storage-status` takes no arguments. It performs directory metadata checks and
`os.statvfs` calls without scanning, reading contents, creating directories,
opening SQLite or invoking the agent. It remains usable when the agent's health
publication fails. Symlinked/missing directories and invalid capacity facts make
only that role unavailable. Other valid roles remain observable.

Available blocks/inodes use the unprivileged `f_bavail`/`f_favail` values;
root-reserved blocks are excluded. Negative availability is conservatively
clamped to zero. A filesystem reporting no inode accounting has null inode
values, distinct from a supported filesystem with zero available inodes. See
the [Python filesystem API](https://docs.python.org/3.12/library/os.html#os.statvfs).
This measures filesystem capacity, not user quotas, write permissions, read-only
mount health, storage latency or future time to exhaustion.

The strict schema-1 envelope contains an observation timestamp, all four roles
and bounded integer aggregates. Duplicate keys, unknown fields/roles, booleans
as integers, oversized/nonfinite JSON, inconsistent totals and timestamps older
than 30 seconds or over five seconds in the future are refused. Error messages
never cross the transport. A single inaccessible role is explicit and carries
no capacity values.

## Collection, display and warning policy

A separate once-per-minute oneshot uses the existing restricted SSH identity,
host pin and private OTLP endpoint. It has one connection attempt, a bounded SSH
process group, a 40-second systemd deadline, no restart policy or public port.
The existing agent observer, executable and schema remain unchanged. Its shared
transport/configuration functions are frozen inside the new immutable package;
no runtime dependency on a moving source checkout is introduced.

The metric prefix is `goldsrcops_game_host_storage_`; the fixed resource is
`goldsrcops-game-host-storage-monitor`. Only capacity facts carry a label,
`role`, bounded to the four values above. Observation failure exports its state
and timestamp, never fake zero capacity. Unsupported inode accounting exports
`inodes_supported=0` and no inode counts. Role failure exports availability only.
Current dashboard facts require successful collection and collector/source
timestamps between zero and 180 seconds old. Capacity facts additionally require
that role to be available; inode facts require supported accounting. These gates
mask retained Collector series after failure, unsupported accounting or expiry.

The private API-managed dashboard `goldsrcops-game-host-storage` displays source
availability, per-role bytes/ratios, inode counts/ratios and accounting support.
All current queries are instant queries. Missing/unsupported facts show no data.

| Warning | Held condition |
| --- | --- |
| `GameHostStorageMonitorUnavailable` | No fresh nonfuture collector heartbeat |
| `GameHostStorageObservationInvalid` | Live collector but invalid/old source, or an unavailable/missing role |
| `GameHostStorageBytesLow` | Any valid role has less than 10% or 2 GiB available |
| `GameHostStorageInodesLow` | Any valid supported role has less than 10% or 10,000 inodes available |

Each condition holds for five minutes and resolves naturally. Exact threshold
values are healthy; zero available capacity is low. Valid roles may warn even
while another role is unavailable. Old/future or failed observations suppress
capacity warnings and surface monitoring uncertainty instead.

Prometheus and Alertmanager admit only the four exact warning/component/severity
tuples (`game-host-storage`, `warning`). Existing five agent and five backup
tuples retain their routing. Messages use the existing IRM/email endpoint and
sanitized name/state/time/public-runbook projection. Role/path/device details
are not sent. No new provider, secret or recipient is configured. A firing email
and resolved IRM state are separate from a recovery email, which is not claimed.

## Rollout, rollback and acceptance gates

Build a clean reviewed source with
`tools/release/build-game-storage-monitor.ps1 -Version 2.104.0 -OutputDirectory <operator-directory>`.
The immutable ZIP manifest binds every dependency, source revision, length,
mode and SHA-256. Candidate `game-storage-monitor-v2.104.0-rc.1` and stable
`game-storage-monitor-v2.104.0` use signed annotated tags; stable reuses accepted
candidate bytes without rebuilding. No application images are part of this slice.

Before installation, freeze exact existing dispatcher/rule/notification config
bytes and metadata, process/container identities, queue continuity and installed
agent/addon identities. Stage into dedicated root-owned directories and require
new unit/dashboard paths to be absent. Preserve all old code, files and existing
notifications. The new helper expands the existing restricted key with only
`storage-status`, without arguments; this new read capability requires the
owner's explicit decision before it is exposed. No shell, forwarding, key,
account, sudoers or firewall change is part of the plan.

The private claimed rollout installs only the fixed helpers/units/dashboard and
reloads affected Prometheus/Alertmanager configuration. Old mounted file inodes
must be retained. Do not restart the game, agent or existing containers. Observe
two ordinary timer/Prometheus samples, verify all current dashboard queries,
role measurements and unchanged services/data, and independently check guards
and queue continuity. Capacity exhaustion is synthetic-only; never fill the live
disk. A separately grouped channel canary may verify firing/resolved delivery
after authorization. It does not establish an actual disk failure or recovery.

Rollback disables only the new timer, removes the exact unmodified API-managed
dashboard through the existing claimed protocol, restores recorded configs and
dispatcher bytes, and validates reload plus old monitoring. No queue/player/backup
data or historical warning is deleted. Unknown outcomes retain claims and require
read-only reconciliation instead of automatic retry. No automatic cleanup,
partition resize, backup capture or full-disk repair is included.

the broad repository check. Local telemetry used the existing pinned Linux
