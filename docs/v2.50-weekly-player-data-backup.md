# v2.50 - Еженедельный backup игровых данных

Статус на 2026-10-09: установка принята, timer включен; первый weekly cycle ожидается.
Режим выбран владельцем: воскресенье, 04:00 МСК, только при пустом сервере.
См. [процедуру и границы](game-player-data-schedule.md).

## Scope и публикация

R3: автоматизация закрытого capture и существующего Archive/readback.
Две проверки A2S, прежний runtime, общий transition lock, один stop/start,
недогоняющий weekly timer и постоянный журнал неопределенных операций.
Контроль свежести использует время capture и порог восемь суток; занятый
сервер не обновляет дату успешной копии. Хранение ограничено 52 слотами;
автоматического удаления или production restore нет.

Addon 0.18.0, форматы vault, API/Web/PostgreSQL и игровой агент не меняются.
Игра вдвоем остается отложенной на неопределенный срок.

## Приемка установки

Владелец подтвердил единый пакет публикации, ограниченного машинного доступа,
установки и итогового evidence PR. На control-plane создан отдельный Ed25519 key,
его private часть осталась на этом хосте. Host key игры сверялся через уже
доверенный операторский канал. Файлы доступа root-only.

На игре создан `gso-player-backup` с заблокированным паролем, без дополнительных
групп. Root-owned authorized_keys ограничивает источник control-plane `/32`
и фиксирует dispatcher с `restrict`; sudo разрешает только этот dispatcher.
Существующий операторский доступ сохранен, sshd reload не изменил игровые
сервисы. Рабочий сетевой путь уже существовал, UFW и provider firewall не менялись.

Проверки непосредственно на хостах подтвердили:

- точные source bytes, root ownership, отсутствие group/other write;
- `visudo -cf`, `sshd -t`, эффективный allowlist и отказ shell, PTY, forwarding,
  SFTP, лишних аргументов и capture вне воскресного окна;
- отсутствие игровых попыток и pending-записей, прежние InvocationID игры и
  агента, прежний addon/configuration baseline, settled queue/spool;
- независимые A2S/RCON: сервер отвечает, addon 0.18.0 и map addon 0.2.0 работают,
  состояние хранилищ и игровых функций без новых ошибок;
- импорт уже принятой v2.49 копии как начального last-success без нового Archive;
- свежесть по времени capture и чтение игрового snapshot из restic в transient
  service с теми же sandbox properties, что у новой службы; точный snapshot
  связан с last-success по id, host, workload tag, пути и bundle hash;
- `systemd-analyze verify`, календарь, точное совпадение установленных units и
  `enabled/active` timer. Сам backup service еще не запускался.

Ближайшая попытка: **2026-10-11 в 04:00 МСК** (01:00 UTC). При установке не было
stop/start игры, новой загрузки snapshot, восстановления vault или изменения
игровых данных. Приватные записи и идентификаторы сохранены вне Git.

## Уточнения установочной проверки

Проверка AllowUsers сначала ожидала одну строку, тогда как sshd выводит каждое
правило отдельно. После сверки частично установленного состояния проверка была
исправлена; ключ и пользователь повторно не создавались.

Первый sandbox-запрос snapshots наследовал host-фильтр основного backup и не
выбрал игровой workload. Явный `<backup-host>.players` подтвердил существующую
игровую копию. Это изменение проверочного запроса, не backup configuration или
опубликованных source bytes. Перед продолжением обе причины были установлены;
неопределенные операции Archive/capture не повторялись.

## Оставшаяся приемка

Первый фактический воскресный cycle и его off-host snapshot еще не проверены.
При занятости сервера ожидается skipped-busy; при неизвестном результате
следующие попытки блокируются. Вне расписания cycle вручную не запускался.
Проверка A2S и stop не атомарны, короткий промежуток для входа игрока остается.
Отдельный engine rehearsal каждой будущей копии и гарантированный RPO/RTO
не заявлены. Ранее принятая v2.49 recovery-проверка сохраняет свою границу.
