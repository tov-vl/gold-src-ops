# GoldSrcOps v2.19 Permanent Receiver Readiness

Decision date: 2026-09-18. Status: the direct Grafana Cloud IRM compatibility
trial failed closed; the thin durable receiver and its muted provider path have
now passed the bounded local and provider-side compatibility trial. Production
alert delivery remains disabled and the pending pair is unchanged.

## Goal

Select the first permanent durable receiver candidate and define the evidence
required before the existing alert dispatcher may be enabled. This slice closes
the design ambiguity around the two durable pending availability events without
draining, deleting, replaying, or reclassifying either row.

Grafana Cloud IRM was the preferred direct candidate because the project already
uses a separate Grafana Cloud stack and its incoming webhook templates can map
the existing payload. The bounded trial below showed that previewed grouping
and resolution templates did not produce the required runtime correlation.
Direct IRM is therefore rejected for the GoldSrcOps sender contract, and the
durable adapter fallback is selected without weakening the gates.

## Existing Sender Contract

GoldSrcOps already supplies the information needed for a receiver trial:

- `eventId` is the immutable outbox identity and is repeated in the
  `Idempotency-Key` request header on every attempt;
- `incidentId` is shared by the unavailable and recovered transitions;
- `eventType` is either `server.availability.unavailable` or
  `server.availability.recovered`;
- `occurredAtUtc`, `openedAtUtc`, and optional `closedAtUtc` preserve source
  chronology;
- `serverName`, `reason`, `consecutiveFailures`, and optional
  `durationSeconds` provide bounded operator context;
- delivery is at least once, redirects are not followed, `408`, `429`, and
  `5xx` responses are retryable, and other non-success responses are terminal.

The generic HTTP channel sends the immutable version 1 JSON body without a
provider-specific transformation. The receiver must therefore either consume
that body directly or sit behind a separately reviewed adapter.

## Hard Gates

A permanent receiver is acceptable only when a bounded trial proves all of the
following:

1. The same `eventId` delivered more than once has one logical delivery effect
   and cannot create an additional page or escalation.
2. The unavailable and recovered events sharing one `incidentId` belong to one
   receiver-side alert group, and the recovered event resolves that group.
3. Repeating an already accepted recovered event does not reopen the group or
   create another notification.
4. Receiver evidence retains the source event ID and source transition time;
   ingestion time must not replace `occurredAtUtc` in the operator record.
5. A reviewed historical catch-up can ingest an already recovered pair without
   notifying an operator about the stale unavailable transition.
6. A fresh post-catch-up unavailable event can notify exactly once and its
   matching recovery can stop escalation and resolve the same group.
7. The endpoint returns a supported `2xx` response within the sender timeout,
   does not require redirects, and behaves predictably under duplicate and
   rate-limited requests.
8. The receiver URL and any authorization material stay outside Git, logs,
   browser output, metrics, and retained test evidence.

Provider documentation or a successful single request is not proof of these
gates. The trial must observe receiver state and notification effects.

## Direct Grafana Profile

The completed non-production compatibility trial used one dedicated incoming
webhook integration and the default route with no escalation chain selected.
It did not reuse the Synthetic Monitoring alert route or change the `API-01`
measurement.

The intended template semantics are:

| Receiver field | Source |
| --- | --- |
| Grouping ID | Constant namespace plus `payload.incidentId` |
| Resolve signal | `payload.eventType == "server.availability.recovered"` |
| Title | Stable GoldSrcOps availability title plus `payload.serverName` |
| Message | Event type, reason, failure count, and source timestamps |
| Labels | Static project/environment labels plus payload version |
| Source link | Omitted unless a later reviewed Reader URL contains no secret or mutable action |

The raw `eventId` must remain visible in receiver evidence even if the provider
cannot use the request header in a template. No field may include a server
address, credential reference, webhook URL, token, RCON data, or arbitrary
response content.

## Compatibility Trial

Use synthetic UUIDs and timestamps that cannot collide with production data.
Send the immutable bodies and matching `Idempotency-Key` headers directly to
the dedicated no-notification integration; do not route them through the
production outbox.

| Step | Request | Required observation |
| --- | --- | --- |
| 1 | One unavailable event | One open group identified by `incidentId`; source `eventId` and time visible. |
| 2 | Exact duplicate of step 1 | Still one logical group and no second notification or escalation effect. |
| 3 | Matching recovered event | The same group resolves and preserves chronological source evidence. |
| 4 | Exact duplicate of step 3 | No new or reopened group and no notification effect. |
| 5 | New unavailable/recovered pair through the muted catch-up route | The pair reaches a resolved terminal state without human notification. |
| 6 | New pair after switching to a test notification route | One trigger notification, no duplicate notification, and one matching resolution effect. |
| 7 | Bounded `429` or documented rate-limit simulation when available | The response and retry behavior remain compatible with the existing sender policy. |

Capture only sanitized request hashes, synthetic identities, response status,
receiver group identity and state, and notification counts. Do not commit the
integration URL or screenshots containing account, route, schedule, user, or
secret identifiers.

## Direct Grafana Trial Result

The bounded trial ran on 2026-09-18 against a dedicated muted integration. Its
endpoint remained masked, no escalation chain was selected, and the integration
recorded no involved users. Template previews rendered the expected grouping
value from `incidentId`; the resolve expression evaluated `false` for the
unavailable body and `true` for the recovered body.

Runtime behavior did not match those previews:

| Step | Observed receiver state | Result |
| --- | --- | --- |
| 1. Unavailable | Group `#1` was `Firing` with one alert. The immutable `eventId`, `incidentId`, and source timestamps were visible in the stored JSON. The route skipped escalation because no chain was assigned. | Field retention and the muted route passed. |
| 2. Exact duplicate unavailable | Group `#2` was created as another `Firing` group with one alert and the same `eventId` as group `#1`. | Failed hard gate 1. |
| 3. Matching recovery | Group `#3` was created already `Resolved`; groups `#1` and `#2` remained `Firing`. | Failed hard gate 2. |
| 4. Exact duplicate recovery | Group `#4` was created as another `Resolved` group; the two unavailable groups still remained `Firing`. | Failed hard gate 3. |

The final receiver summary was two firing groups and two resolved groups, each
containing one alert, with no users involved. The demo-alert surface accepted
the exact bodies but did not expose a way to set the custom `Idempotency-Key`
header, so header-specific behavior remains unproven. That cannot rescue the
direct path: the recovered event had a distinct event ID and still did not
resolve either group sharing its `incidentId`.

Steps 5 through 7 were not run. Once hard gates 1 through 3 failed, exercising a
historical catch-up, a human notification route, or rate-limit behavior would
add risk without changing the receiver decision. No production outbox event was
read, delivered, replayed, deleted, or reclassified.

## Historical Catch-Up Boundary

The failed direct trial does not authorize production dispatch. After the
selected adapter passes its own compatibility tests, the two existing pending
rows form an already recovered pair and must first be drained through a
dedicated catch-up mode and muted downstream route:

1. Reconfirm delivery is disabled, there are zero processing rows, and the
   reviewed pending identities and order have not changed.
2. Reconfirm the unavailable event precedes its recovery for the same incident.
3. Bind the adapter endpoint through deployment secrets and keep its downstream
   route on a no-notification escalation chain.
4. Enable exactly one dispatcher and observe the queue until both reviewed rows
   are processed or one reaches a fail-closed state.
5. Confirm one resolved receiver group, zero pages, zero dead letters, and no
   unexpected attempt or queue growth.
6. Disable delivery again before changing the receiver route.

The later live canary is a separate approval boundary. It may enable one
dispatcher against the normal notification route only after catch-up evidence
is reviewed. It must use a naturally occurring future incident or a separately
approved controlled failure; this document does not authorize either action.

## Selected Adapter Contract

Direct Grafana Cloud IRM failed hard gates 1 through 3, so the fallback is now
the selected receiver boundary. Implement a minimal independently deployable
adapter with:

- durable uniqueness on `eventId` before acknowledging a request;
- a per-incident state machine that rejects or quarantines invalid ordering;
- immutable storage of the bounded versioned event and source timestamps;
- an adapter-owned outbox for provider delivery;
- an explicit catch-up mode that records historical pairs without paging;
- bounded retention, backup, health, metrics, and restore evidence;
- no operator mutation API in the first slice.

An adapter acknowledgement is successful only after the deduplication record
and receiver outbox entry are committed together. A transient provider failure
must not make GoldSrcOps retry into a second logical provider notification.

## Local Adapter Foundation

The local adapter is implemented as the independent
`GoldSrcOps.AlertReceiver` Minimal API. It does not reference the production API
database or reuse its schema. The receiver currently provides:

- `POST /api/v1/availability-events` with an exact configured authorization
  value and a canonical `Idempotency-Key` equal to `eventId`;
- strict version 1 JSON binding that rejects unsupported event types, unknown
  fields, non-UTC timestamps, invalid incident intervals, and unbounded text;
- a dedicated PostgreSQL `receiver` schema containing the immutable event
  ledger, current incident state, and provider outbox;
- transaction-scoped advisory locks for both event and incident identities, so
  concurrent duplicates and competing transitions are serialized before the
  acknowledgement;
- `202` for a newly committed transition, `204` for an exact durable duplicate,
  and `409` for event-ID reuse or invalid incident ordering;
- an explicit fail-safe `CatchUp` default that persists the historical state
  while suppressing provider-outbox creation, plus `Live` mode that atomically
  enqueues one `Trigger` or `Resolve` action;
- process-only liveness and PostgreSQL-backed readiness endpoints.

Twenty-five Testcontainers-backed integration cases apply the real migrations and
verify exact duplicates, changed-payload conflicts, opening/recovery ordering,
catch-up suppression, concurrent duplicate and competing-event races,
fail-closed headers, unknown JSON fields, health probes, and durable
idempotency after a process restart. They also verify single-owner concurrent
claims, strict trigger/resolve ordering, retry durability across receiver
restart, expired-claim recovery, dead-letter blocking, bounded processed-row
retention, an upgrade with existing pending work, and secret-free metrics.
Six of these cases cover submicrosecond source timestamps across a receiver
restart, both original and database-rounded recovery timestamps, CatchUp and
Live modes, and dates on either side of PostgreSQL's epoch. Incident identity
uses PostgreSQL timestamp precision; the original JSON and exact event-payload
hash remain unchanged, and a changed duplicate or a different stored
microsecond still returns `409`.
Nine focused tests cover the dispatcher,
fail-closed options, stable source-event idempotency, provider-neutral request
shape, response classification, and redirect refusal.

The initial migration creates only the new `receiver` schema, three empty
tables, constraints, and indexes. Neither migration touches an existing
GoldSrcOps relation, and the production API does not read this schema. A future
first deployment must apply both migrations before starting the adapter;
rollback stops the adapter and preserves the receiver schema for reconciliation
rather than dropping accepted events. Restore proof remains a pre-deployment
gate.

The provider worker now exists but is disabled by default. Enabling it requires
an explicit HTTPS endpoint and authorization. Its PostgreSQL lease uses
`FOR UPDATE SKIP LOCKED`; retry and claim recovery are bounded, and a dead
letter deliberately blocks later work for the same incident so a resolution
cannot overtake a failed trigger. A committed or processed provider-outbox row
is still not evidence that a human notification reached Grafana IRM or any
other provider.

The lifecycle migration adds only nullable columns, replaces the incident-only
index with an incident/order partial index, adds processing and retention
indexes, and adds a state-field check constraint. It performs no row rewrite or
backfill. `ALTER TABLE`, index replacement, and constraint installation still
take PostgreSQL locks, so the migration belongs in a bounded maintenance step
before starting the new binary. The compatible rollout order is migration,
new binary with provider delivery disabled, health/metrics verification, then
a separately authorized muted route. Rollback first disables and stops the
worker, allows in-flight requests to finish or their leases to expire, and
preserves the schema and rows for reconciliation; it must not drop the
migration or accepted evidence.

The operational-readiness slice packages the receiver in a dedicated non-root
image with an image-local migration bundle and a file-backed secret entrypoint.
Its independent Compose contract uses a dedicated `goldsrcops_receiver`
database and role over a Unix socket and starts the runtime in `CatchUp` mode
with provider delivery disabled. The standalone profile publishes only its own
Caddy. The reviewed `gso-control-01` overlay instead joins the existing
production edge network, omits the second Caddy, and exposes no receiver host
port. The migration action is a separate networkless one-shot container using
the exact runtime image.

The existing encrypted PostgreSQL tooling now selects an explicit
`ControlPlane` or `AlertReceiver` workload. Receiver snapshots use a distinct
archive and restic tag namespace, so they cannot be selected by a control-plane
restore rehearsal. The local container smoke applied both receiver migrations
twice, accepted a CatchUp opening and recovery plus their durable duplicates
across a receiver restart with submicrosecond source timestamps, confirmed
zero provider-outbox rows, created and read a `100%` checked encrypted snapshot,
restored it into a disposable database, and reapplied the migration bundle
without changing its two-row migration history. The restored ledger contained
both suppressed source events. All temporary decrypted resources were
removed after the rehearsal.

The migration entrypoint reads the database secret into the process environment
instead of command-line arguments. Its non-root extraction tmpfs matches the
rehearsed `64m` mount, including ownership and mode; preflight pins that contract.

The muted-provider overlay and trial harness are also prepared locally. The
overlay changes only the receiver mode, provider enablement, and single-worker
limit, and mounts the endpoint and Bearer authorization from owner-controlled
files outside Git. Its preflight rejects inline provider secrets, non-HTTPS
endpoints, repository-local secret files, and weakened container hardening. The
trial is plan-only by default; when explicitly executed, it creates an isolated
database, sends one synthetic unavailable/recovered pair plus exact duplicates,
and requires `202`, `204`, `202`, `204` ingestion plus exactly one one-attempt
`Trigger` and one one-attempt `Resolve` in source order. It removes all local
trial resources afterward. This tooling has passed its local contract,
container, and bounded provider checks.

## Adapter-To-Provider Muted Trial Result

The bounded adapter trial ran on 2026-09-19 against the dedicated Grafana IRM
integration with no escalation chain. The endpoint and Bearer authorization
were mounted from owner-controlled files outside Git. The isolated receiver
accepted the unavailable event, its exact duplicate, the matching recovery,
and its exact duplicate with status sequence `202`, `204`, `202`, `204`.
Exactly one one-attempt `Trigger` and one one-attempt `Resolve` reached the
provider in source order.

The first compatibility attempts exposed two defects before the successful
cycle. Source timestamp precision beyond PostgreSQL's microsecond boundary
caused a valid recovery to be rejected against the persisted opening identity.
The successful provider trial used whole-second synthetic timestamps, but that
harness workaround did not fix the receiver. The receiver now compares incident
timestamps at database precision, with the six regression cases above; source
JSON and event-level idempotency remain exact. Grafana also
parsed a streamed JSON request as an empty object even though its content type
was JSON. The provider channel now sends a pre-serialized UTF-8 body with
`application/json` and an explicit content length; focused transport tests pin
that request shape.

The final provider observation showed one resolved group containing the two
ordered provider alerts. The route had no escalation chain, involved no users,
and produced no notification effect. All failed-attempt groups owned by this
trial were manually resolved after diagnosis. The sanitized transport and
provider observations remain in the owner-controlled evidence directory
outside Git; they contain no endpoint or authorization material. No production
outbox row was read, delivered, replayed, deleted, or reclassified.

## Scope And Non-Goals

The planning slice, direct compatibility trial, local adapter foundation,
operational-readiness slice, and adapter compatibility trial created one
dedicated muted Grafana IRM integration, sent four direct provider-trial
payloads, then delivered one adapter-owned trigger and one adapter-owned
resolution from four isolated source submissions, and packaged two
receiver-only migrations. The endpoint remained masked, no secret was copied
into repository files or retained evidence, and no escalation chain was
assigned. This work did not:

- enable `AlertDelivery__Enabled`;
- read or mutate production outbox payloads;
- drain, replay, delete, or reclassify pending rows;
- change the event contract, sender, retry policy, production database,
  identity, UI, or game-host runtime;
- deploy the adapter, apply its migrations persistently, bind a provider credential
  to a persistent runtime, or run an enabled production provider worker;
- exercise a historical catch-up, human notification route, or rate-limit
  response after the direct receiver had already failed its first gates;
- claim receiver availability, paging reliability, long-term reliability, or
  an achieved SLO.

## Next Gate

The existing paid Selectel VDS `gso-control-01` is selected for the first
persistent receiver placement. This is a deliberate cost-conscious MVP
compromise, not an off-host availability claim: control-plane host failure,
resource exhaustion, or maintenance also removes the receiver. Isolation is
therefore enforced at the process and data boundaries with a dedicated image,
database, Unix-socket volume, secrets, backup namespace, migration history, and
CPU/memory limits. The receiver reuses the existing Caddy and public ports;
only the exact POST ingestion path is routed to its private network alias.

The deployment package is merged. The next repository gate adds dedicated
AlertReceiver publication and published-digest verification alongside the
existing API/Web jobs. The receiver container smoke accepts `-Image` with an
immutable GHCR digest, validates the requested digest and OCI identity, and
runs the complete receiver migration, backup, and isolated-restore rehearsal
without rebuilding it. Publication itself remains pending until the frozen
release-candidate tag runs that workflow. DNS, private environment values,
credentials, and resource identifiers remain in the owner-controlled operator
record.

Only then deploy on `gso-control-01` in `CatchUp` mode with provider delivery
disabled and collect health, migration, resource, backup, and isolated-restore
evidence for the dedicated receiver boundary. The two durable historical rows
must then be re-reviewed before a separately bounded muted catch-up is
authorized. Moving the receiver to a separate host remains a later resilience
upgrade if availability requirements justify the additional VDS.

Production delivery remains disabled. Consuming the existing pending pair and
the later one-dispatcher live canary remain separate gates; neither is
authorized by the successful synthetic provider trial.
