# v2.97 - In-stack game-event agent warnings

## Scope and warning policy

R3 operations-only release on top of the accepted v2.96 observer. Add one
Prometheus rule group and API-managed Grafana dashboard
`goldsrcops-game-event-agent-alerts`. The diagnostic dashboard, observer, agent,
game, queue/spool, application images, SSH permissions and credentials are
preserved. No notification destination, automatic restart, replay or cleanup is
added. These warnings are diagnostic allowances, not availability SLOs.

| Warning | Condition before the common five-minute hold |
| --- | --- |
| `GameEventAgentMonitorUnavailable` | No heartbeat, heartbeat older than 180 seconds, or future-dated heartbeat |
| `GameEventAgentObservationInvalid` | Observer heartbeat is current but the snapshot failed validation, is absent, older than 180 seconds or future-dated |
| `GameEventAgentWorkerProblem` | Agent stopped; a known loop/process gauge is missing; or an enabled loop remains unavailable, starting, stale, failed, retrying, blocked or stopped |
| `GameEventAgentQueueDelayed` | Pending/in-flight exists and oldest enqueue age is at least 300 seconds, while delivery is enabled |
| `GameEventAgentSpoolProblem` | Dead-letter exists, readable spool has rejected files, or spool is unreadable |

All warnings have fixed `severity=warning` and `component=game-event-agent` labels,
without a player, event, source or host label. Loop states are aggregated into one
worker warning, so transitions between failure states do not reset its hold.
Disabled loops and running idle loops do not produce worker warnings. Deliberately
disabled delivery suppresses the waiting-age warning; existing dead letters still
require attention. No new-event timestamp is used to judge an idle server.

Monitor failure suppresses data-specific warnings; a live observer with an invalid
snapshot produces the invalid-observation warning instead. Data warnings require
both collector and source timestamps in the inclusive zero-to-180-second range.
Retained exporter counts cannot keep them active after observations expire.
Waiting age includes elapsed time since the source snapshot while work waits.
Empty waiting queues suppress retained ages. Unreadable spool does not validate
old rejected counts; its explicit availability flag is independently actionable.

The existing observer runs once per minute; Prometheus scrapes/evaluates every
15 seconds. A frozen observer is normally detected after its freshness allowance
plus five minutes of continuous failure. An event first becomes delayed at five
minutes, followed by the five-minute hold. Evaluation cadence adds ordinary
quantization. Transient problems below the hold resolve without firing.

The alerts dashboard shows not-triggered, pending and firing states using instant
queries. It requires the rule group's evaluation timestamp to be no older than
60 seconds and not in the future; otherwise panels show no fresh evaluation.
Not-triggered does not prove end-to-end event delivery. The existing diagnostic
dashboard remains the source for counts and worker details. Prometheus/Grafana
loss itself is outside this in-stack path, and no personal messages are sent.

## Diagnosis

1. For unavailable observations, inspect the existing observer timer/service,
   fixed SSH read and private Collector path. Do not infer a zero queue.
2. For invalid snapshots, inspect the bounded observer failure and passive
   status. Do not initialize a missing queue or repair its schema through status.
3. For worker problems, compare process state, enabled loops, cycle allowance,
   last completed/successful passes and the existing runtime journal.
4. For delayed work, compare pending/in-flight, backoff, oldest enqueue age and
   delivery outcomes. An idle error-free pass is not an accepted HTTP event.
5. For dead-letter/spool problems, preserve the evidence and use the applicable
   recovery runbook. Never delete files/rows or replay uncertain deliveries to
   make an alert disappear. Recovery naturally removes the warning when the
   condition is no longer observed; no artificial reset is needed.

## Immutable package and rollout

Build a clean accepted revision using `tools/release/build-agent-alerts.ps1` with
version `2.97.0`. The five-file manifest binds the new rule file, Prometheus config,
alerts dashboard/wrapper and unchanged accepted dashboard claim protocol. Candidate
`agent-alerts-v2.97.0-rc.1` and stable `agent-alerts-v2.97.0` are signed annotated
operations tags. Stable promotion reuses accepted candidate bytes. No application
or agent image is rebuilt, and the global application release is preserved.

Freeze the current mounted config bytes/hash/metadata, its inode, all existing
rule definitions, runtime container identities, v2.96 observer identity and old
dashboard fingerprints in the private record. Require the new rule path, alerts
source root, rollout claim and dashboard UID to be absent. Stage and hash-check
the package in root-only storage, preserving the exact previous config for rollback.

Install only the new rule file under the already mounted rules directory, and the
dashboard source under `/opt/goldsrcops-agent-alerts`. Validate the complete staged
configuration with the existing pinned Prometheus image before loading it.
The config is a file bind mount, so replace its content in place while preserving
its inode and metadata. Send SIGHUP to the existing Prometheus process, then require
successful reload, unchanged previous rules and the exact new group. Do not
recreate a container, change its image or enable a public reload endpoint.

The new fixed-UID wrapper reuses the accepted v2.96 dashboard claim protocol with
a separate root-only journal. It requires absence and `overwrite=false`, consumes
the existing protected Grafana password only in memory, and does not modify the
old dashboard or provider policy. Pending requests require read-only reconciliation
before any decision, never automatic retry.

On a failed gate, restore only the exact prior config bytes in place after checking
the installed new hash and metadata; validate/reload the previous configuration,
verify old rule definitions and unchanged process identity, then remove only the
hash-matching new rule file. Roll back only the new API-managed dashboard through
its accepted fingerprint/version receipt. Remove only this release's verified
source files and empty owned directories; retain claims, snapshots and receipts.
Refuse operator drift. Do not alter v2.96 files, data volumes, queues or credentials.

## Verification and delivery gates

Independent promtool scenarios cover exact expiry/age/hold boundaries, idle and
disabled loops, all enabled failure states, missing gauges, frozen/future/invalid
observations, retained data suppression, quarantine and recovery. The pinned
telemetry stack additionally exercises real OTLP observations, all five firing
and resolving warnings, exact dashboard expressions, invalid reload retention,
config rollback and unchanged existing dashboards/rules/process identity.
Only the isolated live stack shortens the hold to three seconds; promtool tests
retain the production five-minute policy.

The new dashboard uses the same six root lifecycle/credential-format cases as
v2.96, independently with its own UID. No C# changed; local .NET/InspectCode need
not duplicate required full product CI. Product/main CI, immutable publication,
reviewed reload, independent target acceptance and final evidence closure remain
separate gates until their exact results are recorded. Production fault injection,
real events, client rendering, direct notifications and 24-hour activity are not
required or claimed for this policy installation.

Local verification passed 34 independent production-timing promtool scenarios,
all five live firing/recovery paths and the invalid-reload/config-rollback
rehearsal on the pinned stack. The existing backup/leaderboard/Web rule cases
(21/25/30), their stack checks and v2.96 diagnostics also passed. Both fixed-UID
dashboard installers passed their six root cases. Python/JSON parsing, package
builder parsing and scoped whitespace checks passed. Docker was already running
before this milestone; only this rehearsal's containers and network were removed.
