# v2.127 - Snapshot retention worker liveness

## Scope

R3 monitoring policy exercise: instrument the existing snapshot-retention worker,
install only API and the reviewed private monitoring files, and exercise one
isolated firing/resolved canary through the existing IRM channel. No new provider,
credential, permission, endpoint, migration or cleanup request is introduced.
Web, receiver, game/agent, Archive cadence and retention settings stay unchanged.

## Semantics

The worker still executes one bounded cleanup pass followed by the configured
delay. The repository, cutoff, batch size, transaction and exception handling
retain their existing meanings. A successful zero-deletion or full-batch pass
is progress. A worker/repository exception is a failed cycle. Shutdown cancellation
does not manufacture a completion or failure, and does not trigger another pass.

Always-initialized `goldsrcops.snapshot_retention.worker.*` gauges expose enabled,
process start, observation, last start/completion/success/failure, duration,
in-progress and consecutive failure count, without IDs, paths or exception text.
Failure count saturates at one million and resets after a success. State is
0 Unknown, 1 Running, 2 Error, 3 Disabled or 4 Stale. Running means recent
successful progress, including the normal wait between passes; in-progress is
separate. Restart does not reuse progress. A backward clock becomes Unknown.

The observation budget is `max(300, 60 + 2 * CleanupIntervalSeconds)`:
660 seconds at the five-minute default, and at most 172860 seconds for the
existing validated interval range. This is monitoring headroom, not a timeout,
database-duration bound or reason to retry. Startup without a completed pass
remains Unknown until the budget expires.

Prometheus separately checks observation freshness, bounded metadata and a unique
enabled source. A retained Running value cannot hide old completion timestamps.
Disabled-only or multiple-active-source deployments cannot establish a healthy
singleton worker. HTTP-only disabled replicas do not mask an active failure.

Three held warnings use the existing private notification path:

- SnapshotRetentionMonitorUnavailable: no current valid unique active source for 5m.
- SnapshotRetentionCycleStalled: completion/startup age exceeds the budget for 2m.
- SnapshotRetentionCycleFailed: at least two consecutive failed cycles, Error
  state and recent progress, held for 2m. A successful pass clears the count.

Stalled progress supersedes the recent-failure warning. No-data does not become
healthy or a cleanup failure. The existing background-worker Grafana dashboard
gains five retention panels while keeping its UID and all polling panels.
Rollback restores that same dashboard rather than creating a retained orphan
under provisioning deletion protection.

## First checks and rollback

Preserve current image, source metadata, cycle timestamps and bounded logs.
Check enabled configuration, duplicate instances, database connectivity and
cleanup duration before a separately reviewed recovery. Do not run manual
cleanup, change retention, reset counters or restart the game to hide warnings.

Rollback restores the prior API digest, exact environment and all three existing
monitoring source files, removes only the new retention rules file and reloads
the preserved services. Existing volumes and notification state remain. No
database restore or reversal of ordinary scheduled cleanup is attempted; its
already accepted deletion semantics are unchanged by this release. If a new
notification remains unresolved, retain compatible routing until reconciled;
discarding history or removing a live notification route is not an automatic
rollback. The release does not claim a production fault injection or backlog drain.
