# GoldSrcOps v2.17 Release Readiness

Review date: 2026-09-17. Status: candidate preparation. No v2.17 tag,
immutable image, production rollout, or stable release has been published yet.

## Scope

The v2.17 product scope is the Alert Delivery Overview slice integrated in
protected `main` through pull request
[#177](https://github.com/tov-vl/gold-src-ops/pull/177):

- `GET /api/alert-delivery/status` returns configured delivery state, pending,
  processing, and dead-letter counts, the oldest pending event time, and an
  explicit UTC observation time.
- The PostgreSQL projection uses the existing outbox status and occurrence-time
  fields and returns zeros with no oldest-pending value for an empty outbox.
- The response is aggregate-only and excludes payloads, row identities, event
  types, retry errors, destinations, credentials, and other secret material.
- `/operator/alert-delivery` renders clear, active, paused, and action-required
  states through the existing Reader policy.
- The page links to the existing bounded dead-letter review but adds no replay,
  configuration, or queue-mutation control.
- Focused service, API security, PostgreSQL translation, Reader client,
  static-rendering, responsive Chromium, and token-boundary coverage protects
  the new surface.

The slice adds no database migration, authorization-policy change, background
worker, production identity, mutation permission, event producer, webhook
configuration, delivery activation, or game-host artifact.

This record freezes the release-candidate scope. Delivery activation, queue
drain, replay, retry-policy change, automatic refresh, historical charts,
alert-age policy, notification testing, schema change, infrastructure change,
or another UI slice is not part of `v2.17.0-rc.1` acceptance.

## Claim Boundary

Candidate acceptance can show that an authenticated Reader receives and
renders the aggregate snapshot that exists naturally in production, that the
configuration flag and counts agree with independent owner-only evidence, and
that requesting or viewing the snapshot does not mutate delivery state. It can
also show that the exact candidate keeps public health and unrelated runtime
continuity.

Acceptance cannot prove worker liveness from `isEnabled`, downstream webhook
reachability, delivery success, retry correctness, historical queue behavior,
alert latency, long-term reliability, high availability, multi-region
resilience, or an achieved SLO. It does not exercise every visual state by
changing production data.

Public documentation may contain revision identifiers, image digests,
workflow links, aggregate counts, durations, and sanitized pass/fail results.
Host and provider identifiers, addresses, credentials, secret paths or aliases,
operator identity, raw database rows, tokens, event identities, payloads,
delivery errors, webhook data, and RCON content stay outside Git.

## Compatibility And Reduced Gate

- Existing API clients and response contracts are unchanged. The status route
  and its contract are additive.
- The endpoint and page reuse the existing Reader authorization policy.
  Operator-only replay authorization remains unchanged.
- `isEnabled` is configuration evidence, not a worker-health or
  destination-reachability probe.
- Counts describe one aggregate database query. `observedAtUtc` is recorded
  after that query and is not a shared transaction boundary with another read.
- `oldestPendingAtUtc` uses the existing event occurrence timestamp and is
  nullable when no pending row exists.
- API and Web must be published and deployed together because the Web client
  consumes the new route.
- No EF Core migration or persistence change exists. A fresh backup, restore
  rehearsal, migration timing exercise, and previous-runtime schema rehearsal
  are therefore not v2.17 gates.
- No delivery worker, configuration, or retry behavior changed. Enabling
  delivery, draining pending work, creating a dead letter, or replaying an event
  would add risk without release-relevant evidence.
- No game-host artifact changed. Plugin activation, gameplay capture, RCON
  action, or a game-service soak would not add release-relevant evidence.
- Pull request #177 exercised the complete application, container, and browser
  suites. This readiness pull request uses the fail-closed documentation-only
  path; the candidate tag still runs the complete release workflow against the
  exact source revision.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.16.0..main` commit and file inventory and record the
   reviewed candidate revision.
3. Require `Change Scope`, `Quality Gate`, `Container Smoke`, and `Browser
   Smoke` on the documentation-only readiness revision. The required check
   names remain present while the docs fast path avoids rebuilding unchanged
   application artifacts.

### 2. Candidate Publication

1. Create signed annotated tag `v2.17.0-rc.1` at the reviewed `main` revision.
2. Require the complete tag workflow to build and publish both API and Web
   images from that exact revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

The tag workflow is the one intentional full validation pass after repository
closure. It requires no interactive production authorization while it builds
and verifies the images.

### 3. Digest-Pinned Rollout

1. Retain the current v2.16 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, application
   container identities and restart counts, A2S state, incidents, durable
   queues, incomplete commands, delivery configuration, and scheduled-backup
   freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.
5. Preserve the existing delivery configuration and durable outbox. Do not
   provision an identity, enable delivery, replay an event, manufacture a dead
   letter, install a plugin, start a producer, or create gameplay data.

### 4. Short Production Smoke

Collect at least three healthy read-only samples spanning at least three
minutes and stop on the first unexplained failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image
   digests.
2. Require no unexpected API or Web restart and preserve the baseline for all
   untouched containers and the game service.
3. Require the controlled server to remain recently polled and A2S-reachable
   with zero bots. Require no newly opened incident, unexplained outbox growth,
   dead-letter regression, or incomplete command.
4. Through an existing authenticated Reader-capable session, request
   `GET /api/alert-delivery/status` and confirm that its configured state,
   counts, oldest-pending value, and observation time agree with a bounded
   owner-only aggregate check. Do not retain row identities or payloads.
5. Open `/operator/alert-delivery` and confirm it renders the same natural
   snapshot, the expected state priority, and the bounded dead-letter link.
   Confirm that no replay, configuration, queue-mutation, credential, payload,
   delivery-error, destination, server-address, or RCON value is exposed.
6. Confirm an anonymous API request remains unauthorized and the authenticated
   Reader request remains read-only. Do not exercise Operator replay as part of
   this release.
7. If production naturally exposes only one visual state, record that limit
   and rely on exact-image browser coverage for the other states. Do not enable
   delivery or mutate the outbox to make a presentation appear.
8. Compare the final aggregate with the baseline and explain any natural state
   transition. Do not drain, retry, or reclassify durable work to make the
   smoke pass.
9. Recheck public health, runtime continuity, and scheduled-backup freshness in
   the final sample.

This smoke does not repeat a game-host continuity interval, soak, backup or
restore rehearsal, migration rehearsal, Auth0 reconfiguration, alert replay,
delivery activation, RCON action, or gameplay capture. Existing passive
monitoring continues independently.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On startup, health, authorization, aggregate mismatch, disclosure, navigation,
  or rendering failure, recreate API and Web together from the retained v2.16
  digests.
- Do not mutate PostgreSQL, delivery configuration, monitoring state,
  game-event state, RCON state, incident history, command history, or durable
  queues to make the smoke pass.
- Store sanitized production evidence outside Git as an owner-only regular
  file.

## Stable Publication Gate

Stable `v2.17.0` remains blocked until all four gates pass:

1. The candidate identity table is complete from verified publication output.
2. The digest-pinned rollout and short production smoke pass.
3. Production has either retained the candidate or cleanly rolled back with a
   documented reason.
4. A signed stable tag promotes the exact accepted API and Web digests without
   rebuilding them, and both stable references pass published-image smoke.

Candidate acceptance and stable-publication evidence belong in one short
follow-up pull request after both remote stages complete.
