# GoldSrcOps v2.26 Release Readiness

Acceptance date: 2026-09-24. Status: `v2.26.0-rc.6` accepted on the game host
after rollback rehearsal, persistent activation, controlled reboot, and one
real-round check. Signed stable [`v2.26.0`](https://github.com/tov-vl/gold-src-ops/releases/tag/v2.26.0)
is published from the same source revision.

## Scope

The v2.26 release scope is persistent gameplay telemetry for the accepted
single-host Counter-Strike 1.6 deployment:

- the bounded `round.ended` producer with a fail-closed pending-spool limit;
- the companion agent's versioned, aggregate-only `status --json` snapshot;
- one persistent, hash-bound plugin overlay compatible with the accepted
  `public-classic-v1` profile and `guarded-autostart-v1` game policy;
- boot-persistent spool import and delivery without coupling game availability
  to agent availability;
- explicit identity, restart, reboot, rollback, and retained-evidence rules;
  and
- one fresh real-round acceptance after a controlled reboot.

This is an R3 game-host release. It does not change the API, Web,
AlertReceiver, either PostgreSQL schema, Caddy, the public firewall boundary,
the managed game profile, the RCON source policy, or any delivery worker on the
control plane.

## Candidate History

- `rc.1` lacked the required external pre-delivery gate and was not activated.
- `rc.2` reached spool-only but exposed incomplete restoration of the guard's
  rollback backup. The exact-hash inputs were restored owner-only and checked.
- `rc.3` passed the timeout rehearsal but failed at the agent's unprivileged
  hash guard. Its apply rolled back to the accepted public game.
- `rc.4` passed the external gate but failed at delivery-enabled aggregate
  status capture. Its apply also rolled back without discarding durable work.
- `rc.5` corrected the status credential context and activated persistently.
  Acceptance then exposed an extra empty-round event. PR
  [#224](https://github.com/tov-vl/gold-src-ops/pull/224) suppresses that
  event before identity allocation; `rc.6` is the accepted candidate.

The separate pilot workflow remains deliberately boot-disabled. Rejected
candidate tags and their bundles are immutable evidence, not retry targets.

## Claim Boundary

Acceptance can show that one exact reviewed game-host bundle survives a
controlled reboot, starts the game under the accepted guard, starts the agent
with the reviewed identity and bounded queue settings, emits and delivers one
anonymous real `round.ended` event exactly once, and returns to a settled
aggregate status without changing the public game, firewall, RCON, or
control-plane boundaries.

Acceptance cannot prove multi-player behavior, sustained event throughput,
abrupt power-loss durability, provider-independent delivery, high
availability, long-term reliability, or an achieved SLO. It must not expose
event payloads, source or server identity, filesystem paths, OAuth values,
credentials, private topology, or raw database rows as public evidence.

## Persistent Runtime Policy

The implementation must preserve these invariants:

- `goldsrcops-gameserver.service` remains governed by the accepted game guard.
  The guard must verify the persistent overlay and producer configuration by
  exact hash before `ExecStart` rather than continue to require a plugin-free
  tree.
- `goldsrcops-game-event-agent.service` is enabled only after bundle, identity,
  environment, state-directory ownership, token contract, and rollback inputs
  pass verification. Only its hash `ExecCondition` bypasses the service user
  and group to read root-only activation state; the agent process remains
  unprivileged and all other service restrictions remain in force.
- The game and agent units do not `Require` each other. Agent, OAuth, network,
  queue, or delivery failure must not stop or restart the game process.
- The agent can start and reconcile durable spool and SQLite state without a
  healthy game process. Its existing network-online ordering remains, with no
  circular ordering against the game unit.
- Spool import and delivery are both enabled for the persistent state. The
  producer starts only with the reviewed incoming-directory limit and never
  deletes old files to create capacity.
- The aggregate JSON status is evidence, not an `ExecCondition`. Pending or
  in-flight work may be transient; rejected files or dead letters require
  operator review and must not be erased or retried automatically.
- Automatic host reboot remains disabled. Only the two reviewed services may
  be enabled across boot.

## Identity And Evidence Lifecycle

- The client secret enters only through the reviewed stdin path, is installed
  root-owned with mode `0600`, and never appears in arguments, tracked files,
  logs, status output, or retained public evidence.
- Activation verifies issuer, audience, permission, and server binding before
  mutating the active runtime. It does not provision, rotate, or broaden the
  identity.
- Rollback removes the active secret from the service boundary but does not
  silently delete or rotate the remote machine client.
- Queue, spool, receipt, rejected, and dead-letter aggregates are captured
  before and after each transition. Payloads and identifiers remain
  owner-only.

## Rollback Contract

The persistent workflow must be plan-only by default and own one exact
rollback path. Rollback disables new producer intake first, stops and disables
the agent, preserves unresolved queue and spool evidence, restores the exact
pre-activation game files, guard marker, and the guard's own exact-hash rollback
backup, and returns the game service to its accepted active/enabled public
profile. The original guard backup must be captured before `--disable` removes
it. A restored marker without its referenced rollback files is not a complete
rollback.

Rollback must not delete pending, in-flight, rejected, or dead-letter evidence
to satisfy a gate. If durable work cannot be sealed without loss, stop with the
game boundary restored and retain the evidence for a separate disposition
decision. An interrupted apply must use the same rollback inputs; an uncertain
remote delivery must never be retried merely because the transition was
interrupted.

## Ordered Release Sequence

### 1. Close The Predecessor Boundary

1. Confirm published v2.25 stable identity and retain its exact accepted
   target baseline.
2. Retain the accepted plugin-free game runtime, public firewall, profile,
   game guard, service states, and owner-only rollback inputs.

### 2. Implement And Review Persistent Activation

1. Add a dedicated plan-first host workflow; do not relax the pilot script's
   deliberate boot-disabled contract.
2. Add isolated Ubuntu smoke for overlay ownership and hashes, guard rebinding,
   exact capture and restoration of the guard's own backup, independent service
   ordering, producer and delivery gates, aggregate status, interrupted apply,
   evidence-preserving rollback, and final service states.
3. Require the full repository CI because executable host policy changes.
4. Merge readiness only after the final diff and rollback contract agree.

### 3. Publish And Verify The Candidate

1. Create signed annotated tag `v2.26.0-rc.6` at the exact reviewed merge.
2. Require the tag workflow and independent workflow-image verification even
   though no control-plane image is deployed.
3. Build the production-eligible `2.26.0-rc.6` game-event bundle from the same
   clean revision. Record its ZIP digest, manifest source revision, component
   pins, payload hashes, and all default-off activation flags owner-only.
4. Stop if the tag, bundle source, manifest, or reviewed host scripts disagree.

### 4. Read-Only Target Preflight

1. Verify the accepted public profile, game guard, firewall, RCON source,
   service definitions and enablement, active invocation, restart count, A2S,
   zero bots, disk capacity, dormant agent state, and absence of a live plugin
   overlay.
2. Verify exact bundle, installer, activation, guard, and rollback hashes,
   including the guard marker's referenced rollback directory and file hashes.
3. Verify the existing machine identity contract without printing the secret.
4. Capture aggregate queue and spool status and the owner-only rollback record.

### 5. Rehearse, Apply, And Reboot

1. Rehearse the exact rollback from a spool-only activation before producer or
   delivery is enabled, then restore and independently verify the accepted
   plugin-free baseline.
2. Apply the reviewed overlay in spool-only mode. A planned game restart is
   allowed only inside this frozen transition. The activation pauses at a
   root-only, five-minute external gate before enabling producer or delivery.
3. Verify public A2S and authenticated control-plane RCON against the active
   spool-only game invocation. Retain the observations in the owner-only
   operator record, then return the gate receipt through the reviewed private
   channel. A missing, late, or invalid receipt fails and rolls back. The
   receipt is an operator attestation, not a substitute for the observations.
4. Enable the agent across boot only after the complete persistent gate passes.
5. Perform one controlled reboot. Require a new boot identifier, key-only
   operator access, both reviewed units active/enabled, zero unexpected game
   restarts in the new boot, a passing game guard, settled agent status, public
   A2S, and authenticated RCON.

### 6. Accept One Real Round

1. Require an empty settled delta for the acceptance window, then have one
   operator connect and complete one real round.
2. Observe exactly one new valid `round.ended` record with allowed map and
   aggregate player/bot counts, one accepted delivery, and no duplicate,
   conflict, rejection, or dead letter.
3. Verify the Reader projection and aggregate agent status without exposing
   identities or payloads.
4. Confirm the incoming and processing spool states settle, public A2S remains
   reachable, the managed profile and RCON policy are unchanged, and neither
   service has an unexplained restart.
5. On any failure, execute the reviewed rollback and retain unresolved evidence
   for diagnosis. Do not manufacture or replay another event automatically.

### 7. Promote And Close

After target acceptance, create signed stable tag `v2.26.0` at the exact
candidate revision. Require digest-preserving promotion and independent stable
verification, then update readiness, release notes, backlog, and README in one
short evidence pull request. Stable promotion changes no target runtime.

## Failure Rules

- Stop on the first unexplained bundle, hash, ownership, identity, token,
  guard, service, reboot, A2S, RCON, spool, queue, delivery, projection,
  restart, or continuity failure.
- Never replace a published tag or bundle, retry an uncertain delivery, delete
  durable evidence, broaden identity or RCON permissions, or weaken the game
  guard to make acceptance pass.
- Stop for a new decision if rollback cannot restore the accepted public game
  boundary or preserve unresolved event evidence.
