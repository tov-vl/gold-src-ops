# v2.101 - Actual player-copy engine recovery

## Accepted boundary

On 2026-11-03, the already verified manual player-data copy passed an isolated
AMXX engine recovery exercise. This closes the separate engine gate left by
[manual-copy acceptance](player-backup-manual-refresh.md). That earlier operation
proved encrypted Archive/Recover and exact bytes; this exercise used its retained
verified readback, without a new capture, Archive or remote Recover.

The recovery exercise is R3, confined to a disposable local container. Its
repository follow-up is documentation only. No production restore, service
restart, addon installation, permission change, snapshot deletion, backup-ledger
update or alert reset occurred. Addon 0.39.0 remains the accepted product version;
this milestone does not publish another addon or application image/tag.

## Inputs and privacy

Read-only preflight verified the recorded bundle SHA-256, capture timestamp,
manifest, recovered vault inventory and original Recover operation hash. The
closed copy contains two vaults and no journals. It holds 42 records, not
necessarily 42 distinct players.

The engine fixture was compiled from the exact accepted 0.39.0 product source
and dictionary with AMXX 1.10.0.5481 and ReAPI 5.24.0.300. ReHLDS 3.15.0.896,
ReGameDLL 5.30.0.814 and the existing local client-lab image were pinned to the
reviewed inputs. The private operator record retains all source, compiler,
binary, image and orchestration hashes.

The fixture substitutes a synthetic client identity and a rejecting product-
write observer. Native nVault reads and the actual product loaders remain real.
Any attempted product write fails acceptance. This tests loading and derived
state, not Steam authentication or a player's client session.

The protected readback was streamed through existing SSH into laptop process
memory, then into container tmpfs. Restored vaults, expected rows and engine/AMXX
logs stayed in tmpfs; no raw copy, player identifiers or values were written to
laptop files, command arguments, retained logs or Git. Only bounded aggregate
markers and hashes were retained. The source directory was never a write target.

## Verification and outcome

Before actual-data execution, a synthetic positive control passed two engine
starts with all five record families. A separate control deliberately changed
an expected value and was rejected with a nonzero exit and explicit failed
assertions. Fixture compilation passed with warnings treated as errors. Earlier
preparation faults remained confined to synthetic inputs and were corrected
before use of the actual copy.

A local intent-file name collision stopped the first actual-copy invocation
before container creation. Independent container-inventory comparison confirmed
zero actual-data engine starts. The original intent and that reconciliation
remain retained. A reviewed filename correction preserved the accepted native
fixture/runtime bytes; a distinct identified execution then completed.

The actual copy passed two separate engine process starts. Each checked all
42 native values and timestamps, plus the matching product loading/derived state:

| Record family | Records checked per start | Product evidence |
| --- | --- | --- |
| Statistics | 6 | Saved kills/deaths loaded; derived rank matched |
| Preferences | 12 | Language, primary/pistol and saved confirmation matched |
| HUD | 1 | Stored toggle and saved status matched |
| Streak | 5 | Stored best loaded; current-life progress remained zero |
| Names | 18 | Stored name projection matched |

Both starts reported zero failed assertions, zero attempted product writes and
no AMXX error files or fatal/runtime markers. The container had no network or
published ports, two CPUs, 1 GiB memory, 256 PIDs and a 180-second outer deadline;
input mounts were read-only and private working directories were tmpfs.

The actual container exercise took 39.312 seconds, including its preparation,
two engine starts and removal. This excludes prior SSH transfer, compilation,
encrypted off-host download and full server reconstruction; it is not a
production RTO measurement.

Independent postflight confirmed that the owned container was absent and all
pre-existing local container identities were preserved. A second read-only
control-plane inspection matched every original bundle/vault and Recover
operation hash. The working server, agent, control-plane services, backup
schedule and historical uncertain/failed weekly records were outside mutation
scope. No Steam session or second participant was needed.

The changed-documentation gate and whitespace checks passed locally. No C# or
application runtime changed, so the complete local .NET gate and InspectCode
were not run for this operator exercise and documentation-only follow-up.

## Claim limits

This proves that this recorded, already recovered copy can be read by the pinned
AMXX runtime and current product loaders, with its observed records intact.
It does not prove a production restore, full-host disaster recovery, recovery of
writes newer than the snapshot, arbitrary schema compatibility, RPO/RTO, crash-
journal replay or fsync durability. The closed input has no journal operations,
so the exercise makes no claim about their replay.

Raw input and snapshot identities remain in the protected source record.
Private hashes, aggregate receipts, reconciled intents and control evidence are
retained outside Git; temporary containers and private tmpfs contents are gone.
The existing [player-data recovery runbook](game-player-data-backup.md) remains
the production boundary. A future live restore needs its own explicit decision.
