# Скорость публичных страниц - 2026-10-12

## Результат и граница

Измерены `/`, `/play` и `/leaderboard` на публичном сайте. Выбрана одна
оптимизация: единый пятисекундный бюджет получения данных API, включая чтение
тела JSON. Исправление еще не реализовано; этот этап содержит измерения и выбор.
Приложение, production, игра и конфигурация не менялись.

Исследован исходный revision `ada8617d8664dc7b534e34e4c7e28d1f3b6af871`.
Production проверялся через браузер; локальное воспроизведение использовало
существующую Debug-сборку Web и изолированный HTTP stub. Оно не является
проверкой опубликованного production-образа.

## Методика

Браузер Chromium 151.0.7922.34, анонимный доступ, RU, период истории 24h.
Baseline сохранен 2026-10-12 в 17:42 МСК. Для каждой страницы выполнено пять
пар загрузок в каждом профиле: всего 60 навигаций, все завершились HTTP 200.

- Обычный профиль: 1440x900, сеть рабочего места.
- Ограниченный профиль: 390x844, заданные в CDP 1.6 Мбит/с download,
  0.75 Мбит/с upload, дополнительная задержка 150 мс и CPU slowdown 4x.
  Это синтетический профиль, не реальный телефон; задержка CDP не проявлялась
  равномерно в измеренном времени заголовков.
- Первая загрузка: новый browser context с пустым HTTP-кешем. Повторная:
  тот же context после перехода на `about:blank`. Процесс браузера общий;
  холодные серверные кеши и новое DNS/TLS-соединение не гарантируются.
- LCP наблюдался до одной секунды после `load`, без взаимодействия.
  Это лабораторная метрика, не полевые p75, INP или полный аудит Core Web Vitals.

Медианы пяти измерений, секунды:

| Страница | LCP, обычная первая | LCP, обычная повторная | LCP, ограниченная первая | LCP, ограниченная повторная |

| `/` | 0.152 | 0.044 | 1.024 | 0.272 |
| `/play` | 0.184 | 0.040 | 1.116 | 0.264 |

В обычном профиле медианный TTFB первой загрузки составил 47-49 мс,

### Выброс первого соединения

Самая первая загрузка `/` дала LCP 9.568 с и TTFB 9.372 с. Образец сохранен
в статистике. Из этого времени 9.346 с прошли до `requestStart`, а ожидание
ответа после отправки запроса составило 26.2 мс. Причина задержки до запроса
не установлена; приписывать ее приложению или его серверному кешу нельзя.

Три дополнительных запуска в отдельных процессах Chromium дали время до
запроса 5.854, 0.568 и 0.488 с, ожидание сервера 21.1, 14.4 и 15.3 мс.
DNS занимал 7-21 мс, соединение 31-42 мс. Поэтому приведенные медианы не
гарантируют такое же время первого посещения для каждого пользователя.

## Ресурсы и кеширование

Все три страницы загружают два CSS и четыре небольших JS-файла.
Хешированные ресурсы сжаты Brotli и имеют
`Cache-Control: max-age=31536000, immutable`. При повторных загрузках
передача статических ресурсов равна нулю при ненулевом decoded-размере.
Это соответствует локальному кешу согласно
[описанию Resource Timing](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceResourceTiming/transferSize).

| Ресурс | Сжатое тело, байт | После декодирования, байт |
| --- | ---: | ---: |
| app CSS | 706 | 1991 |
| Общий scoped CSS | 18462 | 216893 |
| Join JS | 256 | 675 |
| Leaderboard JS | 1722 | 7086 |
| Play status JS | 2300 | 9870 |
| Status JS | 3029 | 13026 |

Суммарно статические тела занимают 26475 байт, передача с заголовками -
28275 байт. HTML сжат zstd, повторно запрашивается; Cache-Control и ETag
в ответах документа не наблюдались. Уменьшение общего CSS или подключение JS
только на нужных страницах возможно, но по этим замерам не выбрано первым
улучшением. Кеширование динамического HTML требует отдельного контракта
актуальности и доступа.

## Локальные задержки и отказы данных

Настоящий Web/Kestrel обращался к локальному stub с синтетическими DTO.
Сбои не вводились в production. После прогрева проверены пять сценариев
для каждой страницы. Все 15 ответов сохранили HTTP 200, HTML и навигацию.
Заметной ранней выдачи HTML до завершения ожидания API не было.

Время полного ответа Web, миллисекунды; по одному наблюдению сценария:

| Ответ API | `/` | `/play` | `/leaderboard` |
| --- | ---: | ---: | ---: |
| Обычный | 17 | 24 | 21 |
| Заголовки задержаны на 1 с | 1028 | 1029 | 1026 |
| Немедленный 503 | 42 | 5 | 16 |
| Заголовки задержаны на 7 с | 5033 | 5005 | 5014 |
| Заголовки сразу, тело задержано на 7 с | 7009 | 7020 | 7013 |

Пятисекундный `HttpClient.Timeout` останавливает ожидание заголовков.
В `PublicStatusClient` используется `ResponseHeadersRead`, после которого
`ReadFromJsonAsync` получает исходный токен вызывающего кода без отдельного
бюджета. Поэтому при задержке тела страницы ждут все семь секунд.
Такую границу таймаута подтверждает
[документация HttpCompletionOption](https://learn.microsoft.com/en-us/dotnet/api/system.net.http.httpcompletionoption).
Главная уже выполняет независимые запросы параллельно через `Task.WhenAll`.

Отдельно прошли шесть существующих браузерных тестов задержек, отказов,
перекрывающихся refresh и восстановления: 6 passed, 0 failed, 0 skipped.
Они проверяют поведение обновления интерфейса и не доказывают ограничение
времени чтения тела API.

## Выбранная оптимизация и приемка следующего этапа

Установить один общий бюджет 5 с на запрос и чтение JSON во всех четырех
публичных методах `PublicStatusClient`. Связать его с отменой вызывающего
кода и передавать один токен в отправку запроса и чтение тела.

Сохранить 404/null, существующие состояния недоступности, параллельность
главной и отсутствие автоматических повторов. Не менять API, БД, игру или
правила актуальности публичных данных.

Проверки реализации:

1. Успешный ответ, задержка заголовков, задержка и остановка чтения тела.
2. Общий лимит на обе стадии, без дополнительных пяти секунд после заголовков.
3. Отмена вызывающим кодом раньше таймаута.
4. Повтор локального сценария с семисекундным телом: fallback примерно за 5 с
   с небольшим допуском на планирование вместо текущих 7 с.

Ожидаемое сокращение ожидания в воспроизведенном сценарии - около 2 с.
Это цель будущей проверки, не измеренный результат исправления. Улучшение
ограничивает длительные ожидания при деградации API; ускорение обычной
загрузки не заявляется.
