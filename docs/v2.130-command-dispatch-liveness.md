# v2.130 - Command dispatcher liveness

## Scope and compatibility

Observe the existing RCON dispatcher loop independently of individual command
outcomes. A cycle includes due interrupted-command recovery and one concurrent
dispatch batch. Empty queues, failed RCON responses and lost completion claims
are completed cycles. Exceptions escaping recovery or dispatch fail the cycle.
Shutdown cancellation clears in-progress state without recording a failure.
No commands are created, retried or requeued by monitoring.

Preserve claiming, concurrency, recovery cadence, cancellation, network timeouts
and the immediate next batch after a populated batch. No schema, public/Operator
contract or command execution policy change is included.

## Observation contract

Twelve private gauges expose enabled state, process start and observation times,
cycle budget, last start/finish/success/failure times, elapsed duration,
consecutive failures, in-progress flag and state. No command/server identifiers,
payloads, secret references, addresses or exception text are metric labels.

States are 0 Unknown, 1 Running, 2 Error, 3 Disabled and 4 Stale. Running means
recent completed progress, including a normal empty-queue wait. In-progress is
separate. Restart resets progress; backward clocks are Unknown. Failure count
saturates at one million and resets on the next successful cycle.

The observation budget is `max(300, 60 + 2 * (LoopDelay + RconTimeout))` seconds,
using configured durations in seconds. It is an operational observation policy,
not a new execution timeout or a bound on database/host delays. The default is
300 seconds. Concurrency does not multiply network time because a batch awaits
parallel attempts. Metadata is rejected if the budget exceeds the maximum
obtainable from the existing configuration readers.

## Private warnings and runbook

The source must have a fresh observation within 120 seconds, valid metadata and
exactly one enabled instance. Disabled or duplicate instances cannot hide the
active worker's failures. The existing worker dashboard keeps its UID and adds
five dispatcher panels. Existing routes and provider credentials are reused.

| Warning | Condition and hold | First response |
| --- | --- | --- |
| CommandDispatchMonitorUnavailable | Missing, invalid or ambiguous active observation for 5 minutes | Check API, collector and configuration; do not infer an empty queue |
| CommandDispatchCycleStalled | No completion beyond the observation budget for 2 minutes | Inspect worker/database/network progress and current command states |
| CommandDispatchCycleFailed | At least two consecutive cycle exceptions, Error held for 2 minutes | Inspect sanitized worker logs and database access |

Stall supersedes repeated-failure notification. A single failed RCON command is
not a cycle failure. Check its existing command outcome separately. Do not issue
a probe command, retry an uncertain dispatch, drain a queue or force recovery
to clear a warning. Reconcile uncertain side effects before another action.

## Delivery boundary and readiness

R3. Install only the API image and four reviewed private monitoring files:
Prometheus configuration, the new rules, existing dashboard and Alertmanager
configuration. Fourteen other containers, their state and protected unrelated
files remain unchanged. No new provider, credential, permission or public port.
Web/receiver, game/agent and hourly Archive cadence are outside this rollout.

Rollback restores the prior API digest, exact environment/configuration and
existing dashboard bytes; removes only the new rule file; reloads monitoring
without replacing volumes or changing dashboard deletion protection. Preserve
a compatible notification route until any new group has resolved. Old progress
series may remain in the ordinary lookback and are not acceptance evidence.

Required gates: focused worker/metrics and policy fixtures, full local quality,
scoped inspection, required PR/main CI, signed immutable publication, isolated
file/rollback/dashboard/routing rehearsals, independent API-only continuity,
natural empty-queue progress and one isolated canary firing/resolved through the
existing IRM. Stable promotion must reuse the accepted candidate digests.
Local verification passed 21 focused dispatcher tests and the complete quality
gate with 2,080 passing tests. The 69 opt-in browser cases were skipped locally;
there is no Web change. Restore, formatting, build and dependency audit passed.
Final scoped InspectCode reported zero errors/warnings and nine reviewed notes.
The existing worker catch-and-continue contract and explicit constructor remain;
unmodified helper awaits, unrelated DI nesting and the fixture's first-call/block
layout retain their established structure. No suppressions were added.

The new policy passed 24 promtool scenarios. The actual pinned local routing
stack passed 526 inputs and 47 firing/resolved pairs, including retry, dedup,
reload, restart and privacy checks. Linux guarded-file rollback and same-UID
Grafana restoration from 10 to 15 and back to 10 panels passed. Production and
release acceptance are pending; isolated fixtures are not live evidence.

This stage does not prove command delivery, future queue behavior, an SLO,
Archive cadence or backup recovery. No live command failure injection is used.
