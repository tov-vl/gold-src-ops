# v2.114 - Operational credential expiry metadata

## Scope and semantics

Add `/api/operator/credential-expiry` and a static SSR page at
`/operator/credential-expiry`, linked from game-host health. Existing Operator
authorization and the server-side BFF token boundary apply; Reader and anonymous
access are denied before source reads. Private responses are no-store.

The four fixed purposes are Grafana availability metrics/log reads and B2
availability archive reads/writes. Provider, purpose and consumer labels are
fixed application text. The input is only recorded expiry and verification
dates; no secret value, credential identifier, secret reference or provider
response is read or exposed. This is a metadata register, not a provider-validity
probe, completeness claim or proof that a credential is installed or works.

At the API evaluation time, an exact deadline already reached is Expired;
positive time up to seven days is Critical, up to 30 days is Soon, and later
is Recorded. Displayed days are rounded up and clamped to zero after expiry;
classification uses the exact duration. Missing, malformed, duplicate or
future-verified metadata is Unknown, not unlimited access. Verification dates
record the last actual check and are not refreshed by viewing the page.

The Web bounds the response to four known rows, validates state/date/day
consistency and rejects snapshots older than 180 seconds or from the future.
Unrecognized text is never rendered. A missing endpoint, failed read or malformed
response produces four explicit Unknown rows. Refresh obtains a new evaluation;
JavaScript and automatic polling are unnecessary.

## Configuration and compatibility

API configuration keys use `CredentialExpiry:<section>:ExpiresAtUtc` and
`CredentialExpiry:<section>:VerifiedAtUtc`, with the fixed sections
`GrafanaMetrics`, `GrafanaLogs`, `ArchiveReader`, `ArchiveWriter`. Their response
keys are respectively `grafana-metrics`, `grafana-logs`, `archive-reader`,
`archive-writer`. Alphanumeric configuration sections survive the container
shell entrypoint. Dates use exactly
`yyyy-MM-ddTHH:mm:ssZ` in UTC. Empty or invalid values remain Unknown. Other
sections/fields are not projected.

The production Compose API environment maps the optional expiry/verified pairs
from `GOLDSRCOPS_METRICS_*_UTC`, `GOLDSRCOPS_LOGS_*_UTC`,
`GOLDSRCOPS_ARCHIVE_READER_*_UTC`, `GOLDSRCOPS_ARCHIVE_WRITER_*_UTC`, where `*`
is `EXPIRY` or `VERIFIED`. They contain dates only. Update these alongside a
separately accepted rotation, after confirming the provider metadata, then
recreate API through the reviewed deployment flow. Do not put token values,
account identifiers or paths in these fields. Unknown entries need a provider
check, not invented dates or a forced healthy state.

This R1 release affects API/Web and only their existing configuration mapping.
The endpoint is additive; old Web still works with new API and new Web shows
Unknown against an old API. Existing health report, warning catalog, monitoring,
notification delivery, database, game, agent, providers and access stay fixed.
There is no rotation button, email delivery or new credential/permission.
Rollback restores the accepted v2.111 API, v2.113 Web and original deployment
configuration; there is no durable-state migration.
