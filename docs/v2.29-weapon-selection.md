# v2.29 Weapon Selection

Status as of 2026-10-04: the prototype and separate game-host addon package
compile with the pinned toolchain. Focused packaging, install/toggle/rollback,
and isolated two-plugin loading checks passed. The owner reported the earlier
short local menu/respawn test successful. Not installed on the active game host
or released.

## Product Boundary

The v2.28 MP5 profile remains the host baseline. The next experiment adds a
small primary-weapon choice: MP5, AK-47, or M4A1 for either team. A player
opens `/guns` in chat or `guns` in the console. Selection applies only at
the next living spawn and is retained for the current connection, including
team switches. A reconnect or map change resets the selection to MP5.
Closing the menu keeps the previous choice. Menus do not grant weapons or
refill ammunition during a life. There is no automatic menu on every spawn.

The separate AMX Mod X/ReAPI plugin's cvar and sandbox package default to
`goldsrcops_weapons_enabled=0`. The explicit game-host addon target ships its
own enabled configuration. Neither target modifies the telemetry producer,
profile configuration, objective items, pistol, knife, immunity, economy,
round rules, or buy rules. Bots, HLTV, and spectators receive no plugin loadout.
The common choices are an experiment, not a multiplayer-balance claim.

## Implementation Boundary

The prototype uses the existing pinned AMX Mod X `1.10.0.5481` and ReAPI
`5.24.0.300`. It uses a shared menu, a post-spawn hook, primary-slot removal,
item grant, and bounded backpack ammunition. A failed selected-item grant
attempts the MP5 fallback once; failures do not restart services or retry a
host transition. No timers, database, credentials, or new .NET API are needed.

References: [AMX Mod X menu API](https://www.amxmodx.org/api/newmenus/menu_create)
and the [ReAPI native declarations](https://github.com/rehlds/ReAPI/blob/5.24.0.300/reapi/extra/amxmodx/scripting/include/reapi_gamedll.inc).

## Stopped-Game Addon Workflow

`ops/gameserver/weapon-selection-addon.sh` uses the existing persistent workflow
library and fixed host paths. It has four operations: `--install`, `--enable`,
`--disable`, and read-only `--status`. Mutations remain plan-only without
`--apply`. Installation also requires an absolute extracted bundle directory
and its independently reviewed manifest SHA-256:

```bash
bash ./ops/gameserver/weapon-selection-addon.sh --install \
  --bundle /absolute/reviewed-addon/content --manifest-sha256 <reviewed-sha256>
bash ./ops/gameserver/weapon-selection-addon.sh --disable
bash ./ops/gameserver/weapon-selection-addon.sh --enable
```

Apply requires root through the recorded SSH operator, both transition locks,
the verified schema-2 persistent MP5 baseline, an inactive game service, and
existing root-owned AMXX directories with the recorded service group and mode
`0750`. This includes `configs/plugins`; missing or drifted directories are
refused, not silently created. The script never stops, starts, or restarts a
service and never changes its boot policy. The operator must stop the game
before applying and explicitly start it afterwards.

Installation verifies the trusted manifest digest and all three fixed payload
paths, installs only those files as root-owned `0640`, and records their hashes
in an addon receipt. Existing addon paths are never overwritten. The
supplemental loader is installed last. Disabling moves that loader outside
AMXX's config directory, leaving the binary/configuration in place; enabling
restores it. These operations take effect on the next game start. File/hash
drift refuses a toggle. A failed install or toggle restores only its own prior
files/receipt and leaves the game stopped for inspection.

The original `plugins.ini`, `amxx.cfg`, pilot manifest, guards, identity,
queue, and spool are not changed. The pilot bundle's one-plugin payload
allowlist is not widened. The existing boot guard still validates the original
persistent baseline; it does not hash-bind the addon at boot. Addon integrity is
checked by this workflow and its receipt, not by a new boot-time policy. Do not
claim complete addon recovery through the separate persistent rollback; disable
the addon first before changing that baseline.
