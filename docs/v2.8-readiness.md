# GoldSrcOps v2.8 Release Readiness

Review date: 2026-09-13. Status: release candidate accepted in production.
Signed publication, digest-pinned rollout, and the bounded production smoke
passed; digest-preserving stable publication remains pending.

## Scope

The v2.8 product scope is one Server Trends slice integrated in protected
`main` through pull request
[#132](https://github.com/tov-vl/gold-src-ops/pull/132):

- `GET /api/servers/{id}/trends?window=1h|6h|24h|7d` returns one bounded
  aggregate under the existing `Reader` policy.
- Fixed windows produce 12 five-minute, 24 fifteen-minute, 24 hourly, or 28
  six-hour buckets from PostgreSQL-side aggregation.
- Summary reachability and latency are weighted by retained samples; latency
  includes reachable observations only.
- Missing buckets stay `unknown` and do not enter observed percentages or
  averages.
- `/operator/servers/{id}/history` renders separate reachability, latency, and
  reported player/bot tracks while preserving recent observations and incident
  history.
- Static rendering, responsive layouts, and the existing server-side token
  boundary remain in effect.

The candidate baseline also carries forward the v2.7 production-acceptance and
stable-publication records merged after the signed v2.7 application revision.
Those commits are part of the candidate review boundary but do not add another
v2.8 product workflow.

This record freezes the release-candidate scope. Arbitrary trend ranges, raw
snapshot export, public per-server trends, comparison overlays, SLO activation,
incident mutation, lifecycle commands, schema changes, and infrastructure
changes are not part of `v2.8.0-rc.1`.

## Claim Boundary

The target remains one single-node control plane, one Web instance, and one
controlled external game server. Candidate acceptance can show that an
authenticated Reader can inspect bounded aggregates from retained A2S
observations in that reference deployment without disturbing monitoring. It
cannot prove complete retention, service uptime, a latency distribution, high
availability, multi-region resilience, long-term reliability, real-player
adoption, or an achieved SLO.

Public documentation may contain revision identifiers, image digests, workflow
links, sanitized counts, and bounded outcomes. Host and provider identifiers,
addresses, credentials, secret aliases, operator identity, raw database rows,
tokens, incident reasons, probe failure reasons, and owner-only evidence stay
outside Git.

## Compatibility Review

- The trend endpoint and response contract are additive; existing API routes
  and request or response contracts are unchanged.
- No EF Core migration or persistence model change exists in the candidate
  diff. A fresh backup, restore rehearsal, migration timing exercise, and
  previous-runtime schema rehearsal are therefore not routine v2.8 gates.
- PostgreSQL performs one server-scoped, time-bounded aggregate and returns at
  most 28 rows. Raw multi-day snapshots do not cross the API or browser
  boundary.
- The history route remains static server-side rendering behind the existing
  `Reader` policy. Operator access follows the existing role hierarchy, and the
  trend panel exposes no mutation control.
- Ordinary rollback recreates API and Web from the retained v2.7 digests. The
  database and all non-application containers remain unchanged.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.7.0..main` commit and file inventory.
3. Require `Quality Gate`, `Container Smoke`, and `Browser Smoke` on the final
   candidate revision.

### 2. Candidate Publication

1. Create signed annotated tag `v2.8.0-rc.1` at the reviewed `main` revision.
2. Require build-mode publication of both API and Web images from that exact
   revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

### 3. Digest-Pinned Rollout

1. Retain the current v2.7 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, container and
   game-service identities, restart counts, A2S state, incidents, queues, and
   scheduled-backup freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.

### 4. Short Production Smoke

Run one read-only 10-15 minute session and stop on the first unexplained
failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image digests.
2. Verify anonymous routes remain sanitized and the trend API still requires
   authentication.
3. Through an existing authenticated Operator session, which includes Reader
   access, request `1h`, `6h`, `24h`, and `7d` trends for the controlled server.
   Require the fixed 12, 24, 24, and 28 bucket shapes and valid bounded summary
   counts without printing the server identifier or raw observations.
4. Navigate to server history and verify every range renders the separate
   reachability, reachable-latency, and reported population tracks. Missing
   buckets must remain unknown rather than becoming zero or healthy.
5. Confirm the trend panel adds no mutation control and browser content or
   storage contains no bearer token, credential value, secret reference, or
   command payload. If unchanged OIDC makes a fresh Reader-only login
   unnecessary, reuse Reader authorization and concealment evidence from
   Browser Smoke on the exact Web digest and record that substitution
   explicitly.
6. Require the controlled server to remain recently polled and reachable with
   zero bots. Require no unexpected container or game-service restart, newly
   opened incident, pending outbox item, dead letter, or incomplete command.
7. Recheck public health and scheduled-backup freshness at the end.

This short smoke is sufficient for the additive read-only API and Web change.
It is not a new soak, recovery rehearsal, lifecycle acceptance, or SLO claim.
Existing passive monitoring and the independent `API-01` window continue
without user participation.

## Accepted Candidate Evidence

The digest-pinned rollout and bounded production smoke passed on 2026-09-13:

- Public API liveness and readiness, Web liveness, and the Web root returned
  HTTP `200`; anonymous API access remained `401` and the protected Web route
  remained a login redirect.
- API and Web reported `2.8.0-rc.1`, the exact tagged revision, and the exact
  accepted image digests. The migration count and latest migration were
  unchanged.
- All seven control-plane containers remained running. Configured health checks
  were healthy, restart counts matched their baselines, and Caddy, PostgreSQL,
  and all telemetry container identities were unchanged.
- All 11 control-plane samples passed. The single enabled server remained
  online, reachable, and recently polled with zero bots. No unreachable poll,
  newly opened or open incident, pending outbox item, dead letter, or incomplete
  command appeared during the interval.
- Scheduled PostgreSQL backup evidence remained fresh and alert delivery
  remained disabled.
- The game service remained active and boot-disabled with its baseline restart
  count, invocation, and main process unchanged. Exactly one configured UDP
  listener remained owned by the service control group.
- An existing authenticated Operator session rendered `1h`, `6h`, `24h`, and
  `7d` trends with the required 12, 24, 24, and 28 bucket shapes in separate
  reachability, latency, and population tracks. The trend section exposed no
  form or mutation button.
- Browser markup exposed no bearer-token-shaped value, and the browser console
  emitted no warning or error.

A dedicated Reader production login was not repeated. Reader authorization,
mutation-control concealment, responsive layouts, and the server-side token
boundary passed `Browser Smoke` on the same immutable Web image, while
production OIDC configuration and authorization policies were unchanged. This
is an explicit bounded-evidence substitution; it is not evidence of a fresh
Reader-only production session.

Sanitized control-plane, browser, and game-host evidence is retained outside
Git as root-owned mode `0600` regular files. The control-plane interval ran from

recorded 11 successful samples. Game-host continuity ran from

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On candidate startup, health, authorization, trend-contract, query, data
  boundary, or rendering failure, recreate API and Web together from the
  retained v2.7 digests.
- Do not mutate PostgreSQL, monitoring state, RCON state, incident history,
  snapshot history, or durable queues to make the smoke pass.
- A bad or missing availability minute remains bad. Do not pause, reset,
  backfill, or reinterpret `API-01`.
- Store sanitized smoke evidence outside Git as an owner-only regular file.

## Stable Publication Gate

are complete. Stable `v2.8.0` remains pending only on digest-preserving
