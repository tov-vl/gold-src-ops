# v2.121 - A2S polling liveness

## Scope and release boundary

R3 monitoring policy exercise; install only API and the reviewed Prometheus,
Alertmanager and Grafana files. Web, receiver, game/agent, database schema,
credentials, Archive cadence and existing warning state remain unchanged.
The agreed release includes one isolated canary firing/resolved group through
the existing private IRM/email channel, without a new integration or secret.

## Semantics

The existing worker retains its scope, cancellation, query, persistence, delay
and exception handling. Instrumentation records cycle start, completion,
last exception, last successful cycle and duration. A completed empty cycle or
a cycle where every A2S request fails is progress. A repository/worker exception
is a failed cycle; shutdown cancellation does not manufacture a failed result.
The old game-server incident and poll-attempt counters keep their meanings.

The always-initialized bounded gauges expose enabled, process start, observation,
cycle times/duration and numeric state: 0 Unknown, 1 Running, 2 Error, 3 Disabled,
4 Stale. They add no server address, ID, exception text or arbitrary metric tag.
Restart creates new progress; a backward clock is Unknown. The collector's fresh
scrape is independent of cycle completion. Prometheus independently derives
progress age from completion/start timestamps, so even a retained Running state
cannot hide an old cycle. Metadata must be current and coherent for rule evaluation.

The observation budget is max(300, 60 + 2 * (LoopDelaySeconds + BatchSize *
QueryTimeoutSeconds)): 370 seconds at the defaults. It allows sequential query
cost and operational headroom. It is not a hard maximum, database-duration
bound, new cancellation deadline, latency SLO or reason to retry a pass. A budget
outside 300..86400 seconds is unavailable to policy; it is not silently capped.
A startup with no completed pass stays Unknown until that budget expires.

Exactly one current enabled source is required for production. Disabled
HTTP-only replicas cannot hide missing or failed active polling; multiple
active sources are unavailable rather than merged. A disabled-only deployment
shows Disabled but cannot establish an active poller, so MonitorUnavailable
still warns for this single-active-poller production contract.

Three held warning rules use fixed names and private safe notification routing:

- PollingMonitorUnavailable: no current, valid, unique enabled source for 5m.
- PollingCycleStalled: progress age exceeds the observation budget for 2m.
- PollingCycleFailed: State=Error for 2m while progress remains recent; a new successful cycle clears it.

The separate Grafana dashboard shows state, active source count, completion age,
budget and last duration. Missing values remain Unknown. API HTTP health, A2S
server availability and polling progress remain different observations.

## First checks

Preserve current API identity, metadata, cycle timestamps and bounded logs.
Check source freshness, enabled configuration, duplicate process observations,
query/batch budget and database availability before a separately reviewed
recovery. Do not reset incidents, restart the game, replay a poll or change
thresholds to hide the warning. No public/Reader or Operator Web contract grows.

## Verification and rollout readiness

Eight focused worker/clock cases passed, including empty passes, all A2S
timeouts, repository exceptions, shutdown, restart and clock handling. Real
promtool passed 21 lifecycle scenarios. The local Alertmanager wire rehearsal
passed 376 routing inputs and 41 allowed firing/resolved pairs, including retry,
deduplication, reload, restart and privacy checks. The complete audit-enabled
local quality gate passed: 1,607 tests, with 65 opt-in browser cases left to the
required hosted browser job. Final focused tests passed after inspection fixes.
Scoped InspectCode completed with zero errors/warnings and three reviewed notes:
the existing broad worker catch intentionally keeps polling alive, its existing
constructor remains explicit, and an unrelated DI nesting suggestion is left
unchanged. Required PR/main CI and immutable candidate publication
remain external gates.
Production acceptance must independently verify source/digest, fresh progressing
cycle metrics, the unique active source, all three rules, Grafana provisioning,
existing monitoring/worker continuity and a separate synthetic IRM group.
Stable promotion must reuse the accepted digests without rebuild, followed by
one evidence PR. No live hang or game-server failure injection is required.

Rollback restores the prior API digest and exact monitoring file states,
including removal of only newly introduced owned files. Existing Alertmanager
state and all volumes are retained; no database restore or ledger change.
If a new polling notification group still needs resolution, retain the compatible
Alertmanager route and its state until delivery is reconciled. Do not remove
that route or discard notification history to make rollback appear complete;
that changed rollback boundary requires a separate decision.
