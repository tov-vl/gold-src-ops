# v2.106 - Independent monitoring heartbeat

## Scope and boundary

This R3 operations slice adds a heartbeat from the existing private Prometheus
through the existing private Alertmanager to Grafana Cloud IRM. IRM, outside the
control-plane host, detects missing heartbeats and escalates through the owner's
existing email chain. It does not depend on the failed host to create that alert.

The repository contains source configuration and a local rehearsal. Production
activation, provider configuration and protected endpoint transport require a
separate owner decision. No target rollout or real heartbeat-loss acceptance
is claimed by the implementation alone.

The game host, agent, addon, queues, backups, API, Web, database, identities,
public ports and firewall are outside this slice. There is no direct cron
pinger, new VM or additional monitoring service. Only Alertmanager needs one
reviewed recreation with its existing image and notification-state volume to
mount the additional secret; Prometheus receives a configuration reload.

## Signal and timing

The fixed rule MonitoringHeartbeat evaluates vector(1) every ordinary
15-second evaluation. It carries exactly component=monitoring-pipeline and
severity=none, with no pending period or keep-firing extension. Prometheus
forwards only that exact tuple in addition to the existing 17 warning tuples,
then strips all other labels.

Alertmanager routes this tuple only to monitoring-heartbeat. Group wait is
zero; group and repeat intervals are both one minute. The private endpoint is
loaded from a read-only secret file. The request body contains only constant
project, environment and heartbeat identifiers. Source annotations, generator
URLs, host labels and source data are excluded. Redirects remain disabled and
the request timeout is ten seconds. Resolved alerts do not send heartbeat
requests: expiry of the source must allow the external timeout to elapse.

Configure the production IRM timeout to five minutes. This is a receiver
timeout after the last accepted request, not a five-minute detection SLA from
every failure. If Alertmanager or the entire host stops, IRM can detect absence
without that host. If only Prometheus stops, Alertmanager can repeat the last
firing alert until its explicit endsAt expires. That retained-alert tail and
receiver/escalation scheduling add delay. A healthy heartbeat establishes only
the rule-evaluation/notification/egress/IRM path. It does not prove Collector,
Grafana, application, game or backup health, successful delivery of every other
warning, or independent availability of Grafana Cloud and email.

The official [IRM Alertmanager guide](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/integrations/alert-sources/alertmanager/)
documents the heartbeat endpoint and missing-signal detection. The
[integration guide](https://grafana.com/docs/grafana-cloud/observe-and-act/respond-to-incidents/integrations/configure-integrations/)
documents heartbeat configuration. Native
[Alertmanager timing](https://prometheus.io/docs/alerting/latest/configuration/)
requires the repeat interval to align with the group interval.

## Provider and secret boundary

Use heartbeat settings on the existing Alertmanager integration and preserve
its owner route, grouping, templates and existing warning history. Use a
separate test-only integration for the deliberate missing-heartbeat trial.
Never stop the production heartbeat as a delivery test.

Both endpoints are secrets. Keep them outside Git and command arguments,
transmit only through an approved hidden local prompt and existing protected
SSH, and never record their values in logs, screenshots, receipts or exceptions.
No new API token, scope, user or recipient is required by this design.
Changing integration settings and storing the new endpoint are new provider/
secret operations, not implicit in earlier resource-monitor permission.

## R3 rollout and rollback

Before activation, record exact old configuration bytes and metadata,
container/image/network/volume identities, existing rule definitions,
dashboards, active warning histories and worker flags. Verify the notification
volume is healthy and retained. Validate candidate Compose, Prometheus and
Alertmanager configuration using the installed pinned versions.

1. Stage the verified immutable five-file package and the approved heartbeat
   secret. Preserve exact rollback inputs and claim the operation once.
2. Apply only the reviewed Alertmanager Compose/env/config changes. Recreate
   only Alertmanager with the existing digest and state volume; require ready.
3. Install the new rule and additive Prometheus relabel/rule-file change using
   the mounted configuration's existing inode, then reload Prometheus.
4. Require the rule firing, repeated accepted heartbeat requests, healthy IRM
   heartbeat, and preserved existing warning/routing/runtime identities.
5. On the separate canary integration, establish receipt, stop only the
   isolated sender, verify an automatically generated missed-heartbeat group
   and provider notification, then resume and verify source-based resolution.
6. Disable the test heartbeat after the trial and retain its history. An
   endpoint HTTP success, a manually resolved group, provider email sending
   and owner inbox receipt are different evidence.

Rollback first resets the newly enabled production heartbeat in IRM so that
intentional sender removal does not generate an ongoing false outage. Restore
the exact old Prometheus configuration, reload it, and remove only the
unchanged owned rule. Restore the old Alertmanager config/Compose/env and
recreate only Alertmanager, retaining its state volume. Do not delete provider
history, reset old service failures, replay old alerts or change the game.
If the provider cannot be reached, or any state/identity differs, stop and
reconcile; do not claim a clean rollback or repeat an uncertain action.

## Verification and release gates

The local pinned-process rehearsal exercises actual Prometheus relabeling and
Alertmanager matching, one-minute production timing with fixture-only
acceleration, repeated delivery, transient receiver rejection, constant-body
privacy, existing owner routing, source-rule removal without resolved pings,
redirect refusal, Alertmanager loss and restart, and Prometheus loss with
retained-alert expiry and recovery. All requests stay on disposable local
Docker networks; no provider URL is used. This is not provider acceptance.

The existing full owner-notification matrix and private telemetry rehearsal
remain separate regression checks. No C# changes are needed; an unchanged full
local .NET gate need not duplicate required CI.

Local verification passed on 2026-11-05: the pinned watchdog rehearsal,
17 existing firing/resolved notification paths, 106 routing combinations,
and the complete private Collector/Prometheus/Grafana rehearsal with all six
existing policy suites. Documentation links and source syntax checks passed.
Provider inspection confirmed heartbeat settings are available; it did not
enable or change them. Required CI and immutable publication remain pending.

Build clean reviewed source with tools/release/build-monitoring-watchdog.ps1.
The manifest binds the exact source revision and five file hashes. Candidate
monitoring-watchdog-v2.106.0-rc.1 and stable monitoring-watchdog-v2.106.0 must
reuse the accepted bytes without rebuilding. Global application latest and
addon 0.39.0 remain unchanged. Publication, target acceptance, actual IRM
missing/recovery behavior, and evidence PR closure are separate pending gates.
