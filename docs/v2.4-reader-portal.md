## Scope

An authenticated `Reader` or `Operator` can:

- sign in and sign out through the external OIDC provider;
- list controlled servers and their enabled state;
- inspect the latest status, A2S reachability, map, players, latency, last
  success, and consecutive failures for one server;
- triage open availability incidents across the controlled fleet;
- inspect up to 100 recent A2S observations and 50 recent availability
  incidents for one server, newest first;
- inspect up to 100 recent audited command executions for one server without
  rendering command payloads;
- inspect cursor-paged dead letters and their delivery metadata, failure
  summary, replay count, and newer-event ordering warning without rendering the
  raw event payload.

The portal has no mutation controls. Server registration, configuration, RCON
command submission, dead-letter replay, and all other Operator actions remain
API-only.

## Security Boundary

GoldSrcOps.Web acts as a confidential OIDC client and server-side BFF. It uses
authorization code with PKCE, applies the `Reader` policy to the ID-token
principal, and forwards the access token only on server-side calls to the API.
The browser receives an HTTP-only opaque session cookie and never receives the
API access token.

The identity provider must place the configured namespaced role claim in both
the ID token and access token. `Reader` and `Operator` can render the portal;
the API independently validates the access-token issuer, audience, lifetime,
and role for every request.

The process-local ticket store is bounded to 1,024 sessions. It deliberately
invalidates sessions on restart and supports only the current single Web
instance. A shared encrypted ticket store is a prerequisite for horizontal Web
scaling, not for this MVP slice.

## Production Inputs

The OIDC provider must register:

- application type: regular/confidential Web application;
- callback URL: `https://goldsrcops.com/signin-oidc`;
- logout callback URL: `https://goldsrcops.com/signout-callback-oidc`;
- authorization-code grant with PKCE;
- no public sign-up beyond the existing operator-managed account policy.

Compose maps only three Web-specific secrets: the OIDC client secret, a PKCS #12
Data Protection certificate, and its password. The key ring is stored in the
dedicated UID `1654`, mode `0700` host directory. Direct secret configuration is
accepted only in Development.

expiry, concurrent capacity enforcement and removal, production secret
constraints, mandatory production key persistence, bearer forwarding,
disabled-authentication fail-closed behavior, the Reader/Operator/no-role
policy matrix, and authenticated rendering of the protected Reader routes. The
production container smoke additionally verifies that authentication-disabled
images expose neither the login endpoint nor protected content.

The second slice expands the rendering matrix to the server list, current
status, open incidents, and per-server history. API coverage verifies the
incident-history limit and reverse-chronological query, while application tests
verify its default and defensive maximum. The Kestrel browser fixture now loads
the production static-web-assets manifest and fails if no stylesheet is active.

The third slice adds deterministic API-client tests for command history and
dead-letter cursor handling, authenticated rendering and not-found coverage,
and assertions that command and raw event payload sentinels never enter the
response body or rendered DOM. Its desktop and mobile layouts were reviewed at
`1280x800` and `390x844`; both passed an automated horizontal-overflow check.

The dedicated Kestrel-backed Playwright check exercises the complete browser
boundary with recognizable access-token and ID-token sentinels held in the
server-side authentication ticket. It verifies the authenticated server,
incident, command-history, and dead-letter responses plus the rendered DOM
contain neither sentinel, JWT-shaped value, token-named field, nor deliberately
recognizable payload sentinel; local and session storage remain empty; and the
browser receives exactly one opaque `__Host-GoldSrcOps.Web` cookie with
`HttpOnly`, `Secure`, `SameSite=Lax`, and root-path attributes. The sign-in
fixture exists only in the test host and does not contact the identity provider
or production runtime.
