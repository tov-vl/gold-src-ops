# GoldSrcOps v2.6 Release Readiness

Review date: 2026-09-12. Status: release candidate accepted in production;
publication, digest-pinned rollout, and the bounded production smoke passed.
Digest-preserving stable publication remains pending.

## Scope

The v2.6 product scope is one Fleet Triage slice integrated in protected
`main` through pull request
[#124](https://github.com/tov-vl/gold-src-ops/pull/124):

- `GET /api/dashboard/fleet` returns one Reader-authorized projection with
  aggregate counts, current state, latest bot count, open-incident count, and
  freshness derived from each server polling interval.
- `/operator/servers` consumes that one projection and provides deterministic
  attention ordering, state tabs, search, and sorting in static server-side
  rendering.
- Open incidents remain actionable even when monitoring is paused.
- The read contract omits notes, credentials, failure reasons, incident
  details, command payloads, and other mutation or secret-bearing data.

The candidate baseline also carries forward the v2.5 publication and
acceptance records merged after the signed v2.5 application revision, plus the
restore-compatibility tooling used by that acceptance. These commits are part
of the candidate review boundary but do not add another v2.6 product workflow.

This record freezes the release-candidate scope. Fleet mutation, bulk actions,
pagination, cross-fleet incident workflows, new lifecycle commands, schema
changes, and infrastructure changes are not part of `v2.6.0-rc.1`.

## Claim Boundary

The target remains one single-node control plane, one Web instance, and one
controlled external game server. Candidate acceptance can show that Fleet
Triage works against that reference deployment without disturbing monitoring.
It cannot prove high availability, multi-region resilience, long-term
reliability, real-player adoption, or an achieved SLO.

Public documentation may contain revision identifiers, image digests,
workflow links, sanitized counts, and bounded outcomes. Host and provider
identifiers, addresses, credentials, secret aliases, operator identity, raw
database rows, tokens, and owner-only evidence stay outside Git.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.5.0..main` commit and file inventory.
3. Require `Quality Gate`, `Container Smoke`, and `Browser Smoke` on the final
   candidate revision.

### 2. Candidate Publication

1. Create signed annotated tag `v2.6.0-rc.1` at the reviewed `main` revision.
2. Require build-mode publication of both API and Web images from that exact
   revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

### 3. Digest-Pinned Rollout

1. Retain the current v2.5 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, container and
   game-service identities, restart counts, A2S state, incidents, queues, and
   scheduled-backup freshness.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.

### 4. Short Production Smoke

Run one read-only 10-15 minute session and stop on the first unexplained
failure:

1. Require public API liveness, API readiness, and Web health to return HTTP
   `200`, with candidate version, revision, and exact image digests.
2. Verify anonymous routes remain sanitized and protected routes still require
   authentication.
3. Verify Reader and Operator sessions can render Fleet Triage. Exercise state
   tabs, search, and sorting without submitting a mutation.
4. Confirm Reader receives no mutation controls and browser content or storage
   contains no bearer token, credential value, secret reference, command
   payload, or incident detail.
5. Require the controlled server to remain recently polled and reachable with
   zero bots. Do not manufacture paused, offline, stale, or incident states for
   release evidence.
6. Require no unexpected container or game-service restart, no open incident,
   no pending outbox item, no dead letter, and no incomplete command throughout
   the observation.
7. Recheck public health and scheduled-backup freshness at the end.

This short smoke is sufficient for the additive read-only backend and UI
change. It is not a new soak, recovery rehearsal, lifecycle acceptance, or SLO
claim. Existing passive monitoring and the independent `API-01` window continue
without user participation.

## Accepted Candidate Evidence

The digest-pinned rollout and bounded production smoke passed on 2026-09-12:

- Public API liveness and readiness, Web liveness, and the Web root returned
  HTTP `200`; anonymous API access remained `401` and the protected Web route
  remained a login redirect.
- API and Web reported `2.6.0-rc.1`, the exact tagged revision, and the exact
  accepted image digests. The migration count and latest migration were
  unchanged.
- All seven control-plane containers remained running with zero restarts.
  Caddy, PostgreSQL, and all telemetry container identities were unchanged.
- The single enabled server remained online, reachable, and recently polled
  with zero bots. No unreachable poll, newly opened incident, pending outbox
  item, dead letter, or incomplete command appeared during the interval.
- Scheduled PostgreSQL backup evidence remained fresh and alert delivery
  remained disabled.
- The game service remained active and boot-disabled with its baseline restart
  count, invocation, and main process unchanged. Exactly one configured UDP
  listener remained owned by the service control group.
- An authenticated Operator session rendered Fleet Triage and passed Online,
  empty Attention, search, and name-sort checks without a mutation. Browser
  content exposed no readable cookie, bearer-token-shaped value, secret
  reference, password field, or non-logout POST form, and emitted no console
  warning or error.

A dedicated Reader production login was not repeated. Reader rendering and
mutation-control concealment passed `Browser Smoke` on the same immutable Web
image, while the production OIDC configuration and authorization policies were
unchanged from their previously accepted live matrix. This is an explicit
bounded-evidence substitution that avoids another interactive login ceremony;
it is not evidence of a fresh Reader-only production session.

Sanitized control-plane and game-host evidence is retained outside Git as
root-owned mode `0600` regular files. The control-plane interval ran from
`2026-09-12T16:13:29.913270Z` through `2026-09-12T16:24:07.798935Z`.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On candidate startup, health, OIDC, data-boundary, or rendering failure,
  recreate API and Web together from the retained v2.5 digests.
- Do not mutate the database, lifecycle state, RCON state, incident history, or
  durable queues to make the smoke pass.
- A bad or missing availability minute remains bad. Do not pause, reset,
  backfill, or reinterpret `API-01`.
- Store sanitized smoke evidence outside Git as an owner-only regular file.

## Stable Publication Gate

The candidate identity, rollout, smoke, and retained-production gates are
complete. Stable `v2.6.0` now requires only a signed stable tag that promotes
the exact accepted API and Web digests without rebuilding them, followed by
published-image smoke against both stable references.
