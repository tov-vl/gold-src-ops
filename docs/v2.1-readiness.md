## Migration And Rollout Evidence

- Both replay migrations are new and additive; no already-applied v2.0
  migration was edited.
- Existing outbox rows receive a default replay count, while legacy dead letters
  retain a nullable dead-letter timestamp.
- The audit table intentionally has no cascading foreign key to the outbox row,
  so processed-row cleanup cannot erase accepted replay history.
- Normal partial-index builds and initial constraint validation can block
  outbox writes. Inspect table size and use a serialized low-traffic migration
  action before starting v2.1 instances.
- Rolling the application back to v2.0.0 leaves the additive replay schema
  unused. Do not down-migrate while retained messages or replay audit matter.

## Accepted Boundaries

- Replay preserves at-least-once delivery rather than promising exactly once.
  Receivers must deduplicate by the stable event ID.
- `202 Accepted` proves the audit and requeue transaction committed; it does not
  prove external webhook delivery.
- An ambiguous client result must be resolved through durable lookup and a retry
  with the original key, never a newly generated key.
- One reviewed event is replayed per request. Bulk, scheduled, and automatic
  replay remain deferred.
- A newer processed event is surfaced as a warning because only the operator can
  decide whether the receiver gap justifies an out-of-order replay.
- Replay reasons are durable operational audit data. They are not exposed in
  metrics or logs and must not contain secrets or unrelated personal data.
- Replay audit has no automatic retention policy yet.
- Target-environment TLS, identity-provider metadata, database TLS, secret
  injection, receiver capacity, and backup restoration require deployment
  evidence beyond the container smoke.
