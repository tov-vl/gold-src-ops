# v2.108 - Process-bound client renderer evidence

## Scope and limits

The Windows client runner can retain an engine-reported OpenGL identity from
the actual owned CS process. A launch flag and Windows GPU inventory are not
renderer evidence. The implementation adds no broker command, credentials,
permission, desktop access, production rollout or gameplay change. The runner
remains revision 16 with the same nine files; only Worker and Diagnostics change.

The additive `rendererEvidence` object has schema 1. `identified` requires a
fresh, request-specific `gl_dump` frame, a matching process PID/start time,
session, owner, executable and command line, and verified cleanup. Unsupported,
missing, stale or ambiguous output remains `unconfirmed`. An identified report
describes what the engine reports; it does not attest hardware acceleration,
driver correctness, performance or all future launches.

The historical `rendererVerified=false` field remains false. Old results and
review receipts are not rewritten. Existing campaign validation and visual
acceptance are independent of the new renderer receipt.

## Collection and review

Before launch the worker checks four fixed console-log locations under the game
root and its `cstrike` directory. An existing file, directory or linked path
disables the probe without reading or changing that log. No existing console
logging configuration is edited. When the paths are absent, the worker adds
the constant `-condebug` option and wraps `gl_dump` in unique request markers
in its existing create-only CFG. The desktop helper verifies the same exact
generated program and constant launch option.

While the owned game is alive, the worker reads at most 4 MiB from exactly one
new log. Exactly one ordered marker pair and exactly one Vendor, Renderer and
Version are required. The retained frame is bounded to 16 KiB of ASCII; only
its Base64 encoding, SHA-256, size, projected identity and process/time bindings
enter the result. Unrelated startup/console output and log paths are excluded.

After the owned process is closed, cleanup checks the fixed path, original file
creation time and captured markers again. A missing proof, replacement, multiple
logs or an oversized log prevents deletion and produces uncertain cleanup.
Existing cleanup and no-automatic-retry rules still apply.

Run the read-only local reviewer against a collected terminal result:

```powershell
./tools/client-lab/Test-LabRenderer.ps1 -ResultPath <collected-result.json> -JobId <request-id> -OutputPath <new-private-receipt.json>
```

It independently reparses the frame, verifies its hash and projection, process
and observation-time binding, successful capture status and cleanup. A new
create-only receipt binds to the exact input bytes. It cannot set visual
acceptance or repair old results. Raw client evidence remains in the private
operator record.

## Delivery and rollback boundary

R2 applies to the signed client-worker update. Freeze the reviewed source,
fresh updater sequence and all nine predecessor hashes. Preserve the accepted
weapons baselines and unchanged seven files; stage one signed update through
the existing updater. Do not change its trust engine, policy, keys or access.
Retain the predecessor bytes for a distinct signed rollback if acceptance fails.
An uncertain update or game dispatch is reconciled by its existing ID, never
resent. No application image, addon, cloud VM or production service changes.

One bounded native trial must independently prove the renderer receipt, retained
BMP evidence, process/config/log cleanup, exact installed hashes and unchanged
access scope. A stale Windows session binding is a preflight blocker, not
permission to weaken ownership checks or silently rebind the trusted policy.
