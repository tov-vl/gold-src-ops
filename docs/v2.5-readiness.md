# GoldSrcOps v2.5 Release Readiness

Review date: 2026-09-11. Status: release-candidate preparation; repository
implementation is complete, while candidate publication and production
verification remain pending.

## Scope

The v2.5 product scope contains the six guarded lifecycle slices already
integrated in protected `main`:

1. Monitoring pause and resume.
2. Idempotent paused server registration.
3. Paused non-secret server editing with optimistic concurrency.
4. RCON credential binding and rotation by validated deployment alias.
5. Fixed server restart.
6. Strictly validated map change.

The candidate repository baseline also includes post-v2.4 operational
maintenance already integrated in `main`: WireGuard-scoped SSH preflight
hardening, availability shadow-audit tooling and policy alignment, and v2.4
release and `API-01` evidence updates. These carried-forward changes do not add
another v2.5 product workflow, but every commit remains inside the candidate
review and verification boundary.

This readiness record freezes that scope. Raw RCON, bulk operations, server
deletion, secret-value management, multi-node execution, and additional UI
features are not pulled into `v2.5.0-rc.1`.

## Claim Boundary

The target remains one single-node control plane, one controlled external game
server, and one Web instance. Candidate acceptance can prove the guarded
workflows against that reference environment. It cannot prove high
availability, multi-region resilience, long-term reliability, real-player
adoption, or an achieved SLO.

Public documentation may contain revision identifiers, image digests, workflow
links, sanitized counts, and bounded outcomes. Host and provider identifiers,
addresses, credentials, secret aliases, operator identity, raw request or
command payloads, database rows, and owner-only evidence stay outside Git.

## Migration SQL Review

The three v2.5 migrations were scripted locally in order with EF Core 10.0.7
against the PostgreSQL 16 deployment baseline. The generated SQL:

- adds two nullable registration-idempotency columns and a unique index to
  `servers`;
- adds `Revision bigint NOT NULL DEFAULT 1` to `servers` and
  `server_credentials`;
- renames the existing server-credential uniqueness index without changing its
  indexed columns; and
- records each migration in its own transaction.

There is no explicit row-by-row backfill. PostgreSQL 16 can apply the constant
revision defaults without a heap rewrite, but each `ALTER TABLE` still needs a
brief exclusive metadata lock. The non-concurrent unique-index build blocks
writes to `servers` while it runs. Production migration therefore remains a
serialized maintenance action, and the isolated restore rehearsal must measure
its actual duration on a fresh production backup.

The schema changes are additive for the previous v2.4 runtime. Ordinary
application rollback retains the migrated schema; running the down migrations
would remove v2.5 data and is not the normal rollback path. Previous-runtime
startup against the migrated rehearsal database remains a required empirical
check.

## Rollout Sequence

The production evidence must preserve this order.

### 1. Repository Closure

1. Inventory the exact diff against stable `v2.4.0`. Classify the
   carried-forward operational and evidence changes separately from the six
   declared lifecycle slices, and reject any undeclared application behavior.
2. Inspect generated migration SQL for table rewrites, blocking index work,
   defaults, and rollback compatibility.
3. Pass formatting, build, unit and PostgreSQL integration tests, browser tests,
   NuGet audit, production Compose validation, and API/Web container smoke.
4. Merge through protected `main` before creating the signed candidate tag.

### 2. Candidate Publication

1. Create signed annotated tag `v2.5.0-rc.1` at the reviewed `main` revision.
2. Require build-mode publication of both API and Web images from that exact
   revision.
3. Record both immutable digests and verify OCI revision metadata plus the
   published-image smoke jobs.
4. Do not create a mutable alias or stable release at this stage.

### 3. Deployment Prerequisites

1. Retain the current v2.4 API and Web digests in owner-only rollback
   configuration.
2. Capture sanitized pre-rollout continuity: public health, container and game
   service identities, restart counts, A2S state, incidents, queues, and backup
   freshness.
3. Create a fresh encrypted off-host PostgreSQL backup and run a full repository
   check.
4. Restore into disposable network-isolated PostgreSQL, apply the migration
   bundle from the candidate API image, verify the already-up-to-date path, and
   start the previous v2.4 runtime against the migrated schema.
5. Run host and production preflight against the candidate digests. A failed or
   interrupted migration blocks runtime rollout.

### 4. Digest-Pinned Rollout

1. Apply the candidate migration bundle as the serialized one-shot operations
   action.
2. Recreate only API and Web with the verified candidate digests. Keep Caddy,
   PostgreSQL, telemetry, and the game host unchanged.
3. Require public liveness and readiness, Web health, correct release metadata,
   OIDC metadata, and previous rollback references before continuing.
4. Verify zero unexpected container restarts, a healthy controlled server, and
   no new incident, pending outbox message, dead letter, or incomplete command.

### 5. Live Acceptance

Run the stages below serially. Stop on the first unexplained failure or uncertain
mutation outcome.

#### Stage A: Read-Only Boundaries

- Confirm anonymous public pages remain sanitized and protected routes require
  authentication.
- Confirm Reader and Operator sessions can inspect the inventory, status,
  settings, credential metadata, monitoring state, and command readiness.
- Confirm Reader receives no mutation forms or submission endpoints, while a
  missing-role identity fails closed.
- Confirm protected browser responses and storage contain no bearer token,
  secret, secret reference, or command payload.
- Open every v2.5 Operator review flow without submitting it, then verify that
  durable counts remain unchanged.

#### Stage B: Reversible State

- Require the controlled server to be online with zero players, zero bots, no
  open incident, and no `Pending` or `Running` command.
- Pause monitoring through one confirmed Operator action. Verify the server
  revision advances and scheduled polling stops without manufacturing an
  availability incident.
- While paused, verify the settings and credential review pages use the freshly
  loaded revisions. Do not change endpoint metadata merely to produce release
  evidence.
- When the existing deployment alias is independently available, rebind that
  same alias once and verify only sanitized credential metadata and revision
  changes. Skip the write rather than introduce a temporary secret alias.
- Resume monitoring through a new one-time confirmation and require at least
  three subsequent successful scheduled polls.

Do not submit live registration for a disposable endpoint. The route,
authorization, review, and browser boundary are checked in production; the
idempotent write and concurrency behavior remain covered by PostgreSQL-backed
tests until a real second server is intentionally onboarded or a retirement
workflow exists.

#### Stage C: Disruptive Commands

- Reconfirm zero players, zero bots, empty incomplete-command state, healthy
  A2S, and a valid RCON binding before each command.
- Queue one fixed restart, observe one durable terminal result, and require A2S
  recovery plus at least three healthy scheduled polls. Do not retry an
  uncertain result.
- Record the current map, choose a known installed map that passes the strict
  allowlist, queue one map change, and require one durable terminal result plus
  A2S recovery. Restore the original map only as a separate confirmed action.
- After both checks, require no unexpected service replacement or container
  restart, no open incident, no pending outbox work, no dead letter, no
  incomplete command, and a fresh scheduled backup marker.

This is one bounded acceptance session, not a new multi-day soak. API-01
continues to provide independent forward-looking availability evidence.

## Failure And Rollback Rules

- Never start runtime after a failed or interrupted migration action.
- Roll back API and Web together to the retained v2.4 digests when candidate
  startup, health, OIDC, or read-boundary checks fail.
- Keep the additive v2.5 schema during ordinary application rollback. Use a
  database restore only after a diagnosed migration or data-integrity failure.
- Never repeat an uncertain registration, update, credential, restart, or map
  mutation automatically. Reload current state and durable history first.
- A failed disruptive command blocks stable v2.5 publication but does not
  rewrite prior v2.4 evidence or the API-01 target.
- A rollout-time bad or missing primary availability minute remains bad. Do not
  pause, reset, or backfill the prospective API-01 window.

## Stable Publication Gate

Stable `v2.5.0` may be proposed only when:

1. The readiness matrix contains evidence for every required candidate gate or
   an explicit accepted deferral that narrows the claim.
2. The candidate has passed the bounded production acceptance session and the
   reference environment is healthy afterward.
3. The signed stable tag points to the accepted candidate revision and promotes
   the exact verified API and Web digests without rebuilding them.
4. Published-image verification passes before the GitHub Release is published.

The API-01 terminal review is a parallel post-release obligation and is not a
reason to reinterpret or extend this feature gate.
