## Bounded production acceptance

The existing game coordinator checks status and wire v1 only. The existing
production browser helper is exact-only. Neither is evidence for contains.
Use the following separate, explicit v2 acceptance after installation; no new
production fixture records or synthetic player data are inserted.

- API budget: at most eight search POSTs in 120 seconds, sequentially. Leave at
  least eleven seconds after the coordinator lookup before the cold API check. Use one
  existing saved name in memory. On the fresh API instance, check a legacy exact
  request, then an immediate contains request with the same valid query for busy.
  Wait the advertised delay plus a small margin, then explicitly submit contains.
  Require real matching names, at most ten rows and a valid hasMore flag; an empty
  result for a known matching name fails. Recheck exact from its own cache. Check
  short contains and an unknown mode as invalid. After admission expires, check
  one generated absent-name contains result. Remaining budget is not permission
  to retry an unexplained failure. All responses retain no-store and no identities.
- Browser budget: at most fourteen search POSTs and 256 HTTP requests in 180
  seconds after launch, with per-operation deadlines. RU/EN each check exact and
  contains, keyboard submission, selected-mode preservation during ranking refresh,
  one natural busy countdown, early Enter blocking, mode switching without timer
  reset, no automatic POST and one manual retry. If the first generated busy probe
  is fresh because the prior result was cached, allow only one additional busy
  probe. Also check both modes in RU/EN without JavaScript. Keep the existing
  320/390/1440 and 200% text checks in the same bounded run.
- All traffic stays on the reviewed origins; browser code must not call the API,
  put names in URLs/storage or follow redirects. Keep live names and raw bodies
  in memory only; retain only sanitized counts/results. If live names cannot
  supply a valid three-scalar partial query, record that acceptance gap and stop
  promotion rather than manufacturing durable records.
- Capture Web metrics before/after the bounded submissions, waiting for the
  existing 60-second export and 15-second scrape/evaluation cadence (at most 90
  seconds for visibility). Correlate the new instance's success/busy/failure
  counts with actual requests, not aggregate predecessor series or extrapolated
  recording-rule increases. Require healthy search rules and no unexplained
  failure/warning. No rule, label, dashboard or scrape-policy changes are planned.
