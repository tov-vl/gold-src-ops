# v2.105 - Game-host RAM and CPU observation

## Scope and meaning

This R3 operations slice adds passive whole-host RAM, swap and sampled aggregate
CPU facts. It reads only the fixed /proc/meminfo file and first aggregate CPU
line in /proc/stat. No process inventory, environment, game/player files, queue,
host identity or arbitrary path is read or returned. It performs no writes,
load generation, swap configuration, cleanup or game/agent restart.

RAM uses MemAvailable, the kernel's estimate of memory usable without swapping,
and MemTotal. Missing MemAvailable is unavailable rather than a MemFree fallback.
Swap used is SwapTotal minus SwapFree; zero total means no configured swap,
not a failed observation. These are host estimates, not process RSS, memory
pressure stall information, container limits, an OOM detector or an OOM forecast.
See the primary [Linux proc documentation](https://docs.kernel.org/filesystems/proc.html).

CPU compares two aggregate eight-counter samples separated by one second.
Busy work sums user, nice, system, irq and softirq deltas; its denominator also
includes idle, iowait and steal. Stolen hypervisor time is shown separately.
Guest/guest_nice are not added again. Every included counter must be
nondecreasing, the total delta positive and monotonic elapsed time 0.75-3
seconds. Otherwise only CPU becomes unavailable. In particular, a decreasing
iowait counter is not clamped into a healthy reading. No counter state survives
the invocation. The result is an approximately one-second sample once a minute,
not a continuous minute average, per-core saturation, game FPS or latency.
Steal depends on the hypervisor's reported accounting.

## Contract and collection

The single new restricted command resource-status takes no arguments and returns
schema version 1, observedAtUtc and two independent groups: memory and cpu.
Unavailable groups contain only available=false. Valid memory has bounded
integer byte totals/availability and swap totals/free values. Valid CPU has
bounded numeric busyRatio, stealRatio and sampleSeconds. Combined work/steal
cannot exceed one except floating-point rounding tolerance.

The strict decoder rejects extra/private fields, duplicate JSON keys, booleans
as numbers, negative/nonfinite values, inconsistent capacities, oversized JSON,
missing groups and invalid/stale/future timestamps. Source age must be at most
30 seconds, with at most five seconds of clock skew into the future. Only fixed
numeric metrics cross SSH; no per-host/per-process labels are introduced.

A separate one-minute timer uses the existing pinned SSH identity/config and
private OTLP endpoint. It has one SSH attempt, no automatic retry, process-group
cancellation, an eight-second source alarm and 40-second service deadline.
It publishes observation success and collector/source timestamps under
goldsrcops_game_host_resource_, service goldsrcops-game-host-resource-monitor.
A failed envelope exports only failure and collector time. Partial failure
exports availability and preserves the other valid group's observations.

The existing agent monitor and storage monitor remain independent, with frozen
transport dependencies inside this immutable package. New source roots,
systemd units, dashboard and rollout claims are separate. Existing backup,
agent, storage, queue, gameplay and application contracts remain unchanged.

## Dashboard and warning policy

The private dashboard goldsrcops-game-host-resources displays RAM total,
available bytes/ratio, swap used/total, executed CPU work, steal and sample
duration. Current queries require successful collection and both timestamps
between zero and 180 seconds old, plus the corresponding group availability.
Old Collector values after failure are masked rather than presented as current.
RAM and CPU validity are independent.

| Warning | Condition held for five minutes |
| --- | --- |
| GameHostResourceMonitorUnavailable | No fresh, nonfuture collector heartbeat |
| GameHostResourceObservationInvalid | Live collector but invalid/old source or either unavailable/missing group |
| GameHostMemoryLow | Valid MemAvailable below 10% of total or below 256 MiB |

Exact memory thresholds are healthy; zero available RAM is low. A CPU failure
does not suppress a valid low-memory warning. Invalid memory does suppress
retained low-memory values. Swap usage and CPU/steal are observational only:
no alert thresholds or baseline claims are introduced for them.

Prometheus and Alertmanager allow only the three exact alert/component/severity
tuples, with component game-host-resources and severity warning. Existing 14
agent/backup/storage warning tuples and their histories are preserved. New
warnings use the existing IRM/email secret and sanitized name/state/time/public
runbook projection. There is no new recipient, provider configuration or
credential. A firing email, provider sending and a resolved IRM group remain
distinct evidence; no separate recovery email is promised.

## Packaging and R3 delivery

Build clean reviewed source using
tools/release/build-game-resource-monitor.ps1 with Version 2.105.0 and an
operator OutputDirectory. The manifest binds every file's revision, length,
mode and SHA-256. Candidate game-resource-monitor-v2.105.0-rc.1 and stable
game-resource-monitor-v2.105.0 identify the same accepted source and ZIP bytes.
No application image publication or addon update is part of this slice.

Before exposing resource-status, obtain the owner's explicit decision for this
new permission on the existing restricted SSH key. It grants no shell,
forwarding, new account/key, sudoers entry, firewall rule or public port.

Freeze old dispatcher/config bytes and metadata, installed addon/agent hashes,
unit and container identities, old rules/dashboards, secret metadata and backup
guards. Preserve game data through logical hashes when naturally rewritten
nVault serialization prevents a raw-byte comparison; document any concurrent
logical change without attribution or automatic repair. The monitor never
opens nVault.

Install only the fixed helper, new immutable source root, two new units and new
dashboard through the established claimed protocol. Reuse the existing protected
Grafana credential in memory. Require fresh resource observations before adding
the warning group. Preserve mounted config file inodes, add only the new rule
file, reload Alertmanager then Prometheus and retain all container instances.
Accept two ordinary timer observations, current dashboard queries, source
freshness, old monitoring and runtime/data continuity independently.

Test memory exhaustion, counter regression, stale metrics and recovery only
with fixtures. Never exhaust live RAM, change swap or generate live CPU load.
One separately grouped controlled firing/resolved channel canary may check
delivery without claiming a real host failure or recovery.

Rollback restores recorded routing/configs in the reviewed order and reloads
them, disables only the new timer, removes only the exact unchanged dashboard
through its claimed rollback protocol, and restores the approved dispatcher.
Preserve claims and notification history. Unknown outcomes, drift, unrelated
repair or loss of the recorded rollback boundary require a new decision.
