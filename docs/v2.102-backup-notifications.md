# v2.102 - Owner notifications for player-data backup

## Scope

Extend the existing private Prometheus -> Alertmanager -> Grafana Cloud IRM/email
path to the five existing `PlayerBackup*` warnings. The existing five agent
warnings remain covered. This is an R3 notification-policy slice; product addon
0.39.0, backup capture/Archive/Recover, journals, timers, thresholds and dashboards
are outside mutation scope. No new provider integration, credential, permission,
public port or application image is needed.

| Warning | Meaning |
| --- | --- |
| `PlayerBackupMonitorUnavailable` | Fresh monitoring observations are missing |
| `PlayerBackupObservationInvalid` | The observed backup record cannot be trusted |
| `PlayerBackupInterventionRequired` | A failed or uncertain attempt needs review |
| `PlayerBackupScheduleProblem` | The existing schedule check detects a problem |
| `PlayerBackupCopyUnavailable` | The verified copy is missing or older than eight days |

The existing five-minute holds remain unchanged. Notification grouping remains
one group per alert name, with 30-second group wait, five-minute group interval
and six-hour repeat interval. Source resolution closes the matching IRM group;
a separate recovery email remains outside the established channel guarantee.

## Projection and compatibility

Prometheus accepts exact component/severity/name tuples, rather than independent
component and name allowlists that permit crossed identities. Alertmanager
repeats both family-specific route checks and discards unrelated alerts. Only
alert name, component and severity labels reach it from Prometheus.

The outbound payload preserves the existing group keys and fixed public project
and environment. It includes firing/resolved state, times, fingerprint and a
family-specific public runbook. It excludes arbitrary labels, raw annotations,
private addresses, queries and generator URLs. The existing protected webhook
mount and persistent deduplication volume remain in use.

## Verification and rollout plan

The local rehearsal uses the pinned Alertmanager and Prometheus images with a
mock HTTP sink and synthetic alerts. It checks all ten firing/resolved groups,
the exact projected payload, transient failure/retry, duplicate suppression,
graceful restart persistence and invalid-config retention/recovery. A real
Prometheus process evaluates 42 synthetic identities to verify that only the ten
correct tuples and three allowed labels leave its production relabel rules.

Before rollout, inspect current active warnings and freeze current file hashes,
metadata/inodes, runtime identities, rule definitions, worker flags and dashboard
fingerprints. The November 3 preflight found the historical weekly-service
`PlayerBackupInterventionRequired` warning still firing. Enabling this route is
expected to notify it; it is not a new failed capture. Do not reset the service,
erase its history, replay a backup or silence the warning to make acceptance pass.

Publish the signed immutable `owner-notifications-v2.102.0-rc.1` package from
reviewed main after complete required CI. Validate candidate configurations with
the pinned native tools. Update only the two runtime configuration files and
their package record, preserving bind-mount inodes. Reload Alertmanager first,
then Prometheus, without replacing containers. Preserve exact rollback bytes.
If a gate fails, restore Prometheus first and Alertmanager second; notification
history is retained and an already sent email cannot be retracted.

Use one separately grouped synthetic backup canary for provider firing/resolved
acceptance, without injecting a real fault. Record provider delivery separately
from email receipt and IRM resolution. Verify the actual active warning's route,
unchanged backup rules/dashboards and all existing runtime identities. Promote
the accepted candidate bytes without rebuilding, then close the evidence PR.

## Status and limits

Local notification and telemetry rehearsals passed: ten firing/resolved groups,
the 42-input Prometheus routing matrix, 113 rule scenarios and the pinned
Collector/Prometheus/Grafana stack. The Windows telemetry run needed an existing
pinned Linux image's Moscow timezone data in a process-local fixture; no package
or system setting changed. Documentation links and whitespace checks passed.
No C# changed, so InspectCode and the complete local .NET gate were not run;
complete required CI remains the broad repository gate for this infrastructure
change.
