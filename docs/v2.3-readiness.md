## Claim Boundary

This document evaluates one provider-independent GoldSrcOps control plane and
one separately hosted controlled game server. It does not claim high
availability, long-term reliability, real-player adoption, automatic provider
integration, or an achieved service-level objective.

Detailed target evidence remains in owner-only files outside Git. This document
records only bounded conclusions, public revision identifiers, and the method
used to reach them. It contains no host address, operator source address,
credential, token, private endpoint, backup snapshot identifier, or command
payload.

## SLI Measurement Contract

| Indicator | Source and calculation | What it proves | Limitation |
| --- | --- | --- | --- |
| Host-local HTTPS edge health | Current liveness and readiness through local Caddy using the public hostname | Caddy, certificate selection, API liveness, and database-backed readiness work on the host | It does not traverse the external Internet path |
| External public health | Timestamped heartbeat samples from outside the control-plane host | The public route worked at sampled points | No continuous black-box time series exists yet, so API uptime cannot be calculated honestly |
| Poll coverage | Persisted snapshots divided by expected polls from the configured interval | The scheduler continued producing durable observations | Evaluates the single controlled endpoint only |
| Poll success | Reachable persisted snapshots divided by all soak snapshots | A2S succeeded during the observed interval | A 24-hour sample is not a long-term error budget |
| Poll latency | Average, p95, and maximum `LatencyMs` from reachable persisted snapshots | Observed A2S response latency | Does not isolate Internet, provider, or application contribution |
| Poll continuity | Maximum gap between consecutive snapshots for the controlled server | Detects missed or stalled polling intervals | Clock and database timestamps are assumed trustworthy after host-readiness checks |
| Incident behavior | Incidents opened during the window plus currently open incidents and duration | Detects availability transitions and unresolved incidents | No failure is intentionally injected during the soak |
| Command outcomes | Commands requested during the window plus current non-terminal executions | Detects failed or stranded durable work | No routine RCON command is generated solely to improve a metric |
| Alert outbox | Events created/processed in the window plus current pending and dead-letter counts | Detects unresolved durable alert work | Alert delivery remains disabled after the controlled exercise |
| Telemetry continuity | Prometheus `count_over_time` and `sum_over_time` for application-export and Collector scrape targets | The private telemetry path remained queryable | `up{job="goldsrcops"}` observes the Collector exporter, not public API availability |
| Database capacity | Terminal database and poll-snapshot relation sizes | Provides a bounded growth observation | It is not a continuous capacity time series |
| Host pressure | Terminal free disk, available memory, CPU count, and one-minute load | Rejects obvious terminal resource exhaustion | It does not establish sustained utilization or capacity headroom |
| Container continuity | Image, start time, restart count, running state, and health compared with the baseline | Detects control-plane replacement or restart | Game-server process continuity is checked separately on its host |
| Bot count | Persisted A2S bot count for every soak poll | Keeps controlled load separate from real players | Zero bots is a release observation, not an adoption claim |

Prometheus scrapes only Collector endpoints in the reference topology. Its
application-export `up` series therefore must not be renamed or presented as
public API uptime. A future black-box probe is required before setting a
continuous HTTP availability SLO.

## Release-Soak Bounds

`ops/production/soak-readiness.ps1` applies these fail-closed release bounds:

- the complete window is at least 24 hours and matches the baseline duration;
- candidate identity and all six required control-plane containers are
  unchanged, running, and healthy;
- current liveness and readiness through host-local Caddy both return HTTP
  `200`;
- the scheduled backup freshness gate passes within 36 hours;
- exactly one controlled server is enabled, reachable, and online, with the
  reviewed 60-second poll interval;
- the latest poll is no older than two minutes;
- persisted poll coverage is at least 98 percent, every observed poll succeeds,
  every successful poll contributes one latency sample, no bot-positive poll
  exists, and the maximum gap is no more than twice the configured interval
  plus ten seconds;
- no incident opened during the soak and none remains open;
- no failed or incomplete command, pending alert, or dead letter remains;
- current Collector and application-export scrape targets are up, and each has
  at least 99 percent sample and healthy-sample coverage;
- terminal free disk is at least 10 GiB, available memory is at least 256 MiB,
  and one-minute load does not exceed twice the processor count.

These are release acceptance bounds for this short observation, not long-term
SLO targets. `tools/smoke/soak-readiness.ps1` validates the decision logic with
non-target fixtures in CI.

## Evidence Procedure

The terminal control-plane check is read-only. It inspects Docker state, HTTPS
health through host-local Caddy, PostgreSQL aggregates, Prometheus samples,
backup freshness, and terminal host capacity. It writes sanitized evidence
atomically outside the repository with mode `0600` on Linux.

Run it from a reviewed source snapshot that contains the evaluator. The source
snapshot may be transported independently, but it must not replace or modify
the active release-candidate checkout during the soak:

```powershell
sudo pwsh -NoProfile -File ./ops/production/soak-readiness.ps1 `
  -BaselineFile /var/lib/goldsrcops/evidence/v2.3-soak-baseline.json `
  -EnvironmentFile /etc/goldsrcops/deployment.env `
  -ExpectedPollIntervalSeconds 60 `
  -EvidenceFile /var/lib/goldsrcops/evidence/v2.3-soak-readiness.json
```

During the interval, `-AllowIncomplete` may be used only for diagnostics; a
successful diagnostic result is `InProgress` and cannot close the release gate.
After the expected completion time, omit that switch and require `Passed` plus
`TargetEvidence: true`. Independently compare the game-server service state,
restart count, invocation, main process, and listener ownership with its
owner-only baseline. The repository game-host evaluator performs that
process-continuity check without changing the service:

```bash
sudo bash ./ops/gameserver/soak-readiness.sh \
  --baseline-file /var/lib/goldsrcops/evidence/v2.3-soak-baseline.json \
  --evidence-file /var/lib/goldsrcops/evidence/v2.3-gameserver-soak-readiness.json
```

Validate both files before transcribing any value into Git:

```bash
sudo jq -e '
  .Action == "V23SoakReadiness" and
  .Source == "Live" and
  .TargetEvidence == true and
  .Result == "Passed" and
  .Window.Complete == true and
  (.Checks | all(.Passed == true))
' /var/lib/goldsrcops/evidence/v2.3-soak-readiness.json >/dev/null

sudo jq -e '
  .Action == "V23GameHostSoakReadiness" and
  .Source == "Live" and
  .TargetEvidence == true and
  .Result == "Passed" and
  (.Continuity | to_entries | all(.value == true)) and
  (.Checks | all(.Passed == true))
' /var/lib/goldsrcops/evidence/v2.3-gameserver-soak-readiness.json >/dev/null
```

Both commands must exit with code zero. Address stability was completed as a
separate control-plane-side comparison so the public endpoint is not copied
into repository or game-host continuity evidence.

## Initial SLO Work

The inactive proposal and terminal observation table are defined in
[service-level objectives](service-level-objectives.md). They cover:

- public API synthetic availability after a continuous external probe exists;
- controlled-endpoint poll success and freshness over a longer rolling window;
- incident detection and recovery latency;
- command terminal-state completion;
- alert outbox age and dead-letter rate;
- backup freshness and restore-rehearsal cadence.

Each proposal names its population, exclusions, measurement source, rolling
window, error budget, minimum sample where needed, and activation gate. The
24-hour soak can inform a prospective review but cannot demonstrate that a
monthly objective has been achieved. Public API availability remains inactive
until an independent continuous probe exists.
