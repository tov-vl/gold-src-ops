# GoldSrcOps v2.20 Release Readiness

Review date: 2026-09-21. Status: local candidate preparation. The provider
operations product and deployment contracts are implemented and locally
verified. Product review, candidate publication, target rollout, production
acceptance, and stable promotion remain pending.

## Scope

The v2.20 release scope is Provider Delivery Operations:

- one append-only review relation in the dedicated AlertReceiver database;
- separately authorized internal list, detail, review, and receipt endpoints;
- an Operator-only server-side BFF and bounded review workflow;
- immutable review evidence that does not replay, retry, delete, reclassify,
  or unblock provider delivery;
- disabled-by-default receiver and Web deployment contracts with one shared
  file-backed operations credential;
- a private Web-to-receiver service path while public Caddy continues to
  expose only `POST /api/v1/availability-events`;
- extended preflight, container, migration, backup, and restore evidence.

The detailed local behavior and evidence are retained in
[v2.20 Provider Delivery Operations](v2.20-provider-delivery-operations.md).

## Claim Boundary

Candidate acceptance can show that the exact Web and AlertReceiver artifacts
expose the review workflow only to an authenticated Operator, keep its shared
authorization value outside browser and Compose environment values, append one
idempotent review, and preserve the reviewed message as `DeadLetter`. It can
also show that the additive receiver migration and cross-stack activation can
be recovered without disturbing the existing API, control-plane database,
provider delivery state, or game host.

Acceptance cannot prove notification delivery, escalation, replay safety,
sustained provider operation, high availability, a separate receiver failure
domain, long-term reliability, or an achieved SLO. It does not authorize
provider replay, deletion, reclassification, queue drain, source delivery, or
provider-worker activation.

## Compatibility And Migration Review

- The control-plane database has no v2.20 migration or model change.
- The receiver adds migration `20260921082622_AddProviderOutboxReviews`: one
  empty table, one unique index, and one restrictive foreign key. It performs
  no existing-row rewrite or backfill.
- The migration is additive and the old v2.19 receiver ignores the new table,
  so it may run before application replacement. Only the reviewed migration
  action may apply it; ordinary startup remains migration-free.
- Web and AlertReceiver must use the same owner-controlled operations
  authorization. A one-sided or mismatched activation fails closed and is not
  accepted as a partial rollout.
- API behavior and public contracts are unchanged. The API image is published
  by the repository tag workflow but is not recreated on the target.
- Production Caddy remains unchanged and exposes no provider-operations path.
  The standalone Caddy ordering fix retains the same one-path allowlist.
- The source sender and provider worker remain disabled. A review writes only
  audit evidence and does not consume or alter delivery truth.
- Rollback restores the accepted v2.19 Web and receiver images and removes the
  operations overlays while preserving the additive schema and any accepted
  review row for reconciliation.

## Ordered Candidate Plan

### 1. Review, Merge, And Freeze

1. Push the product branch without force and merge one product/readiness pull
   request through protected `main` after every required check passes.
2. Record the exact merge SHA, confirm `v2.20.0-rc.1` and `v2.20.0` are unused,
   and compare the final inventory with signed stable `v2.19.0`.
3. Retain the accepted v2.19 Web and AlertReceiver digests, owner-only
   environments, secret locations, and rollback commands outside Git.
4. Stop if the final diff changes the version, risk, runtime, migration,
   authorization, worker, or claim boundary recorded here.

### 2. Publish And Verify The Candidate

1. Create, locally verify, and push signed annotated tag `v2.20.0-rc.1` at the
   exact reviewed `main` revision.
2. Require `Quality Gate`, `Container Smoke`, and `Browser Smoke`, followed by
   publication and independent digest verification of API, Web, and
   AlertReceiver images.
3. Verify all OCI source, revision, version, license, and immutable digest
   identities before preparing a target mutation.
4. Stop before rollout if any image identity or published-digest smoke differs
   from the frozen revision.

### 3. Back Up, Rehearse, And Apply The Migration

1. Capture sanitized API/Web/receiver health, image, restart, queue, incident,
   A2S, and game-service baselines. Keep private topology and rows owner-only.
2. Create a fresh encrypted receiver PostgreSQL backup, complete a `100%`
   repository check, and restore it into an isolated disposable database.
3. Apply and reapply all three receiver migrations to the isolated restore with
   the exact candidate receiver image.
4. Apply migration `20260921082622_AddProviderOutboxReviews` once to the target
   receiver database through the candidate image. Do not down-migrate on
   rollback.

### 4. Roll Out Disabled Artifacts

1. Replace only Web and AlertReceiver with their independently verified
   candidate digests using the base Compose contracts.
2. Keep `ProviderOperations__Enabled=false`, `AlertDelivery__Enabled=false`,
   `ProviderDelivery__Enabled=false`, and receiver mode `CatchUp`.
3. Verify exact digests, OCI revision, non-root/read-only hardening, liveness,
   readiness, three receiver migrations, zero active claims, and unchanged
   public `404` for provider-operations paths.
4. Verify the unchanged API, control-plane database, Caddy, telemetry, game
   host, A2S reachability, zero bots, and restart counters.

### 5. Activate And Exercise One Review

1. Create one owner-controlled Bearer authorization file outside Git and point
   both deployment environments at that exact file without printing it.
2. Run the target cross-stack preflight, then recreate only receiver and Web
   with their reviewed provider-operations overlays. Keep both delivery workers
   off and receiver mode `CatchUp`.
3. Verify public rejection, private authorization rejection/acceptance, the
   Reader/Operator matrix, and that the credential never reaches browser,
   Compose environment, logs, or tracked evidence.
4. Through the Operator UI, append exactly one review to the preserved v2.19
   provider dead letter with one fresh request UUID and audit reason. Require
   an immutable receipt and confirm the source message remains `DeadLetter`
   with unchanged attempts, error, ordering, and claim fields.
5. Do not retry an uncertain review submission. Reconcile only through the
   request receipt endpoint.

### 6. Accept Or Roll Back

1. Collect at least three healthy read-only samples over at least three
   minutes for API, Web, receiver, public route, durable queues, and dependent
   runtime continuity.
2. Confirm exactly one accepted review, no replay or provider notification, no
   source/provider claim, and both delivery workers still disabled.
3. On failure before an accepted review, remove both operations overlays and
   restore the v2.19 Web/receiver digests. On failure after an accepted or
   uncertain review, preserve the row and reconcile; do not delete or resubmit.
4. Stable promotion remains blocked until all R3 recovery and continuity
   evidence is accepted.

## Failure And Rollback Rules

- Stop on the first unexplained CI, artifact, migration, backup, restore,
  health, authorization, route, review, or continuity failure.
- Never retry an uncertain review, replace a published tag, rebuild an accepted
  image, expose the operations route publicly, or enable a delivery worker to
  make acceptance pass.
- Never down-migrate the receiver database or delete an accepted review. The
  old runtime remains compatible with the additive table.
- Roll back Web and AlertReceiver independently to recorded v2.19 digests, but
  remove operations overlays from both sides before declaring rollback
  complete.
- If the shared credential or rollback boundary cannot be verified exactly,
  stop and obtain a new decision.
