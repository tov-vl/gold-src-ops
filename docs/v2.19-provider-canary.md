# GoldSrcOps v2.19 Post-Release Provider Canary

Observation date: 2026-09-20. Status: accepted as one bounded post-release
provider canary. The already published and deployed v2.19 AlertReceiver
artifact was not rebuilt or replaced for this operation.

## Purpose And Boundary

The canary was a separate operational gate after stable `v2.19.0`. It tested
one fresh availability incident through the durable receiver and the configured
Grafana Cloud IRM delivery boundary, including one ordered `Trigger`, one
ordered `Resolve`, and one owner-confirmed email notification.

The operation did not authorize sustained source delivery, unattended provider
delivery, escalation reliability, high availability, or an achieved SLO. The
control-plane sender and receiver provider worker were returned to disabled
after the bounded sequence.

## Executed Sequence

1. Verify the stable receiver, source outbox, receiver incident state, provider
   outbox, game runtime, and A2S continuity before enabling either worker.
2. Start one bounded provider attempt. The provider rejected an invalid
   placeholder authorization value with HTTP `403`; the receiver retained that
   attempt as one terminal dead letter and stopped without automatic retry.
3. Restore the receiver to `CatchUp`, process the matching source recovery with
   provider action suppressed, and verify that no direct database mutation was
   used to make the reconciliation pass.
4. Use the existing owner-controlled Grafana service-account credential for a
   fresh bounded pair. Deliver exactly one `Trigger` and one `Resolve`, in
   order, with one source attempt and one provider attempt per action.
5. Confirm receipt of the resulting email through the owner-controlled channel.
6. Disable the source sender and provider worker again and verify the final
   durable and runtime state.

No authorization value, endpoint, integration identifier, provider payload, or
private topology value is retained in this repository record.

recovery timer remained inactive, and the game-event agent remained
boot-disabled.

## Anomaly And Disposition Boundary

The HTTP `403` attempt remains a historical provider dead letter. It must not
be replayed after the later `Resolve`: sending the stale `Trigger` could create
an incorrect notification after the incident has already recovered. It also
must not be deleted, marked processed, or rewritten through direct SQL merely
to make the queue appear clean.

The next product slice should expose bounded provider-outbox inspection and an
audited reviewed disposition that preserves the immutable failure evidence
while distinguishing reviewed terminal work from unreviewed operational
failures.

## Claim Boundary

This evidence proves that one fresh `Trigger` and its matching `Resolve` crossed
the durable receiver and configured provider boundary in order, each on one
attempt, and that the owner received the resulting email. It does not prove
long-term availability, paging reliability, provider rate-limit recovery,
escalation behavior, sustained unattended delivery, or an achieved SLO.

## Next Gate

Keep both delivery workers disabled outside separately reviewed operations.
Implement the provider-outbox inspection and disposition boundary before a
guarded sustained-delivery activation and passive observation window.
