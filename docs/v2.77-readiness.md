## Execution and acceptance plan

1. Recheck the frozen source, tag absence, successful main CI and baseline.
   Publish a locally verified signed annotated candidate tag at that revision.
2. Require the full candidate workflow, including image publication and smoke
   checks. Independently verify immutable image digests and OCI revision/version
   metadata for all images published by the existing workflow.
3. Recheck the live rollback boundary. Change only the Web image setting to the
   verified candidate digest, preserving file ownership/mode and other bytes.
   Recreate only Web with the existing Compose project and `--no-deps`.
4. Verify deployed Web identity, health and RU/EN leaderboard. Exercise bounded
   ordinary lookup, a natural busy response, visible countdown and manual retry.
   Check early submission blocking, preserved input and no automatic lookup;
   compare search telemetry without injecting a failure. Include a no-JavaScript
   check. Keep nicknames, raw page bodies and private metric details out of Git.
5. Compare the other eight container identities, start times, restart counts and
   mounts, all monitoring/Compose hashes and non-Web settings with the fresh
   baseline. Inspect browser errors and request behavior for the changed surface.
6. On an unexplained failure, stop and reconcile any uncertain operation. Restore
   only the recorded Web digest and its image setting, then independently verify
   recovery and the preserved boundary. Do not retry an uncertain write blindly.
7. After acceptance, publish the signed stable tag at the same revision, verify
   digest-preserving promotion and the GitHub Release, then close the evidence
   through a documentation PR, required CI, squash merge and post-merge checks.

## Search telemetry and stable promotion

After the 60-second Web export and 15-second scrape/evaluation intervals, the new
Web instance exposed exactly six successful searches and two busy responses,
matching all eight browser POSTs. The previous instance's series remained at
45 successes and one busy response. Per-instance comparison distinguished these
series; aggregate totals of 51 and three alone were not used as proof of a
counter reset or a per-instance result. No reset, search failure series or active
Web warning was observed, and all three Web rules were healthy.

The 15-minute recording-rule value is an extrapolated sampled increase, not the
discrete acceptance-request count. The new series was first observed after some
requests had already completed, so this short observation does not establish
complete window accounting or an SLO claim. Busy remains excluded from successful
read/failure thresholds under the unchanged accepted policy.
