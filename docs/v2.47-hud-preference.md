# v2.47 Persistent HUD Preference

Status as of 2026-10-08: selected next product slice. Implementation, package
freeze and runtime delivery have not started. This document defines planned
behavior and evidence, not installed functionality or rollout authorization.

## Reason And Scope

In addon 0.16.0, `/settings` toggles HUD for the current connection only.
`client_putinserver` and disconnect reset `g_hud_disabled`; the toggle does not
save a preference. Language and primary/pistol choices already persist by
canonical SteamID in the separate schema-1 preferences nVault described in
[v2.39](v2.39-player-preferences.md).

The next slice will retain an explicit HUD on/off choice after reconnect and
map/plugin restart. Players without a stored choice will keep the current
enabled default, without writing defaults on join. The accepted HUD timing,
position, menu coexistence and alive/player filters remain unchanged.

This is a settings improvement with focused automated acceptance independent
of the two-player combat scenario. The owner deferred that scenario indefinitely
on 2026-10-08. Combat rewards, streak milestones and multiplayer balance remain
unverified by human play; this slice makes no claim about them.

## Compatibility And Storage Boundary

Implementation must preserve existing language/weapon preference and statistics
records. Use canonical identities and the existing refusal of bots/HLTV,
shared/unknown identities and duplicate connected SteamIDs. A late identity must
not overwrite an explicit HUD selection already made in the current session.
Unavailable storage or identity must leave a usable session-only toggle.

Choose and review the HUD record encoding before implementation. A separately
versioned, namespaced HUD record in the existing preferences vault is one option
that can preserve schema-1 language/weapon records and let addon 0.16.0 ignore
new HUD records. This is a proposal, not a frozen format. Verify that the selected
format preserves reverse-upgrade behavior without restoring or rewriting vaults.

Retain corrupt records for diagnosis; do not replace them with defaults. Verify
writes through exact readback and preserve the existing blocked-write/session
fallback semantics. Settings feedback must distinguish an actually persisted
HUD choice from a session-only choice, including when other preferences are saved.

No scoring, streak, heal/ammo reward, weapon application, rank, global leaderboard,
VIP/payment, map addon or control-plane change is included. No PostgreSQL
migration, credentials, new external service or installer-driven vault migration
is needed for the planned boundary.

## Planned Verification And Delivery

The focused engine fixture must use real nVault and cover:

- Explicit off/on selection, exact readback, reconnect, slot reuse and a fresh
  process on another map; joining without a selection must not write defaults.
- Late authorization preserving the current-session toggle, canonical identity
  normalization and refusal of duplicate/shared/unknown identities and bots/HLTV.
- Invalid records retained, unavailable storage and readback failure falling
  back to session behavior; disabled-addon and stale menu callbacks cannot write.
- Existing language/weapon records and statistics remaining intact; reverse
  upgrade to 0.16.0 ignores HUD records and retains them for reconciliation.
- RU/EN settings feedback accurately reflecting persistence, plus the existing
  periodic HUD/menu and loadout regressions.

The expected runtime risk class is R2 because this changes persistent player
state; confirm it against the final diff and [release process](release-process.md).
Compile with the pinned AMXX/ReAPI toolchain, run the focused runtime checks and
the required product PR CI. Freeze a reviewed package and rollback inputs only
after implementation passes. Any later authorized installation requires stopped
game vault preservation and independent artifact/storage/A2S checks. A two-player
combat session is not an acceptance requirement for this settings boundary.
