# GoldSrcOps v2.3 Game-Server Provider Decision

## Status

Conditionally selected on 2026-08-28 for v2.3 Slice 2. The preferred target is
a self-operated MyArena KVM game VDS rather than the provider-managed
Counter-Strike 1.6 product. No account, paid service, credential, server,
public endpoint, or provider support commitment is claimed by this document.

Purchase and provisioning remain blocked until the pre-purchase checks below
are confirmed and the final checkout amount is explicitly approved.

## Decision

Use the smallest currently listed MyArena KVM game VDS that provides one
dedicated high-frequency vCPU, 2 GB RAM, 25 GB SSD, a 100/100 Mbit/s channel,
and game-aware DDoS protection. The
[provider catalog](https://www.myarena.ru/vds_kvm_cloud.html) displayed the
following candidate on 2026-08-28:

| Property | Candidate value |
| --- | --- |
| CPU | `1 x Xeon E3-1271v3`, Turbo up to 4 GHz |
| Memory | 2 GB |
| Disk | 25 GB SSD |
| Network | 100/100 Mbit/s |
| DDoS scope | Protection for two game servers included |
| Catalog price | 1,100 RUB per 30 days |

The catalog value is evidence for comparison, not a price guarantee or
authorization to purchase. Stock, tax treatment, public IPv4 allocation,
renewal price, and cancellation terms must be rechecked at checkout.

This size is a cost-bounded no-bot starting point, not a capacity claim. Record
CPU, memory, disk, and network headroom during the baseline. Reassess and resize
before YaPB if measured headroom is insufficient.

Prefer Debian 12 x86-64 when it is available for the selected plan. A different
current Debian stable image requires a compatibility check before installation.
Prefer the Moscow location when the live catalog offers a choice; record the
actual data-center region before payment. The game-server host remains
independent from the future GoldSrcOps control-plane VPS.

## Why A Self-Operated Game VDS

The first baseline optimizes for artifact control and reproducible evidence,
not panel convenience:

- root SSH access permits local hash and detached-signature verification before
  either pinned runtime is installed;
- the provider cannot select a different ReHLDS or ReGameDLL_CS build through a
  managed game template;
- process ownership, systemd restart behavior, logs, firewall policy, and the
  backup archive are directly inspectable;
- ReHLDS `rcon_users` can be persisted and verified after restart without
  relying on a proprietary panel action;
- the provider documents game-aware UDP protection and firewall rules for VDS
  products, while GoldSrcOps continues to use only the public A2S/RCON
  protocol boundary;
- migration to another Linux host requires operational work but no GoldSrcOps
  code change.

This is an operational provider choice, not a new application architecture
decision. The provider name must not enter application contracts or runtime
domain models.

## Pre-Purchase Gate

Do not order the candidate until each item has a captured answer from the live
catalog or provider support:

1. The selected plan is in stock at the displayed 30-day price, and there is no
   mandatory long-term commitment or non-obvious setup charge.
2. The data-center region is disclosed, and one dedicated public IPv4 is
   included, remains assigned for the rental period, and is not hidden behind
   CGNAT.
3. The CS 1.6 DDoS profile accepts the intended UDP game/query port and
   preserves client source addresses required by the ReHLDS RCON allowlist.
4. The provider does not replace files inside the guest OS or automatically
   update a self-installed ReHLDS or ReGameDLL_CS runtime.
5. Debian 12 x86-64, KVM virtualization, root SSH, and operator-installed
   systemd services are supported on the exact plan.
6. The customer can restrict SSH by source IPv4 and can register the chosen
   game UDP port in the provider protection panel.
7. Cancellation exports or erases customer data predictably; no provider-only
   backup is required to recover the sanitized server configuration.
8. The documented email, Telegram, and trusted-IP account protections are still
   available and can be enabled before the server is ordered.

Any negative or ambiguous answer returns the decision to the Timeweb Cloud
fallback. A changed catalog price requires a fresh comparison, not silent
acceptance.

## Provisioning Boundary

When purchase is separately approved, provision only this minimal boundary:

- one provider account with the strongest available login controls enabled;
  for MyArena this means the documented
  [email, Telegram, and trusted-IP protections](https://wiki.myarena.ru/index.php/%D0%9A%D0%B0%D0%BA_%D0%BE%D0%B1%D0%B5%D0%B7%D0%BE%D0%BF%D0%B0%D1%81%D0%B8%D1%82%D1%8C_%D1%81%D0%B2%D0%BE%D1%8E_%D1%83%D1%87%D0%B5%D1%82%D0%BD%D1%83%D1%8E_%D0%B7%D0%B0%D0%BF%D0%B8%D1%81%D1%8C),
  with recovery material stored outside the repository;
- one VDS with a dedicated public IPv4 and no GoldSrcOps, PostgreSQL, or
  observability workloads;
- one non-root operator account using an Ed25519 SSH key, with password SSH and
  direct root login disabled after recovery access is verified;
- one unprivileged `goldsrc` service account and one pinned systemd unit;
- public UDP only for the reviewed game/query port;
- SSH allowed only from the temporary operator source IPv4;
- ReHLDS RCON restricted to the same approved `/32`, verified through a
  non-empty `rcon_users` result after every restart;
- no YaPB, AMX Mod X, ReAPI, gameplay plugin, custom map, or public promotion
  before the no-bot baseline is accepted.

GoldSrc gameplay, A2S, and RCON share the UDP endpoint. The host firewall cannot
allow public gameplay while distinguishing RCON packets on that port. The
provider DDoS profile and host firewall protect the endpoint generally;
ReHLDS `rcon_users` remains the required RCON source boundary until a private
tunnel from the Slice 3 control-plane VPS is available.

## Backup And Exit Path

Before runtime installation, create a recoverable baseline of the clean host.
If the selected plan has no provider snapshot, the clean OS can be rebuilt from
the recorded image and provisioning manifest.

After configuration:

1. Stop the service and create a versioned archive of the service unit,
   installation manifest, verified runtime files, and sanitized configuration.
2. Keep the RCON password and SSH private key outside the archive unless it is
   encrypted specifically for private recovery storage.
3. Store one encrypted copy off-host and verify extraction into a disposable
   directory before starting the 24-hour baseline.
4. Rehearse configuration restore on the same host, then repeat A2S and
   `rcon_users` verification.
5. Retain enough information to rebuild the server on the Timeweb Cloud fallback
   without changing the GoldSrcOps server contract.

The provider account, public endpoint, support conversation, invoice, and
secret-bearing recovery material are private deployment records. Public
evidence may retain the provider, region, plan class, sanitized firewall shape,
versions, hashes, and measured timings.
