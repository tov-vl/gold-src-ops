# v2.98 - Owner notification delivery

## Boundary and current gate

R3 operations slice, based on accepted v2.97 warnings. The owner selected the
existing Grafana Cloud IRM account and its email channel. Implementation is local;
no provider integration, credential, production container or notification has
been created by this slice yet. Provider changes and secret transport require
the separate exact decision described below. No release is accepted yet.

The first scope contains only the five `GameEventAgent*` warning identities from
[v2.97](v2.97-agent-alerts.md). Other rule groups keep their existing evaluation
and dashboards but do not enter this new outbound path. The API's availability
sender and the old durable receiver/provider workers remain disabled. Historical
outbox events and provider dead letters are preserved; they are not a test queue.

## Data path and policy

```text
Existing private Prometheus
  -> private Alertmanager
  -> dedicated Grafana Cloud IRM Alertmanager integration
  -> existing owner's email notification rule
```

Prometheus filters the exact component, severity and five alert names, then
retains only `alertname`, `component` and `severity` labels. Alertmanager defaults
to discard and repeats the allowlist at its email route. Grouping is one group
per alert name; group wait is 30 seconds, group interval five minutes, and repeat
interval six hours. The existing five-minute warning hold is unchanged.

Alertmanager uses a minimal structured projection instead of forwarding raw
Prometheus data. It includes the warning identity, firing/resolved state, event
times, fingerprint, fixed public project/environment labels and public runbook
links. It omits raw annotations, additional labels, private generator URLs and
queries. The explicit group key is derived solely from the fixed project,
environment and grouped alert name. IRM must keep its `payload.groupKey` grouping
and source-based resolution. Compatibility of this projection with the live IRM
templates remains a canary gate; a local HTTP 200 is insufficient evidence.

The native Alertmanager webhook sends resolved updates and retries transient
delivery errors within its notification cycle. Its notification log and silences
use a dedicated persistent volume with 120-hour retention. Successful duplicates
are suppressed, including across a graceful restart. Repeats are not a promise
of repeated emails: IRM applies its own escalation policy. Exactly-once delivery
and an email SLA are not claimed. Requests time out after ten seconds, redirects
are disabled, and logs/CPU/memory/PIDs are bounded.

IRM currently shows an email notification rule for the existing owner. Source
resolution closes an alert group and stops escalation. A separate recovery email
has not been established and must not be claimed. Acceptance distinguishes an
HTTP receipt, one resolved provider group, and owner-confirmed email receipt.
If separate recovery emails are required, stop and agree the provider mechanism
before enabling production delivery.

This co-located path cannot notify about its own total host/Prometheus/Alertmanager
outage. Source alerts have finite expiry; a resolved notification alone is not an
independent health observation. These limitations need a separate external
watchdog milestone, not an availability claim from this release.

## Deployment and rollback plan

The standalone Compose project adds one digest-pinned Alertmanager 0.34.1. It
joins the existing internal telemetry network at a reviewed unused fixed address
and a new dedicated outbound bridge. Existing network isolation and containers
are preserved. No ports are published; no Caddy route or public administration
endpoint is added. Cluster gossip is disabled and the process uses UID 65534,
a read-only filesystem and dropped capabilities.

The IRM integration URL is a credential. Keep it in an owner-controlled file
outside Git, owned by UID 65534 with mode 0400; mount it read-only as
`/run/secrets/irm-webhook-url`. Never put the URL in environment values, command
arguments, chat, screenshots, logs or retained evidence. No administrative cloud
API token, new user or IAM role is needed for the proposed runtime.

Before rollout, freeze config bytes/hash/inode/metadata, existing container and
rule identities, old worker flags, new-component absence, the chosen address and
the exact provider route. Preserve the current Prometheus configuration as the
rollback input. Inspect existing active warnings before enabling the route.

Create the separately approved integration and a single-owner email escalation
without loops. Keep existing integrations and personal notification rules intact.
Run one labeled synthetic firing/resolved canary using a separate canary group
namespace and the same allowlisted projection. Do not stop services or inject a
game/queue failure. Require a single group, source resolution, no new unrelated
groups and owner-confirmed email receipt. An uncertain provider outcome requires
read-only reconciliation, never blind resubmission.

Start only the new component. Check its digest, isolation, readiness and actual
route before changing Prometheus. Validate the complete candidate configuration
with the pinned Prometheus image; write the config in place to preserve its bind
mount inode, then SIGHUP the existing Prometheus process. Require the successful
reload, new target, unchanged old rules/dashboards/containers and worker flags.

On failure, restore exact prior config bytes in place after checking the installed
hash and metadata, validate and reload. Stop only the new Alertmanager; retain
its persistent state, private receipts and provider history for reconciliation.
Disable only the new provider route through the separately reviewed operation.
Do not remove shared networks, volumes, old events or credentials, and do not
silence unrelated alerts. No game, agent, database or receiver restart is needed.

## Verification

`tools/smoke/owner-notifications.py` uses pinned Alertmanager and Python images
with synthetic data and a local mock receiver. It verifies the actual rendered
payload, all five firing/resolved groups, transient HTTP failure/retry, duplicate
suppression, graceful restart persistence, invalid-config retention/recovery,
outbound field projection and Compose restrictions. Fixture timers are shortened;
production timings remain unchanged. It never consumes a real IRM credential.

Required CI, immutable candidate publication, independently accepted production
delivery, stable promotion and final evidence remain pending. No C# behavior,
game addon, queue schema, source data, game process or observer is changed.

`tools/release/build-owner-notifications.ps1` binds the four runtime/config inputs
to a clean source revision, file hashes and immutable ZIP. Proposed operations
tags are `owner-notifications-v2.98.0-rc.1` and `owner-notifications-v2.98.0`.
Stable publication must reuse candidate bytes; it does not change the global
application release or rebuild application images.
