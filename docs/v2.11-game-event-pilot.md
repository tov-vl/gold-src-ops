# v2.11 Game-Event Pilot Readiness

## Status And Boundary

v2.11 prepares the production game-event delivery pilot without activating it
on the target. The repository can build one immutable bundle containing the
Linux companion agent and the minimal Metamod-R, AMX Mod X, ReAPI, and
GoldSrcOps producer overlay. A separate host installer verifies and stores that
bundle beside the active game runtime. The repository also contains a staged,
fail-closed activation and active-rollback workflow; adding that workflow is not
evidence that any activation stage has run in production.

This slice does not:

- provision an Auth0 machine client or create a client secret;
- execute the activation workflow against the live Counter-Strike tree;
- enable producer, spool import, or HTTP delivery on the target;
- start, enable, stop, or restart either production service;
- send a production event or prove gameplay delivery.

The installer must finish with the existing game runtime unchanged and
`goldsrcops-game-event-agent.service` both disabled and inactive. Crossing any
of those boundaries requires a separately reviewed activation and rollback
procedure.

## Pinned Bundle

`tools/release/build-game-event-pilot-bundle.ps1` assembles:

- `GoldSrcOps.GameEventAgent` as a .NET 10 `linux-x64`, self-contained,
  single-file executable with native libraries embedded for protected runtime
  extraction;
- AMX Mod X `1.10.0.5481` base and Counter-Strike Linux runtimes;
- Metamod-R `1.3.0.149`;
- ReAPI `5.24.0.300`;
- the compiled `goldsrcops_game_events.amxx` producer and minimal loader
  configuration.

Every downloaded archive is pinned by release URL and SHA-256. The bundle
manifest records the exact Git revision, production eligibility, component
pins, producer source and binary hashes, and the size, SHA-256, and intended
mode of every payload file. The four activation values are all `false`.

Review the plan without downloading or writing artifacts:

```powershell
pwsh -NoProfile -File .\tools\release\build-game-event-pilot-bundle.ps1 -Plan
```

Build a production-eligible bundle only from a tracked-clean revision:

```powershell
pwsh -NoProfile -File .\tools\release\build-game-event-pilot-bundle.ps1 `
  -BundleVersion 2.11.0-pilot.1
```

The ZIP and companion `.sha256` file remain below ignored
`artifacts/game-event-pilot/output/`. The builder refuses to overwrite an
immutable output. `-DevelopmentBuild` is available only for local validation
of tracked changes; its manifest is explicitly `productionEligible: false`,
and the host installer rejects it. `-ReplaceDevelopmentOutput` is valid only
with that development flag.

Run the lightweight repository contract without downloading the toolchain:

```powershell
pwsh -NoProfile -File .\tools\smoke\game-event-pilot-bundle.ps1
```

## Host Installation

`ops/gameserver/game-event-pilot-install.sh` is plan-only by default. It
requires the reviewed Ubuntu 24.04 host foundation, the installed ReHLDS
`3.15.0.896` and ReGameDLL_CS `5.30.0.814` baseline, the current active runtime
marker, and a still plugin-free game tree.

The apply path accepts only an absolute regular bundle owned by `root:root`
with mode `0600` and an independently supplied lowercase SHA-256. It rejects
unsafe or duplicate archive paths, symlinks, extra files, development
manifests, drifted component pins, and any payload whose size or digest differs
from the manifest.

Review the generic plan locally:

```bash
bash ./ops/gameserver/game-event-pilot-install.sh
```

After transporting the reviewed script, bundle, and digest to a root-owned
staging location, review the exact target plan and then apply it:

```bash
bash /tmp/game-event-pilot-install.sh \
  --bundle /root/goldsrcops-game-event-pilot.zip \
  --bundle-sha256 <reviewed-sha256>

sudo --preserve-env=SSH_CONNECTION \
  bash /tmp/game-event-pilot-install.sh \
    --bundle /root/goldsrcops-game-event-pilot.zip \
    --bundle-sha256 <reviewed-sha256> \
    --apply
```

The installation creates one content-addressed release, restricted queue and
.NET extraction directories, a non-secret environment file with spool import
and delivery disabled, and a hardened systemd unit guarded by both a separate
activation marker and a systemd credential. It does not create either gate.

Expected post-install state:

```text
SERVICE_STATE: disabled and inactive
GAME_RUNTIME_STATE: unchanged; no plugin loader or producer is active
```

The deterministic installer smoke is:

```bash
bash ./tools/smoke/gameserver-game-event-pilot-install.sh
```

## Pre-Activation Rollback

Before activation, the installer can remove its own installation:

```bash
bash /tmp/game-event-pilot-install.sh --rollback
sudo --preserve-env=SSH_CONNECTION \
  bash /tmp/game-event-pilot-install.sh --rollback --apply
```

Rollback fails closed if the agent is active or enabled, an activation marker
or credential exists, any state file was written, an installed file hash has
drifted, or the game runtime contains a plugin overlay. It removes only the
verified unactivated release, unit, default environment, marker, and empty
state directories. Active-pilot rollback is intentionally not implemented by
this installer.

## Activation And Active Rollback

`ops/gameserver/game-event-pilot-activate.sh` implements the host-local state
machine without provisioning identity or running it automatically. Every
operation is plan-only without `--apply`, and neither systemd unit is ever
enabled across boot.

The base activation accepts a target-specific identity file with this exact
shape:

```text
schema_version=1
server_id=<canonical-lowercase-server-uuid>
api_base_url=https://api.goldsrcops.com/
token_endpoint=https://<tenant>.auth0.com/oauth/token
client_id=<machine-client-id>
audience=https://api.goldsrcops.com
permission=ingest:game-events
server_id_claim=https://goldsrcops.com/claims/server_id
```

Keep this file outside Git as `root:root` mode `0600` under a root-owned parent
that is not group- or world-writable. It contains no client secret. Apply reads
the secret only from redirected stdin and stores it as the existing
owner-only systemd credential. Before changing the game tree, the script asks
Auth0 for a token and inspects the returned JWT contract: exact issuer and
audience, one non-empty subject, exactly one `ingest:game-events` permission,
the exact server binding, a usable expiration, and no human role claim. The API
still performs the authoritative signature, issuer, audience, lifetime,
permission, and route-binding validation when the event is delivered.

The agent accepts the ordinary owner-only credential modes and the exact
read-only `0440` presentation used by systemd for an ACL-backed service
credential. The latter exception applies only to an immediate, non-symlink
file in the exact `$CREDENTIALS_DIRECTORY`; it does not relax permission checks
for configuration files or arbitrary secret paths.

The installed unit also performs a one-shot access-token preflight before each
agent start. It uses the same unprivileged service account, systemd credential,
environment, HTTP stack, and sandbox as the delivery worker. Base activation
therefore fails and rolls back before producer enablement if that runtime path
cannot obtain a token; no gameplay event is required to diagnose the failure.

Review the complete workflow and each transition independently:

```bash
bash ./ops/gameserver/game-event-pilot-activate.sh
bash ./ops/gameserver/game-event-pilot-activate.sh --activate
bash ./ops/gameserver/game-event-pilot-activate.sh --enable-producer
bash ./ops/gameserver/game-event-pilot-activate.sh --seal-event
bash ./ops/gameserver/game-event-pilot-activate.sh --enable-delivery
bash ./ops/gameserver/game-event-pilot-activate.sh --rollback
```

Base activation requires the reviewed identity and escrowed secret:

```bash
<approved-secret-producer> | \
  sudo --preserve-env=SSH_CONNECTION \
  bash /tmp/game-event-pilot-activate.sh \
    --activate \
    --identity-file /root/game-event-agent.identity \
    --client-secret-stdin \
    --apply
```

It re-verifies the content-addressed release and every payload hash, requires an
active/disabled and still plugin-free game service plus empty dormant agent
state, and records the original game invocation and restart count. It preserves
the exact bytes and metadata of `liblist.gam`, the exact dormant agent
environment, a root-only copy of the non-secret machine identity, and whether
the parent `addons` directory existed. It then rechecks those inputs and the
game invocation after the token request. With rollback armed, it stops the
game, installs only the manifest-pinned Metamod-R/AMX Mod X/ReAPI/producer
overlay, creates owner-only spool directories, replaces the loader, and starts
the game and spool-only agent. Producer and delivery remain off. Both services
must be active, boot-disabled, at zero automatic restarts, the sole game-port
listener must belong to the game service control group, and the game process
must map all three native modules; the queue and every spool state must be
empty.

The controlled progression is:

1. Verify external A2S reachability and zero bots after base activation.
2. Run `sudo bash /tmp/game-event-pilot-activate.sh --enable-producer --apply`.
3. Complete exactly one controlled real round boundary.
4. Immediately run
   `sudo bash /tmp/game-event-pilot-activate.sh --seal-event --apply`.
5. Require exactly one pending local event, no in-flight item, receipt, dead
   letter, rejected file, or other residual spool state; recheck A2S and bots.
6. Run
   `sudo bash /tmp/game-event-pilot-activate.sh --enable-delivery --apply`.
7. Require the local queue and all spool states to return to zero, then verify
   the API receipt/idempotency evidence and one Reader-visible anonymous event
   from the control plane.
8. Run `sudo bash /tmp/game-event-pilot-activate.sh --rollback --apply` and
   repeat A2S, bot, service-state, and plugin-free-tree checks.

The producer cannot be enabled from the spool-only stage unless local state is
empty. Sealing fails unless exactly one event remains. Delivery cannot start
until that event is sealed and the producer is off. A failed mutating
transition, lost controlling session, multiple events, dead letter, rejected
spool file, module-load failure, service restart, or delivery timeout invokes
the same active rollback. Rollback stops both services, removes only the
pilot-owned live roots and credential, discards pilot-local SQLite/spool state,
restores the original bytes and metadata, restarts the original game service,
and leaves the dormant agent inactive and disabled. If restoration cannot be
proved, it retains the owner-only recovery state and reports an incomplete
rollback instead of claiming success. Explicit rollback also tolerates a
missing or one-transition-stale activation gate left by interruption between
the two atomic state writes; the root-only activation state and verified backup
files remain authoritative for recovery.

The deterministic repository contract is:

```bash
bash ./tools/smoke/gameserver-game-event-pilot-activate.sh
```

This smoke covers syntax, sanitized plan-only behavior, strict identity and
state parsing, token-claim rejection, loader/config rendering, transition
ordering, stdin-only secret transport, service boot-disablement, and active
rollback structure. It does not load 32-bit modules, query production Auth0,
restart a host service, send an event, or prove external A2S/API/Reader behavior.

## Bounded Production Attempt

The controlled attempt on 2026-09-16 reached spool-only activation, passed
external A2S with zero bots, captured exactly one anonymous round event, and
sealed the producer window. Delivery then made seven unsuccessful scheduled
attempts. Sanitized ingress checks found no matching Caddy request or API log,
and the durable inbox and Reader projection remained empty. The event therefore
was not accepted or persisted; this attempt is not delivery evidence.

Explicit active rollback subsequently restored the plugin-free game runtime.
The game service was active and boot-disabled with zero automatic restarts, the
agent was inactive and boot-disabled, temporary identity and credential state
were absent, A2S remained reachable with zero bots, and the control plane had
no open incident or residual game-event record. The pre-ingress failure remains
unresolved. A later attempt must use the service-context OAuth access-token
preflight described above before producer enablement or player participation.

A second bounded activation attempt reached that service-context preflight and
failed closed before contacting the token endpoint. The agent rejected
systemd's ACL-backed `0440` credential presentation under its earlier generic
owner-only mode check. The producer and delivery remained off, no player round
was requested, and no API or durable-inbox evidence was created. Explicit
rollback again restored the active, boot-disabled, plugin-free game service
with zero automatic restarts and left the agent inactive and boot-disabled;
temporary identity, credential, activation, and plugin state were absent. A
narrow local fix now recognizes only the exact systemd-managed read-only form;
another reviewed bundle and preflight are still required before this becomes
production evidence.

## Production Execution Gate

Before using `--apply`, the operational session must still:

1. Provision one server-bound OAuth machine identity with only
   `ingest:game-events` and retain its secret outside the repository.
2. Capture current A2S, bot count, durable API state, game service continuity,
   and sanitized rollback evidence outside Git.
3. Execute each stage separately and stop whenever its named external gate has
   not passed.
4. Use a reviewed control-plane verification path for receipt/idempotency and
   Reader projection; do not improvise with production SQL or expose the event
   payload or token in shell history.
5. Complete active rollback and prove the exact plugin-free runtime and service
   boundary before closing the pilot.

One successful bounded event would prove only that the reviewed pilot path
worked once. It would not establish long-term reliability, broad plugin
compatibility, an achieved SLO, or permission for unattended rollout.
