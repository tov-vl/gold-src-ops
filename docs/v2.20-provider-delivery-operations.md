# v2.20 Provider Delivery Operations

Status: local API, database, Operator BFF/UI, and deployment-contract slices
implemented; not published or deployed.

## Objective

Give an authenticated operator a bounded way to inspect and record review of a
terminal provider outbox message without changing delivery truth. This closes
the immediate operational gap exposed by the preserved v2.19 HTTP `403` while
keeping sustained provider delivery and production rollout separately gated.

## Local Contract

The receiver owns four internal endpoints under
`/internal/v1/provider-delivery`:

- `GET /dead-letters?limit=&cursor=` returns at most 100 newest terminal
  messages with a stable `(DeadLetteredAtUtc, MessageId)` cursor;
- `GET /dead-letters/{messageId}` returns one terminal message;
- `POST /dead-letters/{messageId}/review` appends one review record and requires
  a canonical UUID `Idempotency-Key`;
- `GET /reviews/{requestId}` returns the immutable review result.

Responses contain message, source-event, and incident identifiers; action and
bounded attempt/failure metadata; timestamps; and optional review metadata.
They do not contain the provider envelope, raw response body, receiver
authorization, provider endpoint, provider authorization, or database
connection material.

`ProviderOperations:Enabled` defaults to `false`. Disabled endpoints return
`404`. When enabled, `ProviderOperations:Authorization` is mandatory, bounded,
and compared independently from both receiver-ingestion and provider-delivery
authorization.

## Persistence And Invariants

Migration `20260921082622_AddProviderOutboxReviews` creates only
`receiver.provider_outbox_reviews`:

- `RequestId` is the primary key and idempotency identity;
- `MessageId` has a unique index and a restrictive foreign key to
  `provider_outbox_messages`;
- `RequestedBy`, `Reason`, and `ReviewedAtUtc` are append-only review evidence;
- existing outbox rows are not backfilled or rewritten.

An accepted review leaves the source row in `DeadLetter`. It does not alter
attempt count, error, timestamps, claim fields, per-incident ordering, or later
message eligibility. Exact retries return the stored review. Changed intent
with the same request ID, a second request ID for the same message, missing
messages, and non-dead-letter messages fail closed.

## Operator BFF And UI

The Web host now owns a separate, disabled-by-default `ProviderOperations`
client. When enabled, its receiver base URL and exact authorization value stay
server-side; outside Development the authorization must come from a one-line
file-backed secret. It is not derived from the interactive user's access token
and is never returned to browser code.

Operator-only pages provide a bounded dead-letter list, one-message detail,
and immutable review receipt. Review submission requires antiforgery
validation, a ten-minute single-use confirmation bound to subject, message,
and request UUID, and a non-empty audit reason. `RequestedBy` is always the
authenticated subject rather than a form value. A transport timeout redirects
to receipt reconciliation and is never retried automatically.

The pages state the behavior boundary directly: review appends evidence only.
It does not retry, replay, delete, reclassify, or unblock provider delivery.
Reader sessions cannot access these routes, and the existing public and Reader
contracts remain unchanged.

## Deployment Contract

The receiver entrypoint now reads a dedicated
`provider-operations-authorization` file only when
`ProviderOperations:Enabled` is true. Missing, empty, multiline, and oversized
values fail closed before the process starts. The base receiver and Web Compose
contracts explicitly keep provider operations disabled and do not mount this
secret.

Two reviewed overlays activate the cross-stack path. The receiver overlay
mounts the authorization without enabling provider delivery or changing
`CatchUp`; the Web overlay mounts the same file and points its server-side
client at the private `goldsrcops-alert-receiver` alias. The public Caddyfile is
unchanged in production and continues to forward only
`POST /api/v1/availability-events`.
The tracked preflight verifies this shared-file, private-address, disabled-
delivery boundary without reading placeholder secrets in CI.

The extended smoke also exposed and corrected an ordering defect in the
standalone Caddyfile: its allowlisted proxy and fallback response now use the
same mutually exclusive `handle` structure as production. The accepted route
surface did not expand.
