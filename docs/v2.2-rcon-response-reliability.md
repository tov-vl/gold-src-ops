# RCON Response Reliability

Status: implemented and locally verified for v2.2.0. Synthetic protocol and UDP
tests, the full quality gate, production container smoke, and isolated
owned-server verification are complete; protected-main integration and release
evidence remain.

## Why This Slice Is Next

GoldSrcOps already treats RCON commands as durable, auditable operations, but
the UDP client reads exactly one command-response datagram. A GoldSrc server can
flush a longer redirected console response through several ordinary
`A2A_PRINT` datagrams. Returning after the first datagram can therefore persist
a successful but incomplete result summary.

This is a correctness gap in an existing supported capability. It has higher
priority than adding another alert channel, bulk replay, a broker, service
extraction, or distributed polling, whose requirements remain hypothetical.
The change is also narrow: it does not require a public API or database-schema
change.

## Current Behavior And Evidence

`GoldSrcRconClient.ExecuteAsync` currently performs the challenge exchange,
sends the command, receives one datagram, and returns its parsed text. The
existing timeout covers the challenge and that single command response, while
`GoldSrcRconOptions.MaxResponseLength` bounds only the sanitized text persisted
in `CommandExecution`.

The ReHLDS reference implementation provides useful compatibility evidence:

- `SV_Rcon` redirects command console output to the request endpoint.
- `Con_Printf_internal` flushes the redirect buffer when another console write
  would exceed it.
- `SV_FlushRedirect` sends each flush as a normal connectionless `A2A_PRINT`
  datagram, and `SV_EndRedirect` flushes the final buffered text.

These RCON response chunks do not use the indexed split-packet envelope used by
A2S server queries. The reviewed path exposes no response id, fragment count,
or explicit completion marker. GoldSrcOps must therefore keep A2S split-packet
handling separate and treat RCON completion as a bounded receive-drain problem.

ReHLDS is compatibility evidence, not proof of every Valve HLDS or third-party
engine variant. Before release, the behavior must also be checked against an
owned GoldSrc server without sending commands to a third-party host.

## Goals

- Preserve the complete text from one or more RCON `A2A_PRINT` datagrams when
  they arrive within the bounded receive contract.
- Accept datagrams only from the resolved server endpoint.
- Keep one end-to-end command deadline across endpoint resolution, challenge,
  command send, first response, and additional response draining.
- Bound response datagram count and aggregate response bytes independently of
  the smaller persisted result-summary limit.
- Preserve cancellation and the existing timeout, authentication, protocol,
  and socket failure mappings.
- Never log command response text, command payload, or credential material.

## Non-Goals

- Retrying an RCON command automatically. A timed-out command may already have
  executed remotely.
- Claiming reliable delivery or perfect reassembly over UDP.
- Reusing the A2S split-packet parser for ordinary RCON response chunks.
- Adding IPv6, quoted-password support, new command types, or a management UI.
- Persisting complete console output beyond the existing bounded command
  result summary.

## Proposed Receive Contract

1. Start one end-to-end deadline before resolving the configured host.
2. Resolve an IPv4 endpoint and connect the UDP socket to that endpoint so
   unrelated senders cannot satisfy either receive operation.
3. Complete the existing challenge exchange inside the remaining deadline.
4. Send the RCON command and require the first valid `A2A_PRINT` datagram before
   the remaining command deadline expires.
5. After the first response, continue receiving valid response datagrams until
   a short response-drain interval elapses without another datagram.
6. Parse each response chunk without trimming its boundaries, concatenate text
   in receive order, and normalize whitespace only after the final chunk.
7. Fail with a protocol error instead of returning a known partial result when
   the byte ceiling, datagram ceiling, or end-to-end deadline is reached while
   response data continues to arrive.
8. Preserve caller cancellation as cancellation rather than mapping it to a
   timeout or protocol failure.

The response-drain interval is a completion heuristic because the legacy
protocol has no fragment metadata. A datagram delayed beyond that interval can
still be missed, and UDP loss or reordering cannot be detected. This residual
limit must remain documented even after multi-datagram support is added.

## Bounds And Configuration

The implementation keeps `Rcon:TimeoutMilliseconds` as the end-to-end deadline
and adds three independently validated settings:

| Setting | Default | Valid range |
| --- | ---: | ---: |
| `Rcon:ResponseDrainMilliseconds` | `100` | `10` to `1000` |
| `Rcon:MaxResponseDatagrams` | `32` | `1` to `256` |
| `Rcon:MaxResponseBytes` | `65536` | `5` to `1048576` |

The byte ceiling counts complete UDP datagrams, including each four-byte
connectionless header. It is intentionally separate from
`Rcon:MaxResponseLength`, which remains the post-sanitization character bound
for persisted command history. Existing deployments remain valid when the new
settings are omitted, while explicitly invalid values fail startup.

The initial defaults are covered by synthetic tests with response chunks sent
inside the quiet interval and completion after that interval elapses. They
were retained after the owned-server verification described below.

## Owned-server Verification

On 2026-08-28, the guarded workflow ran end to end against an ephemeral,
loopback-only Counter-Strike 1.6 server using ReHLDS 3.14.0.857 and
ReGameDLL_CS 5.28.0.756. The image was built from source commit
[`f194e45`](https://github.com/jstnmthw/rehlds-docker/commit/f194e45043b9ea783d40292ddcdce39305424ee4);
the build verified pinned SHA-256 checksums and the ReHLDS release signature.

The normal guarded `say` command completed successfully. A second, read-only
`cvarlist` command exercised a longer response through the authenticated API
and durable dispatcher. A loopback UDP proxy recorded only monotonic timing,
direction, datagram length, and response type; it did not record packet payloads,
the RCON password, credential references, or bearer tokens.

| Observation | Result |
| --- | ---: |
| Command terminal status | `Succeeded` |
| Command-response datagrams | `12` |
| Aggregate command-response wire bytes | `16549` |
| Command send to first response | `9.999 ms` |
| First-to-last response span | `75.615 ms` |
| Maximum observed inter-datagram gap | `8.206 ms` |
| Dispatcher lifecycle duration | `212.225 ms` |

All 12 command-response datagrams carried the ordinary `A2A_PRINT` type. The
largest observed gap remained well below the 100 ms quiet interval, so the
default is retained. This is representative evidence from one controlled
ReHLDS build, not a completeness guarantee for other server variants, network
paths, packet loss, or production load.

## Acceptance Matrix

| Scenario | Expected result |
| --- | --- |
| One valid command-response datagram | Existing successful behavior remains compatible. |
| Several valid response datagrams | Text is concatenated once, in receive order. |
| No first response before the deadline | Existing timeout result is preserved. |
| Quiet interval after at least one response | Collected response is completed successfully. |
| Continuous responses reach the overall deadline | Protocol failure; no partial success is persisted. |
| Datagram or byte ceiling is exceeded | Protocol failure; no partial success is persisted. |
| Malformed or non-`A2A_PRINT` command response | Existing protocol failure mapping is preserved. |
| Bad-password response | Existing authentication failure mapping is preserved. |
| Caller cancels during any receive | Cancellation is propagated. |
| Datagram from another endpoint | It cannot satisfy the connected UDP socket receive. |

## Implementation Status

Completed in the reviewable reliability slice:

1. Protocol parsing preserves ordinary `A2A_PRINT` chunk boundaries until one
   final normalization pass.
2. The response collector enforces the configured datagram and aggregate-byte
   ceilings.
3. A connected UDP socket and one cancellation-backed deadline cover endpoint
   resolution, challenge, command send, first response, and quiet draining.
4. Synthetic UDP tests cover single and multi-datagram success, quiet
   completion, challenge and first-response timeout, caller cancellation,
   malformed responses, both ceilings, continuous response flow, and endpoint
   isolation.
5. Tracked defaults and RCON operations documentation describe configuration,
   failure behavior, and residual UDP limits.
6. The full local quality gate and production container smoke pass.
7. Guarded single- and multi-datagram commands pass against an isolated local
   ReHLDS instance, with payload-free timing and framing evidence recorded
   above.

## Compatibility And Rollout

- Public HTTP contracts and authorization policies remain unchanged.
- No EF Core migration is required.
- Existing single-datagram responses remain supported.
- New receive settings have safe defaults, so existing deployments require no
  configuration change.
- Rollback restores the one-datagram limitation without changing persisted
  data.
- Live verification uses only an owned server and a read-only, output-producing
  command. It must not weaken the guarded RCON smoke workflow or automatically
  retry an ambiguous command.
