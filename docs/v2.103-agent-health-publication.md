# v2.103 - Agent health publication after interrupted writes

## Scope and implementation

The v2.95 health writer used one fixed `.health.json.tmp` file with exclusive
creation. An interrupted process could leave that file behind, preventing every
later snapshot while the import/delivery workers continued. This slice gives
each publication attempt a unique sibling temporary name, retains exclusive
creation and replaces the destination only after complete serialization and
stream disposal. Finally cleanup touches only a file actually created by that
attempt. Existing orphan evidence is neither overwritten nor removed.

The schema-1 health/status contract, strict reader, freshness budgets, sanitized
write-failure logging and worker outcome semantics remain unchanged. The writer
does not create missing parent directories, change queue/spool behavior or turn
diagnostic success into event delivery evidence. A failed write leaves the last
published bytes intact; a later cycle can publish again when storage recovers.

The update is R3 through the existing agent-only upgrade/rollback workflow.
Product addon 0.39.0, game process, credentials, permissions and control-plane
services remain outside mutation scope. No queue migration or synthetic live
event is part of acceptance.

## Repeated upgrade compatibility

Source and read-only target review found that the upgrade preparer recognized
only a legacy scheduled-capture consumer without the agent-pending gate. The
already installed v2.95 consumer contains that gate. Preparation now accepts
either the original legacy boundary or the exact recognized existing block.
It rejects duplicated/altered gates and preserves existing gate bytes without
reinsertion. Apply/rollback skip byte-identical references, retaining the inode
of an unchanged capture consumer. The durable claim, locks, runtime guard,
queue/spool refusal and exact rollback graph remain required.

## Verification gates

Focused C# cases cover empty/partial orphan files from both old and unique-name
attempts, repeated successful publication without new leftovers, failed rename
cleanup, missing-parent preservation/recovery and concurrent readers during
both loop updates. A worker case confirms idle import progress despite an old
orphan, preserving the original file.

The complete local Quality Gate passed with 792 unit, 454 Web and 54 receiver
tests, clean formatting/build and no vulnerable packages. The 62 opt-in browser
cases were skipped locally; required Browser Smoke is their separate CI gate.
The 12-case networkless Linux upgrade fixture passed legacy apply/rollback,
repeat upgrade with inode preservation, unknown/duplicate gate refusal, partial
install, completed failure rollback, interruption/no retry and unchanged queue/
game boundaries. Scoped InspectCode and complete required CI remain separate
recorded gates. InspectCode 2026.2.3.1 completed at Hint and higher with zero
errors, zero warnings and 11 notes. Existing grouped-record, constructor,
trailing-comma and reader-pattern suggestions were retained; the local writer
test helper remains before its assertions for test-flow readability. No
inspection settings or suppressions changed.

Before target apply, freeze the standalone Linux x64 package/source, old/new
reference graph, previous executable, queue source/sequence and settled spool.
Require current persistent and backup guards. Stage the reviewed installer in
the protected operator record, prepare one new hash-bound transition and review
its exact plan. Apply stops/starts only the agent, updates the already managed
hash-bound references and backup baseline, and retains old releases. Unknown
outcomes require reconciliation instead of a retry.

Published-binary acceptance must exercise the real Linux executable with orphan
files, advancing idle cycles, passive reads and unchanged synthetic queue bytes.
Production acceptance must independently establish the exact new executable,
unchanged game invocation, preserved queue identity/sequence/spool, advancing
idle health, valid guards, A2S and fresh monitor observations. No orphan is
injected into production. Stable promotion must reuse the accepted candidate
ZIP/checksum without rebuilding; no unrelated application images are published.

## Status and limits

Implementation, publication, agent-only target acceptance and stable promotion
completed on November 4. This prevents old temporary files from blocking future
publication; it does not make a full/unwritable disk
healthy or claim power-loss/fsync durability. A hard process kill can still
leave one temporary file from an interrupted attempt. Old evidence is retained
for explicit operator review; normal successful/handled-failure attempts clean
their own files without a directory scan or automatic orphan deletion.
