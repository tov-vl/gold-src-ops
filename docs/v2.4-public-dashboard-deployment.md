## Public Boundary

- `https://goldsrcops.com` serves the public Blazor static-SSR dashboard.
- `https://api.goldsrcops.com` remains the API origin.
- Caddy is the only process publishing host ports.
- The Web host calls the anonymous `/api/public/status` and
  `/api/public/a2s-history` routes over the private edge network. The browser
  receives rendered markup and static assets, not direct API access or
  credentials. The history route is part of the pending follow-up candidate,
  not the deployed `v2.4.0-rc.6` runtime.
- The API host allowlist includes its private Compose alias solely for that
  server-side call; Caddy still exposes only the public API hostname.
- The public request path does not require a credential. The authenticated Web
  extension receives only its own OIDC and Data Protection secrets; it receives
  no database, RCON, backup, or observability secret.

The public status projection remains deliberately aggregate-only. Server names,
addresses, provider identifiers, command data, credentials, and private
telemetry are outside this boundary.

## Historical A2S Projection

The anonymous history contract accepts only `window=24h` or `window=7d`; an
omitted value defaults to 24 hours and every other value returns a validation
problem. The API returns:

- 24 hourly buckets for the trailing 24-hour window;
- 28 six-hour buckets for the trailing seven-day window;
- `operational`, `degraded`, or `unreachable` for buckets with observations;
- `unknown` for a bucket without a recorded poll;
- an observed reachability percentage that excludes unknown buckets.

The database query aggregates snapshots only for currently enabled servers and
uses a half-open `[from, to)` interval. Each recorded probe has equal weight:
the percentage is reachable probes divided by all recorded probes in the
window. The one-minute output cache varies by the validated `window` value.
Neither response level includes server IDs, names, addresses, provider details,
maps, players, bots, raw versions, failure reasons, or sample counts.

This projection describes A2S reachability observed by the control plane. It is
not the independent external API-availability stream, and it neither activates
nor proves `API-01` or another SLO.

## Artifact Contract

One signed annotated release tag publishes two independently digest-addressed
`linux/amd64` images:

```text
ghcr.io/tov-vl/gold-src-ops@sha256:<api-digest>
ghcr.io/tov-vl/gold-src-ops-web@sha256:<web-digest>
```

The API and Web images carry the same source revision and release version. The
Web image is built from `Dockerfile.web`, runs as UID `1654`, contains neither
the SDK nor Development settings, and has a built-in `/health/live` probe.
Candidate and revision tags are write-once. A stable Web tag promotes the
verified candidate digest for the same source revision and base version.

## Runtime Contract

The `web` Compose service:

- is part of the `runtime` profile;
- uses an immutable digest reference;
- has a read-only root filesystem, bounded `/tmp`, no Linux capabilities, and
  `no-new-privileges`;
- exposes port `8080` only to the private `edge` network;
- trusts forwarded headers from the configured Caddy address only;
- accepts the public hostname plus `localhost` for its image-local health
  probe;
- restarts unless explicitly stopped;
- renders a clear unavailable state without substituting stale data when the
  API cannot be reached.

Caddy does not depend on Web health because it also owns the API ingress. The
rollout verifies Web health before enabling its site, while a later Web failure
does not gate API startup or restart.

The initial deployed anonymous static-SSR slice did not persist ASP.NET Core
Data Protection keys. The authenticated Reader extension adds an encrypted,
persistent key ring and a bounded process-local session store as documented in
`docs/v2.4-reader-portal.md`.

## Rollout

1. Merge the reviewed source revision after `Quality Gate` and `Container
   Smoke` pass.
2. Create and verify a signed annotated release-candidate tag.
3. Wait for both published-image verification jobs and record both digests.
4. Create and check the encrypted off-host PostgreSQL backup before changing
   the API process.
5. Run production preflight with the candidate API and Web digest references.
6. Run the migration action from the candidate API image. A no-op migration is
   still a required compatibility gate.
7. Replace the API while preserving its single polling and retention-worker
   configuration, then verify public liveness, readiness, anonymous status, and
   the authenticated Reader/Operator matrix.
8. Start the Web service and verify its container health through the private
   edge network.
9. Route `goldsrcops.com` to the control plane, reload Caddy through Compose,
   and wait for successful certificate issuance.
10. Verify the public dashboard at desktop and mobile widths, security headers,
    API-unavailable rendering, container restart counts, and absence of new
    incidents or durable-queue backlog.

Do not switch DNS or Caddy routing before both candidate digests, API
compatibility, and the Web health endpoint have passed.

## Rollback

Keep the previous API digest and configuration until the post-deployment checks
complete.

- A Web-only failure is rolled back by removing its Caddy site and stopping the
  Web service; the API remains available at its existing hostname.
- An API compatibility failure restores the previous API digest without
  down-migrating the database. The public Web route stays disabled until its
  required anonymous status endpoint is available again.
- DNS rollback restores the previous root-domain record only after confirming
  that the old destination is intentional.
- Persisted PostgreSQL, Caddy, Prometheus, and Grafana volumes are not removed
  during either rollback.

Repository checks:

```powershell
pwsh -NoProfile -File .\ops\production\preflight.ps1 `
  -EnvironmentFile .\ops\production\deployment.env.example `
  -ContractOnly

pwsh -NoProfile -File .\tools\smoke\container.ps1
pwsh -NoProfile -File .\tools\smoke\web-container.ps1
```

Target evidence must record only sanitized source revisions, image digests,
HTTP results, service health, and restart continuity. Host addresses, provider
identifiers, tokens, secret paths, database payloads, and private monitoring
details remain outside Git.
