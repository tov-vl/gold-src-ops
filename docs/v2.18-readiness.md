# GoldSrcOps v2.18 Release Readiness

Review date: 2026-09-18. Status: stable release published. Candidate
publication, production acceptance, exact-digest stable promotion, and the
GitHub Release are complete.

## Scope

The v2.18 release scope is Pending Delivery Triage:

- a Reader-authorized bounded pending-delivery endpoint;
- versioned opaque cursor pagination in existing claim-index order;
- safe retry and linked incident/server display metadata;
- explicit visibility for missing incident links;
- a static-rendered Reader page and a link from Alert Delivery Overview;
- focused application, cursor, PostgreSQL, authorization, Reader-client, SSR,
  token-boundary, and desktop/mobile browser coverage.

The slice adds no migration, background worker, retry-policy change,
authorization role, production identity, mutation permission, delivery
activation, receiver configuration, event producer, or game-host artifact.

## Claim Boundary

Acceptance can show that the exact candidate returns naturally existing pending
rows through the Reader policy, preserves claim-index ordering, renders only the
reviewed safe fields, and does not mutate queue state. It can also show public
health, exact candidate identity, runtime continuity, and parity with bounded
owner-only queue evidence.

Acceptance cannot prove dispatcher or receiver liveness, delivery success,
historical queue behavior, retry correctness under failure, alert latency,
long-term reliability, high availability, or an achieved SLO. It must not
change production data to manufacture pagination, a missing relation, a retry,
or any other visual state.

## Compatibility And Risk Class

This is an R1 additive read-only API/Web release:

- existing routes and response contracts are unchanged;
- API and Web are the only affected runtime components;
- the query uses the existing `IX_outbox_messages_pending_claim` order and adds
  no schema or persistence-model change;
- the endpoint and page reuse Reader authorization and expose no mutation;
- no backup, restore rehearsal, migration rehearsal, game-host activation,
  gameplay capture, Auth0 change, RCON action, alert delivery activation, queue
  replay, or queue drain is a release gate.

## Production Acceptance Result

The exact candidate API and Web digests were deployed together without a
migration and without recreating PostgreSQL, Caddy, telemetry, or the game
service. Four read-only samples over 181 seconds retained public API and Web
health, exact candidate version, revision, and digests, seven healthy
containers, and zero container restarts. One controlled server remained
enabled, online, recently polled, A2S-reachable, and at zero bots.

No open or newly opened incident, processing outbox row, dead letter, or
incomplete command appeared. Scheduled-backup evidence remained fresh. Alert
delivery stayed disabled, and the two naturally existing pending rows retained
their baseline count and oldest-pending value. No queue row, incident,
monitoring setting, delivery setting, database schema, or game-host state was
changed to make the check pass.

An existing Reader session rendered two pending rows in claim order with zero
attempts and zero missing incident links. The bounded page exposed the reviewed
event, retry, server-display, and incident-link metadata without a payload,
delivery error, claim identity, destination, address, credential, token, or
mutation control. The anonymous pending API request returned `401`.

Independent checks before and after rollout retained the active,
boot-disabled, zero-restart game service and its single owned UDP listener. The
runtime remained plugin-free, and the dormant game-event agent remained
inactive and boot-disabled. All private rollout evidence was stored as regular
`root:root` files with mode `0600`.

## Stable Promotion And Closure

Signed stable tag `v2.18.0` targets the exact accepted candidate revision.
Stable workflow
[#35335400426](https://github.com/tov-vl/gold-src-ops/actions/runs/35335400426)
skipped both image-build paths, promoted the candidate API and Web digests, and
passed both published-image smoke jobs. The
[GitHub Release](https://github.com/tov-vl/gold-src-ops/releases/tag/v2.18.0)
is published.

The failed `rc.1` workflow is retained as an immutable pre-publication anomaly.
No `rc.1` image reached production. The race fix, replacement candidate,
production acceptance, stable promotion, and closure evidence preserve that
history instead of rewriting the failed tag.

This readiness record defines bounded release evidence. A short production
smoke is not proof of long-term reliability or an achieved SLO.
