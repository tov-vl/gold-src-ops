# v2.111 - Active game-host warnings in the Operator portal

## Scope

Extend the existing private `/operator/game-host-health` page and API response
with a compact list of the 17 existing agent, player-backup, storage and
resource warning rules. Each active entry contains a known rule name, fixed
component, Pending/Firing state, application-owned description and a fixed
Grafana detail link when private dashboard access is configured. Firing sorts
before Pending; the remaining order is deterministic. There are no write,
acknowledgement, silence, retry or threshold controls.

Existing Operator authorization, stable-subject validation, server-side BFF
tokens and no-store behavior are preserved. Public/Reader surfaces, database,
game addons, agent, rule definitions, Alertmanager, IRM and Grafana are unchanged.

## Source and validity

The existing health query and a new read-only Prometheus `/api/v1/rules` read
run concurrently. Both retain a five-second total transport/body deadline,
64 KiB response limit, no redirects/cookies and no automatic retry. The rules
request filters exactly four existing groups, requests alerting rules only
and excludes per-instance active-alert payloads. It accepts at most 17 rules
and never follows pagination. Caller cancellation propagates.

The rules endpoint is used instead of treating an empty `ALERTS` vector as
health proof: it exposes evaluation health and the last evaluation of each
loaded rule, including inactive rules. A read-only production preflight
confirmed the required fields on all 17 existing rules. This API's payload
compatibility is tested explicitly; missing or changed fields fail closed.

Application requires the exact known rule identities, components, warning
severity, group membership, healthy evaluations and recognized states.
Missing/duplicate/unknown rules or future timestamps produce Unknown. If any
otherwise valid rule evaluation is older than 60 seconds, the list is Stale.
Only a complete fresh set of inactive rules produces the explicit empty
success. The displayed observation time is the oldest evaluation in that set.
Unavailable/stale lists contain no purported current active entries.

Warning availability is independent of the existing five cards and values.
A monitor-unavailable warning can therefore remain readable while its host
card is unknown. Rule state and metric observations are separate snapshots,
so cards can lag an evaluation. This is not atomic whole-host health proof.

Provider query text, annotations, error messages, filenames, per-instance
labels and active-alert payloads are never projected into API/Web output.
Descriptions and dashboard destinations come from fixed application data.
This list excludes other application warnings and the monitoring heartbeat;
it does not prove external notification delivery.

## Compatibility and delivery

The optional `warnings` response field is additive. Old Web versions ignore
it; new Web versions show unavailable warnings when an older API omits it.
An invalid warning read does not hide other usable health measurements.
The existing feature switch and trusted Prometheus origin apply to both reads;
no new configuration, credential, permission, port or service is introduced.

R1 release `2.111.0`: deploy only independently verified API/Web digests.
Preserve the accepted v2.110 image references and exact deployment inputs.
Rollback recreates only API/Web with those immutable images; there is no
migration or durable-state conversion. Candidate/stable publication may also
verify an AlertReceiver image, but the running receiver is not updated.

Required gates: projection/protocol/freshness/authorization and mixed-version
tests, static SSR/no-JavaScript browser and responsive/token-boundary checks,
complete local .NET gate, scoped InspectCode, required PR/tag CI, independent
published-artifact checks, bounded runtime and existing Operator-page
acceptance, same-digest stable promotion and a final evidence PR.
