# План сохранности игровых данных после SIGKILL

Статус: план от 2026-11-17; локальная реализация отдельно разрешена владельцем.
Результаты и оставшиеся gate записаны в [отчете реализации](player-data-durability-implementation.md).
Этот документ не разрешает production-развертывание. Основание - воспроизведенная
[потеря изменений после SIGKILL](player-data-crash-acceptance.md).

## Рекомендуемая граница потери

Предлагается **ноль потерянных подтвержденных сохранений при падении процесса**.
Подтверждение означает успешный явный commit, а не совпадение `nvault_lookup`
с данными в памяти. Для сохраненных kills/deaths, рекорда серии, языка, оружия,
HUD и сохраненного имени используется одна и та же граница.

Допускается потеря текущей незавершенной операции. Она также может оказаться
записанной до падения, хотя вызывающий код еще не получил подтверждение.
Автоматически повторять такую операцию после рестарта нельзя. Завершенный
обработчик учета смерти должен иметь подтверждения всех его сохранений.

Периодическое окно в 5-30 секунд не предлагается: игрок уже видит результат
сохранения, а произвольная потеря последних убийств или выбранных настроек
затрудняет понимание поведения. Записи короткие; сначала следует измерить
стоимость flush для одного события, прежде чем вводить задержку подтверждения.

Это не нулевой RPO для выключения питания или потери диска. `fflush` передает
буфер процесса операционной системе и не заменяет `fsync`. При ошибке записи,
превышении лимита или недоступности хранилища игра продолжает работать с
connection/map-состоянием, но не объявляет новые изменения сохраненными.

Событие убийства не становится транзакцией между двумя vault: падение внутри
обработчика может оставить часть его неподтвержденных изменений. Если нужна
атомарность всех счетчиков обоих игроков и серии как единого события, это
отдельное расширение формата и контракта, за пределами этого предложения.

## Выбор механизма

Рекомендуется узкое исправление **закрепленного Linux-модуля nVault**: явный
commit журнала и безопасный checkpoint с сохранением существующего формата.
Addon подтверждает сохранение только после успешного commit. Исходный AMXX
и зависимости остаются закрепленными; модуль публикуется отдельным проверяемым
артефактом, а не подменяется внутри прежнего AMXX-архива.

| Вариант | Оценка |
| --- | --- |
| Таймер с `nvault_close/open` каждые несколько секунд | Не выбран: переписывает весь vault, оставляет окно потери и не защищает падение в момент checkpoint |
| `fflush(0)` или открытие того же journal из Pawn | Не выбран: в закрепленной реализации `fflush(0)` возвращает ошибку; отдельный файловый handle не сбрасывает буфер nVault |
| Только flush после записи в модуле | Недостаточно: повторное падение при восстановлении и переписывании checkpoint остается отдельной проблемой |
| Commit плюс безопасный checkpoint в закрепленном модуле | Рекомендуется: один источник данных, прежние форматы и закрытые backup, явный результат записи |
| Собственный WAL/SQLite/внешняя БД для addon | Резервный вариант, если модуль нельзя воспроизводимо сопровождать: потребует миграции, новых правил backup и более сложного отката |

Первый этап - проверить возможность воспроизводимой сборки и ABI на целевых
ReHLDS/AMXX/ReAPI. Если этот gate не проходит, выбор пересматривается до
изменения production. Поддержка Windows-модуля здесь не заявляется.

## Изменения в модуле

1. Добавить явный проверяемый commit для одного vault, например
   `nvault_process_commit(handle)`, и идентификатор поддерживаемого контракта.
   Точные имена фиксируются при прототипировании. Успех требует полного append,
   успешного `fflush`, отсутствия `ferror` и ранее обнаруженных ошибок записи.
   Нынешние `nvault_set`/`close` не имеют пригодного контракта возврата ошибки;
   нельзя молча трактовать их текущий результат как подтверждение сохранности.
2. Сохранять ошибку записи в состоянии соответствующего handle. После short
   write/flush error не продолжать append за поврежденным хвостом и не снимать
   ошибку успешным readback. Commit возвращает отказ, история сохраняется для
   отдельной сверки. Не добавлять автоматический повтор неизвестной записи.
3. Писать checkpoint в новый файл в том же каталоге: ограниченная сериализация,
   проверка всех write/flush/close, независимое повторное чтение и проверка
   формата. Прежний vault и журнал остаются до успешной публикации.
4. Публиковать checkpoint атомарной заменой файла в пределах одной файловой
   системы Linux. Только после нее закрывать/удалять прежний журнал и открывать
   новый. Не переписывать основной `.vault` через `fopen(..., "wb")`.
5. При startup сначала проверить исходные файлы и воспроизвести журнал,
   затем безопасно опубликовать восстановленный checkpoint. Только после этого
   очищать журнал и разрешать новые записи. Ошибки чтения, replay и открытия
   журнала должны приводить к отказу открытия, а не к пустому успешному vault.
6. Проверить все переходы между публикацией checkpoint и очисткой журнала.
   Повтор старого журнала поверх уже опубликованного checkpoint допустим только
   после доказательства идемпотентности Insert/Remove/Clear/Prune и timestamp.
   Если доказательство не проходит, нужен отдельный формат поколения/маркер;
   это останавливает обещание совместимости и требует пересмотра плана.

Сам по себе временный файл не является принятой копией. Незавершенные файлы
не заменяют валидный vault и не удаляются автоматически до классификации.
При невозможности однозначно выбрать состояние storage становится unavailable.

## Интеграция с addon

- До использования storage проверить точную capability/version модуля. Старый
  модуль не должен позволять новому addon заявлять новую гарантию. Определить
  явное поведение отсутствующей capability: storage unavailable с работающей
  connection/map-частью, либо отказ совместимого пакета до старта игры.
- Покрыть все пути записи: `SavePlayerStats`, `SavePlayerPreferences`,
  `RecordSavedStreak`, `SaveHudPreference`, `RememberLeaderName` и прямые записи,
  найденные повторным аудитом. Не ограничиваться двумя полями из crash-fixture.
- Устанавливать saved/confirmed-состояние и выдавать сообщения о сохранении
  или повышении ранга после commit и readback. Readback остается проверкой
  значения, commit - отдельным подтверждением выхода байтов из процесса.
- При отказе переводить соответствующий storage в ошибку через существующие
  bounded status/error-поля. Не выводить ключи, имена или содержимое vault в
  метрики/логи. Новый dashboard и новые права доступа не входят в этап.
- Изменения памяти, рейтинга и записи должны иметь описанный порядок. После
  отказа UI не должен показывать неподтвержденные totals как сохраненные.

Предварительные ограничения - прежние лимиты размеров backup и индекса;
лимиты journal/операций задаются явно до реализации. При их достижении нельзя
бесконечно накапливать журнал, зависать в игровом кадре или стирать историю.
Нужен bounded checkpoint либо отказ новых сохранений с сохранением старых данных.
Точные значения выбираются по инвентаризации и нагрузочному измерению; размер
реальных vault и список других потребителей nVault сейчас не проверялись.

## Проверки и критерии приемки

| Группа | Обязательная проверка |
| --- | --- |
| Исходная регрессия | Прежний модуль воспроизводит потерю; новый проходит тот же сценарий без test-only flush/close |
| Подтвержденные записи | SIGKILL сразу после commit сохраняет все обновленные totals, серию, язык, оба оружия, HUD и имя двух игроков; перестановка слотов не смешивает данные |
| Незавершенная операция | Падение до append, в середине записи и до возврата commit допускает старое или полностью новое значение; не допускает повреждения ранее подтвержденных значений |
| Повторный crash | Kill во время startup replay, создания/flush/публикации checkpoint, до/после очистки журнала; минимум два последовательных падения до штатного quit |
| Идемпотентность | Повтор журнала после опубликованного checkpoint не меняет counters, timestamps и результат Remove/Clear/Prune; нет автоматического повтора игровых событий |
| Ошибки I/O | Short write, ENOSPC, read-only каталог, flush/close/rename failure, ошибка открытия журнала; commit не подтверждается, исходные файлы сохраняются |
| Повреждения и лимиты | Оборванный последний record не отменяет подтвержденный префикс; повреждение середины, чужой temp или превышение лимита не превращаются в пустой healthy vault |
| Игровые регрессии | Все прежние 26 native-сценариев, saved streak/ranks/preferences и независимость игроков; отдельные отрицательные проверки commit и checkpoint |
| Backup/совместимость | Синтетическая старая копия открывается новым модулем; новая закрытая копия восстанавливается существующим bundle/guard и читается прежним модулем по старому контракту |

Для старого checkpoint-only механизма контроль удаления journal должен терять
строго определенные новые записи. После введения безопасного checkpoint нельзя
сохранять неверное требование "vault обязан остаться старым": проверка должна
доказывать новое принятое состояние через валидный checkpoint **или** его журнал.
Отрицательный контроль обязан удалять именно необходимую еще не checkpointed
историю и падать по сохранности данных, а не по отсутствию случайного файла.
Исходный красный результат сохраняется как историческое доказательство.

Для нативного модуля нужны unit/fault-injection проверки файловых переходов,
проверка инструментами памяти и настоящий engine smoke. Точки остановки в
реальных I/O-переходах должны быть частью тестовой сборки; положительный прогон
проверяет отдельно опубликованный production-бинарник без тестовых hooks.

Предварительный performance gate: не более 2 мс p99 на commit и 5 мс p99 на
полный обработчик учета смерти при 32 синтетических идентичностях и минимум
10 000 операций. Измерять CPU/frame time, размер vault/journal и число flush.
Отдельно проверить максимальный поддерживаемый размер и медленный диск.
Это предлагаемый порог приемки, не уже измеренный результат и не SLA.
Если он не выполняется, пересмотреть механизм/контракт, а не скрыто увеличить RPO.

## Порядок реализации и поставки

1. Зафиксировать выбранную гарантию, inventory потребителей модуля, форматы,
   размеры и пригодность закрепленной 32-битной сборки. Секреты не нужны.
2. Сделать прототип commit/checkpoint и fault-тесты вне production; проверить
   ограничения, лицензию, ABI и воспроизводимую упаковку исходников/бинарника.
3. Интегрировать addon, статус и тексты подтверждения; включить исправленную
   строгую crash-цепочку и отрицательные контроли в обязательный CI.
4. Пройти полный CI, независимо проверить скачанные артефакты и их source/
   binary hashes, затем выполнить новый native replay из скачанного пакета.
5. Подготовить отдельную R3-поставку пары addon + nVault. После разрешения и
   проверки пустого сервера остановить только игру, получить закрытую backup
   обоих vault/journal и off-host readback, установить проверенные артефакты,
   запустить игру и провести bounded приемку. Archive и агент не меняются.

Откат штатной установки: остановить игру при пустом сервере и вернуть прежние
совместимые бинарники, сохранив последние проверенные файлы данных. Прежний
модуль снова имеет прежнюю слабую гарантию; это должно быть явно указано.
Возврат предустановочной backup не является обычным откатом: он потеряет более
новые данные и требует отдельного решения. Если новый формат или неясное
состояние не допускают безопасного возврата, остановиться и согласовать recovery.

Создание/push/PR, новый модуль, изменения игрового runtime и production rollback
не выполняются на этапе подготовки этого плана. Наблюдение Archive и человеческий
пилот остаются отдельными gate; план не объявляет их завершенными.

## Проверенные исходные основания

Использован закрепленный AMXX 1.10.0.5481, commit
`eaab23f0068b34e295987486ed5ca89408326271`:

- [Journal.cpp](https://github.com/alliedmodders/amxmodx/blob/eaab23f0068b34e295987486ed5ca89408326271/modules/nvault/Journal.cpp): буферизованный журнал.
- [NVault.cpp](https://github.com/alliedmodders/amxmodx/blob/eaab23f0068b34e295987486ed5ca89408326271/modules/nvault/NVault.cpp): replay/erase при open и переписывание vault при close.
- [file.cpp](https://github.com/alliedmodders/amxmodx/blob/eaab23f0068b34e295987486ed5ca89408326271/amxmodx/file.cpp): `amx_fflush` требует действительный FileObject, нулевой handle возвращает -1, несмотря на комментарий include.

Это основания для выбора механизма, а не доказательство production-готовности.
Исходная неуспешная приемка сохранена; отдельно реализованное исправление и
его локальные проверки описаны в [отчете](player-data-durability-implementation.md).
