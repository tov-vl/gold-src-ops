# GoldSrcOps v2.12 Release Readiness

Review date: 2026-09-16. Status: release-candidate preparation; the repository
scope is integrated, while candidate publication and the bounded production
smoke remain pending.

## Scope

The v2.12 product scope is one Latest Round Overview slice integrated in
protected `main` through pull request
[#156](https://github.com/tov-vl/gold-src-ops/pull/156):

- The existing Reader server overview requests only the newest retained
  completed round through `GET /api/servers/{id}/game-events?limit=1`.
- The compact summary contains occurrence time, map, aggregate player count,
  and aggregate bot count only.
- The summary links to the existing bounded Events history.
- Empty history is a normal state, while an unavailable gameplay projection is
  isolated from the core A2S status so the overview remains useful.
- Static server-side rendering and the existing server-side browser token
  boundary remain unchanged.

The candidate baseline also carries the v2.10 production-acceptance and stable
publication records merged after the signed v2.10 application revision. It
contains the v2.11 pilot bundle, activation tooling, focused agent preflight
fixes, and the final bounded-pilot evidence from pull requests #148 through
#155. That pilot is closed: the temporary identity, credential, activation,
and plugin state was removed, the game runtime returned to its plugin-free
baseline, and the dormant agent remains inactive and boot-disabled. These
source and documentation changes do not authorize unattended game-event
delivery or expand the v2.12 runtime rollout.

This record freezes the release-candidate scope. New game-event types,
continuous producer or delivery activation, another gameplay event, event
pagination or export, schema changes, worker changes, identity-provider
changes, infrastructure changes, and mutation controls are not part of
`v2.12.0-rc.1` acceptance.

## Claim Boundary

The target remains one single-node control plane, one Web instance, and one
controlled external game server. Candidate acceptance can show that an
authenticated Reader can inspect the newest retained anonymous completed-round
summary on the existing server overview without disturbing monitoring or
reactivating the pilot. It cannot prove complete gameplay-history retention,
continuous delivery, high availability, multi-region resilience, long-term
reliability, user adoption, or an achieved SLO.

Public documentation may contain revision identifiers, image digests, workflow
links, sanitized counts, durations, and pass/fail results. Host and provider
identifiers, addresses, credentials, secret paths or aliases, operator identity,
raw database rows, tokens, source identities, event identifiers, and RCON
content stay outside Git.

## Compatibility Review

- The server overview composes an existing Reader endpoint and response
  contract; no API route or request or response schema changes.
- No EF Core migration or persistence model change exists in the v2.12
  application diff. A fresh backup, restore rehearsal, migration timing
  exercise, and previous-runtime schema rehearsal are therefore not routine
  v2.12 gates.
- The Web host requests exactly one record and preserves the existing bounded,
  minimized game-event contract.
- Gameplay-history failure does not replace or conceal the core server and A2S
  status. Empty and unavailable states are explicit and separate.
- The route remains static server-side rendering behind the existing `Reader`
  policy. Operator access follows the existing role hierarchy, and the page
  adds no mutation control.
- Ordinary rollback recreates API and Web from retained v2.10 digests. The
  database, Caddy, telemetry services, game service, and dormant pilot state
  remain unchanged.

## Ordered Release Sequence

### 1. Repository Closure

1. Merge this readiness record through protected `main`.
2. Repeat the exact `v2.10.0..main` commit and file inventory.
3. Require `Change Scope`, `Quality Gate`, `Container Smoke`, and `Browser
   Smoke` on the documentation-only readiness revision. The required check
   names remain present while the verified docs fast path avoids rebuilding
   unchanged application artifacts.

### 2. Candidate Publication

1. Create signed annotated tag `v2.12.0-rc.1` at the reviewed `main` revision.
2. Require build-mode publication of both API and Web images from that exact
   revision.
3. Record and independently verify both immutable digests, OCI revision
   metadata, and published-image smoke jobs.
4. Do not create a mutable alias or stable GitHub Release at this stage.

### 3. Digest-Pinned Rollout

1. Retain the current v2.10 API and Web digests in owner-only rollback
   configuration.
2. Capture a sanitized continuity baseline for public health, container and
   game-service identities, restart counts, A2S state, incidents, queues,
   scheduled-backup freshness, and the dormant game-event agent state.
3. Run production preflight against the verified candidate digests.
4. Recreate only API and Web. Do not recreate Caddy, PostgreSQL, telemetry, or
   the game service, and do not run a schema-changing operation.
5. Do not provision an identity, install or activate a plugin, start the
   producer or delivery path, or manufacture another gameplay event.

### 4. Short Production Smoke

Collect at least three healthy read-only samples spanning at least three
minutes and stop on the first unexplained failure:

1. Require public API liveness, API readiness, Web health, and the Web root to
   return HTTP `200`, with candidate version, revision, and exact image digests.
2. Verify anonymous routes remain sanitized and the game-event API remains
   authenticated.
3. Through an existing authenticated Operator session, which includes Reader
   access, render the controlled server overview and require the newest retained
   completed round to show occurrence time, map, aggregate players, and bots
   only. Follow the link to the existing bounded Events history.
4. Verify empty and unavailable fixture behavior from Browser Smoke on the exact
   immutable Web image. A production fault must not be manufactured to exercise
   those states.
5. Confirm browser content and storage contain no bearer token, credential,
   secret reference, source identity, event identity, ingestion metadata, or
   raw database record. Require no mutation control on the summary.
6. Require the controlled server to remain recently polled and reachable with
   zero bots. Require no unexpected container or game-service restart, newly
   opened incident, pending outbox item, dead letter, or incomplete command.
7. Require the game-event agent to remain inactive and boot-disabled, with no
   active producer or delivery path. Recheck public health and scheduled-backup
   freshness in the final sample.

This short smoke is sufficient for the additive read-only Web composition. It
requires no repeated interactive authorization once a valid session or
non-interactive evidence path is available. It is not a new soak, recovery
rehearsal, gameplay-delivery exercise, or SLO claim. Existing passive monitoring
continues independently.

## Failure And Rollback Rules

- Do not deploy if publication, digest verification, preflight, or the
  continuity baseline fails.
- On candidate startup, health, authorization, latest-round boundary, failure
  isolation, or rendering failure, recreate API and Web together from retained
  v2.10 digests.
- Do not mutate PostgreSQL, monitoring state, game-event state, RCON state,
  incident history, command history, snapshot history, or durable queues to
  make the smoke pass.
- Do not reactivate the v2.11 pilot as part of v2.12 release acceptance.
- Store sanitized smoke evidence outside Git as an owner-only regular file.

## Stable Publication Gate

Stable `v2.12.0` remains blocked until:

1. The candidate identity table is complete from verified publication output.
2. The digest-pinned rollout and short production smoke pass.
3. Production has either retained the candidate or cleanly rolled back with a
   documented reason.
4. A signed stable tag promotes the exact accepted API and Web digests without
   rebuilding them, and both stable references pass published-image smoke.

Production acceptance and stable-publication documentation should use short
follow-up pull requests so the stable tag continues to target the exact
accepted candidate revision.
