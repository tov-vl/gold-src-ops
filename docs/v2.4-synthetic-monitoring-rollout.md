# GoldSrcOps v2.4 Synthetic Monitoring Rollout

Rollout date: 2026-09-04. Status: three non-authoritative Grafana Cloud
Synthetic Monitoring checks are enabled under monitor revision
`v2-4-shadow-001`. `API-01` remains `Draft`; these samples do not enter an
official SLI window.

## Account Boundary

The owner created the Grafana Cloud account with accurate current details and
initialized Synthetic Monitoring without adding a payment card or purchasing a
paid plan. The account currently has the standard 14-day trial. Grafana's
published billing documentation states that an account moves to the Free plan
when the trial completes, and current pricing describes that plan as free with
no credit card required.

Successful signup proves current technical account availability only. Continued
service remains subject to the provider's terms, export controls, product
changes, and free-plan limits. GoldSrcOps therefore keeps its normalized schema
and independent archive as an exit path.

Provider account metadata, resource identifiers, owner identity, and
credentials are intentionally excluded from this document and from Git.

| `goldsrcops-api-ready-primary-shadow` | `https://api.goldsrcops.com/health/ready` | `primary` | Frankfurt, DE (AWS) | 60 seconds | 44,640 |
| `goldsrcops-api-live-diagnostic-shadow` | `https://api.goldsrcops.com/health/live` | `diagnostic` | Frankfurt, DE (AWS) | 60 seconds | 44,640 |
| `goldsrcops-api-ready-diagnostic-shadow` | `https://api.goldsrcops.com/health/ready` | `diagnostic` | Stockholm, SE (AWS) | 300 seconds | 8,928 |

Every check has the following effective request contract:

- HTTP `GET` with no body, authentication, cookies, query parameters, or
  response-body assertion;
- a 10-second complete timeout;
- redirect following disabled;
- target certificate and hostname validation enabled, with TLS required;
- exactly HTTP `200` accepted;
- `User-Agent: GoldSrcOps-Availability/1.0`;
- the default reduced metric set; and
- built-in per-check alerts disabled.

The custom labels are:

| Label | Primary value | Diagnostic value |
| --- | --- | --- |

| `role` | `primary` | `diagnostic` |

The job names and labels explicitly identify this revision as shadow evidence.
They do not create an activation timestamp or make Grafana's displayed uptime
canonical.

## Initial Verification

The provider UI confirmed that both selected public probes were online and
available to the account. Before each check was saved, its interactive test
completed target resolution and an HTTP request-response round trip without a
reported error. The saved forms were then re-read and matched the sanitized
configuration above. Initial scheduled results from both Frankfurt checks and
the Stockholm check reported 100% uptime and reachability. These early provider
aggregates validate setup only; they are not an `API-01` result.

Grafana's per-check calculator reports a combined maximum-month estimate of
98,208 API test executions:

```text
primary readiness:       1 probe * 1 check * 44,640 / 1 = 44,640
diagnostic liveness:     1 probe * 1 check * 44,640 / 1 = 44,640
diagnostic readiness:    1 probe * 1 check * 44,640 / 5 =  8,928
total:                                                     98,208
free monthly allowance:                                  100,000
remaining margin:                                           1,792
```

This uses a conservative 31-day month. Do not add saved checks, locations, or a
shorter interval without reviewing the complete account usage estimate. Manual
tests and temporary failure-path checks must also stay within the remaining
allowance.

## Remaining Gates

The checks may continue producing shadow telemetry, but `API-01` cannot leave
`Draft` until all of the following are complete:

1. **Live export proved 2026-09-04:** the dedicated `metrics:read` credential
   produced one bounded normalized export without retaining response content;
2. **Implemented 2026-09-04:** deterministic normalization, bounded overlap
   export, source-timestamp correlation, create-only JSONL, deduplication, and
   expected-slot evaluation;
3. **Live archive proved 2026-09-04:** a separate private B2 namespace with split
   prefix-scoped reader/writer credentials accepted one content-addressed upload,
   rejected a sequential duplicate before a second upload, and returned the same
   25-record segment for SHA-256 and deterministic report verification;
4. **Transport path proved 2026-09-05:** missing-slot, retry, DNS, connect,
   TLS, timeout, redirect, non-`200`, 1,440-slot, and 216/217 budget behavior,
   including bounded Loki parsing, unknown and ambiguous failure fallback,
   correlation, and payload-safe exception paths are fixture-covered. A scoped
   `logs:read` credential and controlled diagnostic check then proved live DNS
   classification without disrupting the production endpoint;
5. test the custom notification route and resolution policy; and
6. complete and review a contiguous 24-hour shadow window before recording a
   prospective activation tuple.

No user-managed Synthetic Monitoring configuration token was created for the
manual setup. The Metrics API, Loki, and B2 credentials are separate, narrowly
scoped, time-bounded where supported, and stored outside Git. The serialized
GitHub-hosted scheduler environment, reviewed exporter pin, scheduler enablement,
and manual archive/recovery cycle are complete. The live DNS proof passed in
[run 33964036998](https://github.com/tov-vl/gold-src-ops/actions/runs/33964036998),
scheduled export/archive passed in
[run 33964685839](https://github.com/tov-vl/gold-src-ops/actions/runs/33964685839),
and independent read-only recovery of that scheduled segment passed digest,
canonical-record, and deterministic-report verification in
[run 33968872991](https://github.com/tov-vl/gold-src-ops/actions/runs/33968872991).
No raw segment was retained as a GitHub artifact. These runs close the current
availability implementation slice, but irregular scheduler invocations do not
establish hourly continuity. Provider cadence compatibility, alert routing, and

## 24-Hour Shadow Audits

### First attempt

On 2026-09-08,
[run 34257679406](https://github.com/tov-vl/gold-src-ops/actions/runs/34257679406)
evaluated the fixed window from `2026-09-07T16:58:00Z` through
`2026-09-08T16:58:00Z`. The report had 1,440 expected, evaluated, and mature
slots, with 1,439 good slots and one bad slot classified as missing. There were
no duplicate records, pending slots, or ignored non-canonical attempts. The
99.93056% shadow result met the draft percentage target, but the missing slot
failed the stricter activation-readiness integrity gate. No evidence was
archived, the runner deleted its temporary raw files, and `API-01` remains
`Draft`.

A bounded read-only follow-up localized the missing population entry to the
minute beginning at `2026-09-07T18:45:00Z`. The primary source timestamps moved
from their preceding 60-second cadence to a roughly 73-second interval that
crossed the next UTC-minute boundary. Adjacent samples retained the same check
configuration and were successful, while the diagnostic check in the same
public location continued reporting. This is consistent with an isolated
primary-check scheduling delay rather than a demonstrated API outage, but it
does not establish the provider's internal root cause. The immediately
preceding 24-hour range had no equivalent missing-minute signal in the bounded
diagnostic query; that comparison is context only and is not an official audit.

Do not waive or reclassify the missing slot. A later activation-readiness run
must use a fresh contiguous window that excludes it and must still contain
exactly 1,440 mature slots with no missing data. Alert routing remains a
separate activation gate.

### Second attempt

On 2026-09-09,
[run 34340321910](https://github.com/tov-vl/gold-src-ops/actions/runs/34340321910)
evaluated a different fixed window from `2026-09-08T10:15:00Z` through
`2026-09-09T10:15:00Z`. It again evaluated all 1,440 mature slots, with 1,439
good slots and one bad slot classified as missing. Identity matched, duplicate
and ignored non-canonical counts were zero, and the 99.93056% aggregate met the
draft percentage target. The population-completeness gate nevertheless failed,
no evidence was archived, and temporary raw files were removed.

The missing minute began at `2026-09-09T08:49:00Z`. A bounded read-only source
timestamp query showed the primary cadence moving from `08:48:29Z` to
`08:50:13Z`, a 104-second interval crossing that UTC-minute slot. The Frankfurt
liveness diagnostic had an overlapping source gap from `08:47:59Z` to
`08:50:06Z`. Meanwhile, the independent readiness diagnostic in the second
public location reported a successful source sample at `08:49:47Z`, and its
bounded success query remained successful throughout the comparison. Adjacent
primary values were also successful. This evidence is consistent with a
location-level public-probe scheduling disruption rather than a demonstrated
API outage, but it does not establish the provider's internal root cause.

Two distinct 24-hour windows have now each lost one primary UTC-minute slot.
Do not keep rerunning the audit merely to obtain a chance pass. Before another
activation-readiness run, review whether the provider cadence can satisfy the
current slot-attribution contract or select a different primary location or
provider. Any measurement change requires a reviewed monitor revision and new
shadow evidence. Missing slots remain bad by contract, and alert routing remains
a separate activation gate.
