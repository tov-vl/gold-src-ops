# v2.72 - Public API read observability

The Web host records complete public API read duration, including response-body
JSON parsing. One histogram supplies duration, counts and outcomes. The five-second
deadline and page fallbacks from v2.71 remain in place.

| Metric | Contract |
| --- | --- |
| Instrument | `goldsrcops.web.public_api.duration`, seconds |
| Prometheus | `goldsrcops_web_public_api_duration_seconds_{bucket,sum,count}` |
| Operations | `status`, `history`, `leaderboard`, `server` |
| Outcomes | `success`, `not_found`, `error`, `timeout`, `canceled` |
| Labels | Only operation and outcome; no URL, query, player or server identifier |

A successful read includes deserialization and a non-null response. Optional
leaderboard/server 404 responses are `not_found`; other unsuccessful HTTP status,
invalid JSON and empty responses are errors. Caller cancellation has precedence
and is excluded from the dashboard's failure ratio and latency. Each actual read
records once, including failures. Invalid history windows never start a read.

## Private transport and dashboard

`Telemetry:Otlp:Enabled` defaults to false. Enabled export requires an HTTP(S)
origin without credentials, path, query or fragment. Web exports only this meter
using gRPC to the existing Collector, every 60 seconds with a 30-second export
budget. Export is asynchronous and Collector availability does not gate startup
or page responses. Web does not expose `/metrics` or browser telemetry.

Production Web joins the internal telemetry network with a dynamically assigned
address and retains edge as its preferred egress gateway. API, Collector,
Prometheus and Grafana keep their existing configuration. A provisioned dashboard,
`goldsrcops-web-public-api`, uses the existing Prometheus datasource. Grafana
loads the new file through its existing directory mount without restart.

The six panels show cumulative outcomes, request rate, p95, failure ratio,
timeouts and caller cancellations. Rates and quantiles use 15 minutes; sparse
traffic limits their precision. A zero denominator or absent telemetry remains
unavailable rather than being presented as healthy. Cumulative counts reset with
the Web process. This is passive request telemetry, not an availability probe or
SLO. No alert rules or personal notification channels are added.

## Verification and recovery boundary

Risk R3 is limited to Web telemetry network attachment and dashboard provisioning.
Use the production Compose contract check and the synthetic isolated rehearsal:

```powershell
docker build -f Dockerfile.web -t goldsrcops-web-observability:local .
python tools/smoke/web-public-api-stack.py --web-image goldsrcops-web-observability:local
```

The rehearsal uses pinned observability images, local synthetic API data and
loopback-only test ports. It checks all four operations, body timeout, optional
404, failure, empty dashboard data, PromQL, Collector outage and removal/restoration
of Web's telemetry connection. Unit tests cover caller cancellation independently.

The release saves the previous Web digest, exact Compose file and dashboard
inventory before a hash-bound rollout. Only Web may be recreated. Restore Compose
and the previous digest on failed acceptance; preserve API, database, game and
telemetry containers and all volumes. The new provisioned dashboard is retained
as diagnostic UI on rollback; it has no new Web observations after reverting the
exporter. This explicit recovery boundary avoids changing Grafana state or other
dashboards.

Production acceptance requires the reviewed Web digest, private network and
port readback, all four successful operations in Prometheus, provisioned Grafana
panel/query readback, public page checks, zero unexpected restarts and continuity
of the six unaffected containers. Production failure injection is excluded.
